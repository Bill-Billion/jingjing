## 1. 对V5用户关系的理解

- 不再要求进App先选“艺人/买家/机构”才能使用；全员同一套“广场/试镜/通告/消息/我的”。同账号可以买，也可经营自己获准使用的艺人资产。
- 登录人、订单签约/付款主体、真实艺人权利人、数字人、造型/声音版本、本次演出角色分别保存。导航一致，不代表企业授权和个人授权合并。买单时显示“谁下单/向谁付款”；替机构办事保留代表权检查；为项目选艺人时再选具体数字人/版本/用途，不能靠全局换头像修改旧订单阵容。

- V5与合同模板在作品/模型权属上仍有冲突，按D1 DEC-08逐商品确认，不能把以上产品方向当法律结论。
- 用户上轮反映的“机构不绑定哪位艺人”在V5应落到明确的订单出演/项目角色绑定，不能仅靠前端把个人机构页面拆开解决；后台也必须知道真实人、数字人、造型声音和授权版本。

## 3. 交易与消息必须分清的用户路线

1. 买现成视频：广场视频/艺人商品 → 看许可 → 下单付款 → 服务器核验 → 解锁/下载。不能要求先建数字人，不能填故事或进人工制作等待。
2. 私人定制：品类 → 填故事/保存草稿/补件 → 客服确认 → 报价合同 → 首款30%托管 → 派单 → 正式预览与约定改稿、按合同补至累计90% → 客户确认成片 → 尾款10% → 正式文件交付下载（首次预览与90%补款先后仍待该商品确认）。样片制作服务50/50另配付款计划，不能混用。
3. 试镜：公开可约艺人 → 一口价含交通 → 付款 → 接单/拒绝 → 接受后行程与会话 → 到场6照1视频 → 确认与清分；拒绝/未接受退款。试镜并不转让后续出演权。
4. 通告/投稿：六类通告或出品人 → 单向结构化意向 → 感兴趣/婉拒 → 客服工单 → 正式报价/付款/接受 → 订单会话。“感兴趣”不能直接开自由聊、确定角色或自动下单。
5. 共创：一个主订单 → 各人接受并授权 → 按真实权利人去重 → 10人+授权+付款等条件 → 开工申请 → 20人优惠快照 → 主片/本人片段按权限查看；发起人不能代所有人签字，同人多个数字人不增加人数。
6. 消费、晶钻、成长、券、现金余额、供给方应付分别展示；不能把现有finance余额改名做买家钱包。

会话门禁注意：V5 2.8使用“付款或接受”，2.10细表使用“接受且付款”；D1 DEC-03正确保留待确认。可以按更具体的表起草AND，但正式启用前必须留下业务裁决。官方定制一直走平台客服；艺人/MCN联系方式、买卖双方会话、平台通用客服是三个不同入口。

### 接口什么时候交给前端

把“第一条可开发的接口及例子”作为预先约定的小交付点，而不是等整个大功能写完。这份交付包括当前来源/商品类型、身份/艺人/订单对象关系、请求与响应、状态/下一步动作、失败原因、重复操作、版本冲突、分页及旧版兼容。正式编写阶段计划时确认此点是允许集中上传的节点；通过后发布同一份契约/固定提交供前端开发，不能用以前授权恢复逐小任务push。

前端可在隔离示例上写页面，示例只匹配契约；Core随即实现同一接口和真实隔离MySQL检查。前端从示例切到后端时不改字段格式；双方用相同测试账户、资料与规则版本。后端未实现时页面显示真实未开放，不把stub放入正式包。程序生成的类型重新生成，不手改。

默认每个明确业务成果只保留一个集成合并申请。前后端分别在core/与ux/工作分支开发；阶段交付时，由当次明确登记的协调者保留双方原提交整合、解决冲突并跑同版本检查，再集中推送和提出申请。不能为了合在一起覆盖队友的原提交，不能擅自替双方改共享文件。已有阶段申请的修复继续更新同一个入口，不因每次聊天新增申请。

共享接口如需提前给另一方使用，把它列成预先约定、可独立检查的小交付点；交付内容和兼容方式齐备后集中上传，不恢复逐任务推送。其后各自继续实现业务，避免把整套后台完成作为前端开工条件。

交付说明同时记录前后端提交和整合后的提交，所有跨端测试对应整合版本。由另一名开发者或实际指定的独立审阅人检查代码和结果，留下真实账号、意见及处理记录；本侧Codex、其子代理或自测不能冒充队友批准。共享接口、权限、资金、授权和迁移必须交叉审阅后才合入integration。main、生产部署及真实收费仍单独处理。现有[阶段集中交付规则](../../collaboration/STAGED_DELIVERY.md)的这些要求继续适用。
