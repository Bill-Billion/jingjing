# 首两轮交接：先让故事真正送到运营，再接补件和报价

这是下一轮的具体施工说明。下面接口路径/字段是待双方检查的设计，尚未写入正式OpenAPI，尚未实现；不是可直接调用的服务。本侧可以据此开展已授权的本地开发，前端伙伴可并行检查页面所需信息，不能把“文件写好”写成“双方已约定”。

## 第一轮交出什么

普通用户从广场进入定制入口（不必先创建数字人或充值星探），选品类，保存未填完的故事，从“我的”找回再继续；正式提交后看到“平台待查看”。有受理权限的运营人员能看到同一份正式提交，开始受理。故事提交不产生收款，不代表资料授权通过，不自动开工。

第一轮先交可独立检查的文字流程；涉及必填附件的模板，只有私有上传、用途和读取权限具备后才允许完整提交。不得为了先跑通而把必填附件改成可选、把他人照片当普通公开文件，或假报已实名。隔离测试用合成资料；真实敏感材料的提交条件另行核验。

本侧负责规则、MySQL迁移、接口、权限和测试资料；前端负责App动态表单、草稿列表/恢复、提交状态以及运营待受理页面。具体前端人员仍待队友本人确认。第一轮不以全部数字人、全部收银或所有页面写完为前置。

## 页面怎样让人看懂

- 入口使用“把我的故事拍成片”或同等清楚名称，说明是平台人工受理制作；艺人合作邀约、现货购买、共创不要共用一个含混按钮。
- 品类改变实际问题，不仅改标题。婚礼/亲情/人生/创业/宠物等字段按V5来源和已发布模板呈现；只问本次制作必要的信息。
- 草稿可以不完整；正式提交逐字段指出缺什么。清空输入后保持空，不能用旧值偷偷回填。
- 保存后说明已保存，正式提交后说明谁处理、在哪里查看进度。承诺响应期限只有已批准配置才显示。
- 运营只看到已提交版本；受理不修改用户原话。个人草稿不因切机构变成机构资产，机构成员也不能看到不属于其权限的需求。
- 对应Figma重点为63平台制作服务、64定制/共创需求、65我的出品与参演，以及后续补件状态；画面调整见原型审阅，不能直接复制本地PR0.5的静态表单逻辑。

## 第一轮的最小接口草案

复用既有 `/api/v1/me`、`/api/v1/me/parties`、主体成员、规则内容与错误格式，不新建第二套登录。沿用Bearer、操作主体、请求去重键、并发版本和请求编号。以下八项对应真实用户动作；最终名称以双方审阅后进入contracts的版本为准。

|用户动作|拟用接口|必要边界|
|---|---|---|
|看可用定制品类和字段|GET /api/v1/customization-categories|仅返回已发布可用模板；收费规格未定不擅填价格|
|创建草稿|POST /api/v1/customization-requests|记录创建人及当次责任主体；草稿可不完整|
|找回自己的需求|GET /api/v1/customization-requests|按当前有权主体分页；不把所有运营/机构成员默认授权|
|读取一份需求|GET /api/v1/customization-requests/{id}|本人可读草稿；运营按受理岗位和已提交范围读，不能读未提交私密内容|
|保存草稿|PATCH /api/v1/customization-requests/{id}|检查并发版本；不允许前端写PAID/已审核等状态|
|正式提交|POST /api/v1/customization-requests/{id}/submissions|按所绑定模板校验，保存不可变提交版本；重复请求返回原结果|
|运营看待受理需求|GET /api/v1/operations/customization-requests|只给有对应岗位动作的人员必要字段；敏感详情按需打开|
|运营开始受理|POST /api/v1/operations/customization-requests/{id}/intake|记录受理人和时间；不是报价批准、人格授权或制作开工|

既有私有附件接口目前用途枚举和8MB限制不直接适合故事素材。需要新增准确用途及有边界的媒体处理，不借用RIGHTS_EVIDENCE掩盖新用途。第一轮若尚未完成附件扩展，如实交付文字流程，并保持相关含附件场景未通过，不把整包DEL-14标完成。

需要保存的最小事实：需求ID、创建账号、责任主体、品类和字段版本、答案、受控附件引用、对象版本、正式提交版本、提交/受理时间、当前有权动作。后续报价/订单/制作仅引用已有对象；第一轮关联为空，不创建一套新的定制交易账。

草稿、正式提交和受理中分别呈现；补件、报价在第二轮扩展。模板更新不覆盖已有草稿或正式提交；必须迁移时显示差异并让用户明确确认。故事里的真人意向可以暂未选定演员，开工前必须落实具体演员/数字人及授权。

## 第二轮接到哪里

运营针对已提交版本列出“缺哪一项、为什么需要、怎样补”；用户补后提交新版本，旧版保留。具有真实商户授权的人将当前版本关联到既有trade报价；独立复核后，买家确认生成同一套交易系统中的未付款订单。

现有报价写入要求合法商户OWNER，客服受理资格不自动等于商户报价权。普通运营不能冒充商户、代表用户同意或绕过独立复核。若需员工委托，应先实现明确授权动作。需求状态引用报价/订单事实，不另存一个能被随意改成已付款的副本。

本侧同时补齐新版商品、规则快照、付款计划和财务校验兼容。平台/MCN新分账须与财务应付来源同时修改；MCN默认20%、本人确认可约10%—30%，无MCN和不同有效比例分别验算，不能一律固定20%，普通人工定制按自身合同规则，不因样例就套现货18%或商单22%。第二轮可以用标明用途的测试报价验算；未获批准的真实商品不发布。
