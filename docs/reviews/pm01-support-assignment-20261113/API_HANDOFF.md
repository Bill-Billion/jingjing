# 合作案件客服指派：后端接口交接

候选接口0.31.61-rc.1，迁移0214；最终来源188fa0e3（初始开发bd467e65），最终同版测试见REPORT。后端负责人chengcongcong222。仅共享接口事实，当前不安排前端开发修补，未代Bill-Billion认领。

## 原需求和实施范围

原ACC-DEL-11.03“同意合作生成一次客服工单，指派并补需求报价”。对应V5总纲2.6/2.8/2.10的意向同意后客服人工对接，保留原意向、授权、报价、合同及付款的关联。具体调度权限、并发保护、转派失权和最小返回属于流程补全，不是新增付费服务或自由聊天。

## 现在如何办理

|接口|用途|权限与前提|
|---|---|---|
|GET /api/v1/notices/cases/{record_id}/assignment-options|查询本案件有效候选客服，仅账号编号和名称|独立NOTICE_ASSIGN，案件仍待接管、原合作有效；支持cursor/limit，空页可能还有游标|
|POST /api/v1/notices/cases/{record_id}/assignment|指派或交接；body为account_id、reason|独立NOTICE_ASSIGN；目标具有效NOTICE_SUPPORT且非案件参与方；If-Match和Idempotency-Key必填|
|GET /api/v1/notices/cases/{record_id}/assignment-history|读取原承办/新承办、调度人、时间、方式和理由|当前有效承办人或独立NOTICE_ASSIGN；cursor为对象版本整数，limit最多100|

三项均为账号级运营入口，不带X-Acting-Party。不存在自动授予的调度员，也不通过这几个接口授予岗位权限。用户侧仍从原案件读取当前承办人、时间和方式，内部调度理由与调度人仅授权历史可读。

已有quote-options和quote接口保留：已明确指派时，只允许当前有效承办人；未指派时继续允许独立NOTICE_SUPPORT处理，并在实际关联报价的同一事务中记首次承办（QUOTE_CLAIM）。这不意味着所有旧案件已补造承办历史，既有已关联案件只保留已有事实。

指派后的当前案件data.support_assignment是增量可选字段：account_id、assigned_at、mode（ASSIGNED或QUOTE_CLAIM）。旧记录可不存在，不能把缺字段解释成已完成指派。调度历史不返回给买卖双方或原承办人；双方自己的原案件与意向仍按原权限可读。

## 恢复与拒绝

- 转派后原承办人不能再读受指派案件、查询该案报价选择、看调度历史或关联报价。岗位撤销、停用账号、加入案件参与方后同样重核；不会因旧命令存在而绕过。
- 同一指派键重试不会再增历史或通知；若中间已经转派，返回当前承办状态，不返回可误认成当前的旧指派结果。
- 版本已变返回VERSION_CONFLICT。案件关闭或已关联报价后禁止改派（NOTICE_CASE_NOT_OPEN）；原合同、已成立订单不会被调度动作重写。
- 调度权不等于承办权。持NOTICE_ASSIGN但未被指派或不具NOTICE_SUPPORT者，不可借调度权限关联报价。目标候选查询和实际提交分别检查有效权限。
- 新增的指派历史、当前案件版本、通知事件处于同一事务；历史写入失败时整笔回滚，不能留下半次转派。

## 部署及验证边界

0213仅扩展可授予的权限枚举，0214仅新增notice_case_assignments历史表；不更改旧迁移，不授予账号，不改现有订单。需要按项目既有迁移审阅/回退要求处理，不直接倒删新表以伪装旧版本；实际旧库样本与恢复签收仍单列。
