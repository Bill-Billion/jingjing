# W18误充值退款后续执行边界

本页是原维护计划W18的流程补全和实施安排，不是新增商业政策、已批准的具体退款或已接通的渠道协议。负责人chengcongcong222；原文和本批完成范围见[报告](REPORT.md)。

## 本批已经具备什么

assessRefund在账户锁内读取同笔成功充值与关联消费分配，按“原充值－已原路退金额－净消费－付款冻结－未知付款占用”给出当前可退余额；读取不生成退款、支付指令或资金占用。错误商户/渠道/环境/版本不跨账核算。输出带来源摘要与观察时间，只供核对，不能跨事务充当可执行批准。

本批尚无原路退款申请记录，因此没有将“申请中的原路退款占用”加入余额分配。下一步一旦新增退款申请占用，必须同步纳入cash.snapshot、overview、原充值核算与对账，防止同一余额一边付款、一边退款。不得只新增一个退款发送器而遗漏原付款路径。

[21号合同第十三条](../../sources/contracts-20261029/extracted/21.md)原文：“未成年人未经监护人同意发生的充值、消费、抽奖，经核实后按规定予以退款”；[37号合同](../../sources/contracts-20261029/extracted/37.md)原文：“未成年人误充、误消费，凭监护人材料核实后按规定原路退回”。因此，本次available_for_refund_minor仅表示原充值批次当前未被占用的资金，不是案件退款资格或最终核定金额。本人只读入口也不能代替监护人材料审核与授权代办。已消费部分的退款处理及资金来源必须按案件另核，不能因为可用余额低于申请额就自动驳回整个案件。

## 后端可继续独立实施的顺序

|步骤|必须满足的约束|验收方式|
|---|---|---|
|1 同笔申请与独立审核|绑定原充值/原交易/本人/渠道快照；审核使用现有运营授权与禁止关联方自审规则，案件核定金额与当前可直接占用余额分别记录，缺额须核原消费逆向或其他合法资金来源，不透支此批次；同键同输入返回原申请，同键变金额冲突。退款资格按有效制度和案件事实，不通过核算自动批准或驳回|未批准不可发送；本人或关联方不得自审；原键重放不新建，改金额不偷换批准；监护代办与已消费案件不被本人余额入口替代|
|2 原批次资金占用|审核通过后和实际发送前均锁定账户、重核原账；资金占用与批准同事务。支付分配和退款分配共用同一原充值可用余额，失败整笔回滚|同一余额竞争付款/两次退款，只允许可承担的一方成功；占用失败不得留下已批准可发送记录|
|3 原请求发送与未知恢复|采用现有可信适配与任务租约约束；记录稳定的原请求标识。发送后超时/进程退出只查原请求，结果未明保留占用；新操作键不能绕过同笔未决占用|丢响应、任务重启、租约失效不得重复出款；未知状态不提前释放或扣减会员|
|4 可信回执落账|只有经渠道验证/查询的回执能确认成功或明确未退款关闭；同时核原交易、退款请求、绑定、币种和金额。成功累计写原充值refunded_minor并结清对应占用；重复回执不再扣；矛盾/晚到回执进入复核|同笔部分/余款退款、重复回执、错金额/商户/环境、关闭后晚成功分别验证；任何落账审计失败整事务回滚|
|5 会员、余额与成长核对|到账后会员按原充值净额重新计算；消费成长仍依原订单消费/退款事实；充值退款不得制造消费积分、抹历史订单或改已签快照|同笔退款前后余额、会员有效期/等级、消费成长逐项对应；模拟到账与真实回执分别登记|

上述是待实施的约束与验收办法，不能记为已开发或本批已通过。当前全量测试只能证明本批只读能力和现有功能，不证明未写的退款执行链。
