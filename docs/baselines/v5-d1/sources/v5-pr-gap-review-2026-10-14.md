# 晶晶日上 V5 需求与当前 PR 差距审阅

审阅日期：2026-10-14。对象是需求变更记录中的 V5 总纲、开发交接包非机密业务资料、合规包、PR0.5 原型与增量任务单，以及 GitHub 当前最新 PR23。仅审阅，没有修改业务代码、原型或原需求文件。

**结论：06 的产品方向和两流分工基本合理，但不能直接作为从当前 PR 交付完整 V5 的开发清单。** 它主要整理了 V4 到 V5 的新增专题，而当前代码尚未完成 V4 已要求、V5 继续保留的一大批业务。另一方面，人工制作、合同、订单、反馈验收等已有基础，应继续使用，避免重复建设。

差距集中在三个层次：补齐消费者业务链；迁移导航、权限和分账等旧规则；落实 V5 的故事采集、共创、晶钻权益及用户保护。只完成 06 的 10 项 Core 和 8 项 Experience，仍不足以交付原型展示的全部产品。

## 最需要先修正的判断

**一，不能把“V5 保留 V4 设计”写成“当前 PR 已具备这些功能”。** [06 第31行][task-navigation]的“继续五Tab”和[01 第181行][review-navigation]的“不改五Tab”，适用于原型迭代，不能指导当前代码直接增量施工。活跃 App 仍是“首页／入戏／培育／成角／我的”，其导航测试也保护旧标签；公开艺人目录、数字人管理等入口仍明确未开放。需要迁移入口、页面归属、返回路径、深链、旧导航测试和仓库旧版实现说明。[导航代码][app-nav] [活跃路由][app-routes] [导航测试][app-nav-test]

**二，分账需要改算法，而且必须保留历史版本。** [01 第177行][review-finance]说“现有18/22、80/20及订单快照继续保留”，但当前代码的 MCN 金额从平台佣金里扣；V5 要先扣平台佣金，剩余再按艺人80%、MCN20%分配。财务应付校验也绑定旧算法，不能只改显示文案或一个计算函数。[现有佣金算法][be-commission] [财务来源校验][be-settlement]

以实收100元、有 MCN、暂不计推荐返佣为例：

| 业务 | 当前算法代入新比例的实际结果 | V5 目标结果 |
|---|---|---|
| 数字商品，平台18%、MCN20% | 报 MCN_EXCEEDS_PLATFORM，拒绝计算 | 平台18、MCN16.40、艺人65.60 |
| 商单／试镜，平台22%、MCN20% | 平台2、MCN20、艺人78 | 平台22、MCN15.60、艺人62.40 |

上面两种旧算法结果已直接运行纯函数复现。应增加 V5 分账规则版本、MCN 与推荐返佣分别计账、新旧订单按快照分流、部分退款冲回、尾差和对账测试。旧测试通过只说明旧口径被稳定实现，并不说明符合 V5。

**三，真人承制工作流已有较完整基础，不应重新做第二套。** 当前后端已实现按订单行建制作项目、受派人权限、四阶段版本、权利与内容审查、反馈、返修、客户验收及受控下载；前端也有相应页面。CORE-V5-03 应写成扩展现有制作链，增量在故事卡与报价关联、品类模板、补件、档期、自营与外部承制区别、共创个人片段等。[制作后端][be-production] [制作前端][app-production]

**四，现货购买和定制制作必须是两条链。** [01 第77行][review-flow]把“选择高定或现成模板”之后都串到故事卡、人工报价和制作，虽然后一段又正确解释了现货性质，流程仍会误导实现。V5 要求现货即买即得、不填复杂表单。现有剧本开发许可不等于成片商品许可，旧视频路由目前也只是映射到制作项目。[V5 现货要求][v5-stock] [现有许可模型][be-licensing] [视频路由][app-video]

- 现货：商品与许可说明 → 下单付款 → 服务端核验 → 购买权益 → 播放／受控下载。
- 定制或改版：故事采集 → 报价与合同 → 约定付款 → 派单制作 → 版本反馈 → 最终验收与交付。

**五，“有通知和留言”不能计作 V5 消息已完成。** 当前是系统通知与订单／项目内纯文本留言；V5 要单向意向／投稿、感兴趣或婉拒、客服介入、条件成立后的订单双向会话，以及冻结、归档和访问控制。旧 SQLite 路由虽然有同名聊天功能，也不在新 MySQL 主接口链中。06 没有单列这条 Core 与 Experience 共同任务。[现有留言][be-comments] [当前消息 API][app-messages]

**六，实名、数字人和晶钻账本不能当作已完成依赖。** 当前 AVATAR 是私有档案，创建结果没有真实模型引用；授权中的身份核验明确为 NOT_VERIFIED。当前 finance 余额是合作方应付账，不是消费者储值钱包。共创去重、青少年限制、星探资格和抽奖需要先有对应业务模型与接口，而不只是等供应商开通。[数字人及授权记录][be-works] [财务余额含义][be-balance]

**七，撤下旧作者自助入口要落实到代码与权限。** V5 本期不开放剧本作者自助上传，但当前 App 和 Web 仍有作者申请、新投稿等正式入口。应停止新增自助供稿，保留历史记录与权利证据，交由 CMS 代录。不能误删 V5 仍需要的艺人／MCN 自制视频上架。[V5 作者范围][v5-author] [作者入口][app-author] [Web 路由][web-routes]

## 需要补入决策台账的冲突

已有的权属、十连保底、IAP有效期、真实服务证据等风险识别值得保留。以下矛盾也会直接改变价格、权限或退款，不能由两位开发者各选一份材料实现。

| 待统一事项 | 冲突来源 | 对开发的影响 |
|---|---|---|
| 制作金能否用于样片 | V5第427行允许“承制／定制片／样片”；抽奖V2 §3及合规治理明确排除样片 | 商品适用范围、可用券计算、核销与退款 |
| 免单奖的公示价值 | V5第428行约1800元；抽奖V2 §3写市场价约3000、成本约1800 | 免单SKU、公示价值、费用上限、成本应分字段 |
| 会话何时开放 | V5第311行“付款托管或邀约接受”；第344—345行“接单／接受＋托管” | 已接受但未付款能否开聊和显示联系信息，必须有反例测试 |

## 建议的开发衔接顺序

1. **建立当前PR到完整V5的覆盖表。** 每条包含原需求／旧REQ、当前代码和测试、处理方式、Core与Experience任务、接口版本、验收路径与外部条件。同步旧导航、作者端和分账规范，解决会让两个开发流采用相反规则的冲突。
2. **优先贯通可复用的定制链，并补关键基础契约。** Core扩展故事卡与现有报价／制作模块，Experience接定制前台；同时明确本人权利主体、实名年龄、商品与订单类型、现金／积分／成长的边界。供应商未就绪时可开发和隔离测试，不标为正式可用。
3. **把继承业务作为显式工作推进。** 公开艺人／现货购买、线下试镜、通告／投稿／会话、认证／星探／榜单、MCN经营分别形成可检查的小阶段。现货付款与许可、试镜接拒单与退款不能只有页面壳。
4. **共创与晶钻权益按真实依赖接入。** 共创依赖本人授权、订单和优惠规则；抽奖依赖积分来源、退款／过期、年龄和资格；卡券依赖商品、收银台和可兑批次。固定兑换、曝光卡、月冠军和推荐返佣一并纳入，而不是开奖后再补。
5. **用跨端业务链验收。** 现货付款→解锁；试镜邀约→接拒单→取样→确认→清分；投稿→客服→订单会话；故事→报价付款→制作→验收；共创→授权→成团→个人片段；消费→发积分→抽奖／兑换→核销／退款。每条都覆盖失败、重复请求、撤权和旧版本。

原06“故事卡、共创、积分抽奖三路立即并行”的方向可以保留为接口设计并行，但两人只有两条实施流，且共创和抽奖依赖的实名、积分、商品等并未完成。应逐个冻结可交付的契约，不把全部依赖都压到后续联调。正式上线条件与可以先开发的工作分别记录。
