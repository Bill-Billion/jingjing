# 第十阶段：队友怎样接结算页面

本侧提供后端，队友负责App、运营和合作方网页。本次新增23项接口，入口统一是 `/api/v1/finance`；字段以 [OpenAPI](../../contracts/openapi.yaml) 的0.10候选为准。已有商单和项目接口都保留，不要求旧页面改字段。页面尚未开发或联调，未代队友认领。

## 页面上先把三笔钱说清楚

|用户看到什么|表示什么|不能解释成什么|
|---|---|---|
|客户已付款|订单支付渠道已核验的到账，退款另有记录|合作方已收到分成|
|待付给合作方|按这笔交易的约定算出的金额；须审核和各方确认|平台已经转账|
|合作方实际收到|真实外部付款凭据经独立复核后记账|点了申请或点了批准就到账|
|发行收入|渠道账单确认的收入，扣除明确列出的退款、渠道费和税款|银行实际到账|
|渠道尚欠／多收待核对|账单净额减去实际收款；负数是多收待处理|收入凭空增加或已经退回渠道|
|待追回|历史已付超过退款或调整后的权益|程序已经自动扣回|

当前金额都是人民币分，比例用万分数。例子里的15%只是测试示例，不是默认商业规则。不要在页面自行补佣金、税率、日期或未知商品参数。商户自己的收入显示“商户留存”，不再虚构一次给自己转账。

## 从约定到结算，再到实际付款

1. 付款方提交结算约定：`POST /agreements`。选择订单或发行记录，列明每条订单明细分给谁、比例、费用由谁承担、退款时费用保留还是同比减少、何时可结算；附私有合同依据和有效规则版本。首次 `previous_agreement_id=null`。发行只用 `revenue` 这条收入明细，账单已扣渠道费和税，不得在分配规则重复扣。
2. 独立财务人员通过 `POST /records/{id}/reviews` 核查人员、合同、金额、凭据。提交人以及所有参与方的成员不能审核自己这笔业务。通过不等于签了合同或转了钱。
3. 相关方通过 `POST /records/{id}/confirmations` 确认收到的准确 `content_sha256`。客户、商户、供给方及分配对象都须确认。一个人只代表当前有权操作的身份。读取 `/records/{id}/confirmations` 可看还差谁。
4. 付款方用 `POST /agreements/{id}/settlements` 生成核对单，保存当时收退款来源和余额。再次独立审核、各方确认。来源有新收退款或调整后，旧单保留，须生成新单，旧确认不替代新确认。
5. `/agreements/{id}/balances` 返回当前可付金额及不能付款的原因。`POST /agreements/{id}/payouts` 由付款方或指定收款方申请；需私有收款资料。并发申请共同占用可付额度。申请通过审核仍未付款。
6. 财务在线下实际处理后，`POST /payouts/{id}/evidence` 登记付款、失败或退回凭据；再由独立人员复核。只有核实成功付款才记已付；失败释放占用，退回追加一笔返还，不删除原付款。重新付款另建申请。待批准申请可用 `/payouts/{id}/cancellation` 取消；已批准的需真实结果凭据结清。

尚未生效且没有后续业务的约定可以关联旧约定重新提交，旧版显示已替代。已经各方确认生效的规则不覆盖；后续差额通过调整记录处理。拒绝的确认不能偷偷改成同意，重新提版本或结算单后再确认。

## 发行账单和实际到账

`POST /agreements/{id}/statements` 分别填写毛收入、退款、渠道费和税额。审核账单只确认收入；`POST /statements/{id}/receipts` 才登记实际到账，凭据审核后计收款。不能超过对应账单额度，同一银行凭据不能跨记录重复入账。

当前保护方式：约定涉及的已确认渠道收入尚未收齐时，阻止向合作方付款；收齐后仍要最新结算单确认、日期及争议检查。不是程序擅自垫款。渠道冲减用新的 `DEBIT` 账单关联原账单，累计不能超过原额；原账单和实际收款保留。多收渠道款只列待核对，没有自动退款功能。

同一付款方、环境、渠道下的外部账单编号不能重复。一个渠道总账涉及多个作品时，先按渠道提供的明确明细拆开，每条使用可追溯的唯一外部明细编号，不能重复登记同一笔总额。

## 调整、对账和争议

- `/agreements/{id}/adjustments` 提交有依据的各方差额，增减合计必须为零；复核后追加记账，再确认新结算单，不改旧合同、旧分成或付款事实。
- `/agreements/{id}/reconciliations` 核对Apple/支付宝账单，单次最多200条，输出匹配或差异。它只比较本订单已验证事实，不把导入内容变成付款。退款的外部引用使用向渠道提交的退款请求编号；测试和正式环境分开。
- `/records/{id}/disputes` 提出质量、退款、权利、独家性或结算异议；`/disputes/{id}/responses` 保存回复和材料；`/disputes/{id}/decisions` 由独立审核人处理。未决争议暂停新的付款申请与批准，已真实发生的付款仍须记账。每次处理决定追加保存。
- 表示“已采取补救”必须引用已审核调整或真正成功的本订单退款；不能只点按钮就假报退款、撤回版权或消除法律争议。程序不代替版权律师。

## 读取、权限和按钮状态

- `/agreements`、`/agreements/{id}/records?kind=...` 列出获准查看的约定和记录；`/records/{id}` 读详情。`cursor`是翻页位置，不是日期；记录列表按编号翻页，刷新时从首页重读。经过权限过滤的页可能为空，仍须按非空的 `next_cursor` 继续。
- `/agreements/{id}/entries` 提供追加记账；余额接口区分暂计、调整、已付、可付和待追回。合作方只看自己余额；付款方及获准审核人可看全体。
- `/notifications` 只返回当前身份的业务通知，递增编号可用于读取新通知；不是通用聊天系统。末页的 `next_cursor=null` 表示本次翻页结束，可保存最后一项编号再查询新通知。
- `/records/{id}/evidence/{asset_id}` 下载私有材料。材料先按供给模块的私有上传接口入库，下载会检查身份、文件完整性，并在取回后再次检查权限；没有公开链接兜底。付款申请、收款资料和付款凭据不向无关参与方开放。
- `/agreements/{id}/readiness` 明确自动出款尚未实现；页面显示“自动出款未启用”，真实线下凭据流程另外显示。不得设计“模拟转账成功”。

所有写请求带登录令牌和 `Idempotency-Key`；业务方带 `X-Acting-Party`，审核请求以获准审核账号执行。修改已有记录带 `If-Match: "版本号"`。返回412时重新获取记录并让用户确认当前内容，不静默重放旧决定。原样重复操作复用原编号，换内容必须新操作编号。

队友可用本分支直接启动后端对接以上页面，无需引用数据库字段或后端内部函数。真实财务人员、合同依据、银行凭据及供应商权限需业务方提供；本侧只做过合成材料的隔离测试。已实现接口与正式可用不是同一个状态。


### 前端接入时的余额隔离修正（2026-10-03）

SETTLEMENT 的详情、记录列表、本人确认与原编号重放均按当前身份投影余额：合作方仅本方，付款方和有权核验员保留全体。数据库原快照和 `content_sha256` 不改；此指纹绑定原始不可变记录，不是投影后JSON的文件摘要。本人界面只确认本方金额及原约定，不声称看过他人余额；原指纹用于准确版本确认。AGREEMENT原分配规则继续向约定参与方公开，没有改费用或分配规则。
