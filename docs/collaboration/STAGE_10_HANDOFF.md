## 独立验证

在仓库根目录安装既有锁定依赖、配置专用隔离MySQL后执行：

```text
node scripts/backend-check.cjs finance
node scripts/backend-check.cjs all
.local/contract-venv/Scripts/python.exe scripts/validate_contract.py --runtime-fixtures .local/finance-http-fixtures.json
python scripts/collaboration_check.py
```

Linux使用该虚拟环境下的 `bin/python`。测试只连接127.0.0.1的jx_dev控制库并创建、删除本次独立的jx_test库。不能将测试配置指向业务库。单独跑finance包含其真实订单、制作和发行来源准备，不运行无关模块的测试套件；完整回归再覆盖所有模块。HTTP里的付款、存储、外部发行材料均为合成测试，不是真实收付款或上线验收。

验收顺序：明确规则→独立审查→各方确认→按已核实来源生成结算→再确认→申请付款→真实外部结果凭据→独立核验。核对并发超额、重复凭据、拒绝/退款/退回、旧单留存、账单未到账、差额追加、异议冻结、失去身份、私有材料损坏和审计失败回滚。界面需让使用者看懂“已批准但未付款”。

## 已有能力与尚缺条件

本次实现按来源逐笔核算、手工渠道账单、真实线下付款凭据审核、差额和争议流程。自动银行/钱包划款未实现也未启用。程序不预设税率、发票政策、佣金或支付周期；真实规则与合同由业务方给出并逐笔保存。

发行账单的负差额保留待核对，不能冒称已把多收款退回渠道。旧系统“已付”和旧版权人工凭据不自动导入成新订单到账。跨来源经营报表、统一通知、订单/项目评论留给下一阶段；没有把本次结算内通知冒称全站通知已做完。

下一步本侧做业务通知、订单/项目内评论、经营报表与运营审计；队友可同时做当前页面并审阅。之后集中处理脱敏旧库迁移演练、真实供应商验收、前后端联调和发布条件。缺真实服务不以模拟成功补齐，也不影响继续做不依赖真实服务的后端工作。
