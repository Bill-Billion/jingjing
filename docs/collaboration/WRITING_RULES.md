# 项目沟通与文档写法


## 长期要求：先让人看懂，再补技术细节

这是用户在2026-09-21明确提出的长期、严格要求，适用于双方Codex的聊天回复、分工、进度、任务表、交接说明和提交审阅说明。

- 默认用直白中文。先说在做什么、为什么做、谁负责、怎样算做完；不要让用户靠术语翻译表才能理解正文。
- 先写具体事情，再在必要时附技术名称。比如“每次上传代码后自动检查有没有弄坏已有功能”，不要只写“推进CI”；比如“支付服务是否真的能用”，不要只写“Readiness”。
- 面向人的标题和表格以工作名称为主，不能只用任务编号、英文缩写或代码状态。编号、文件名、命令和提交版本放在补充记录中，保持准确以便查找。
- 分工必须说明本侧做什么、队友做什么、各自现在可以开始什么、哪些要等另一方先做完，以及验收办法。负责人尚未接手时直说，不能把建议分工写成已认领。
- 进度必须分清“写完了”“测试过了”“另一方检查过了”“已放进共同版本”“正式能用了”；不要用一个“完成”代替全部状态。测试时的模拟结果不能写成真实业务已经可用。
- 每轮主线结束，更新主线进展、双方相关进度和任务记录，并向用户解释：现在的计划、这次做了什么、还有什么没做、下一步由谁做什么。技术证据另附链接，不能拿日志和编号代替说明。
- 提交前自查：不熟悉项目技术的人能否直接回答“谁、做什么、做到哪、接下来做什么”？若不能，先重写。不要只新增词汇表，也不要把一句行话换成更长的一句行话。
- 原始方案、历史证据和程序使用的字段名保留，不能为了通俗修改业务规则或伪造状态。自动生成的任务表也必须遵守上述表达方式。
