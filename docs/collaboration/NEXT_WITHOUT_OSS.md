# 等待OSS期间，继续做什么

2026-10-04。用户负责催甲方开通OSS；本侧先完成短信阶段集中上传和页面检查。无需暂停全部开发，也不重复开发已有业务模块。

## 建议按这个顺序推进

|顺序与工作|现有基础|现在能做完什么|谁负责／还需什么|
|---|---|---|---|
|1．审阅第7—12阶段已有成果|制作、商单、项目、结算、通知、恢复工具已有代码及页面；本轮核对第16—21份申请均开放、已有自动检查全部通过|逐份核对业务规则、接口和依赖，处理发现的问题，准备维护者按依赖顺序合并|本侧检查后端和证据；队友检查页面及重要共同规则；维护者实际合并。不能用本侧自测代替对方批准|
|2．把整条业务流程在测试环境走一遍|已有各模块测试；后续阶段仍在待审分支|用虚构资料串起选本、报价、订单、合同内容、制作反馈、验收和结算；重点补跨模块权限、撤回、退款与失败恢复检查|本侧做服务端和数据核对，队友配合页面；依赖包含后续阶段的明确测试版本，不一定等OSS|
|3．数字人和模型服务接入准备|制作任务与恢复框架已有；真实数字人供应商尚未绑定|先核对实际产品、官方接口和现有账号材料，再实现能够独立检查的提交、查询、超时结果核对及费用保护|本侧负责；产品/API版本、实际接入点和授权素材不足时单列缺项。文件正式保存和交付仍等OSS，真实收费另行授权|
|4．支付、实名和电子签的接入准备|订单/合同规则已做；部分支付实现已有，部分外部接入仍缺|整理每项现有资料、实现差距和最小验收场景；完善金额/主体/归属、重复通知、拒绝和失败处理|本侧负责后端，队友负责对应页面；真实商户、具体产品、签署模板或测试额度仍需甲方按批补齐|
|5．上线前的本地演练|已有MySQL迁移、备份恢复和上线检查工具|复核剩余缺项，检查日志脱敏、服务未启用提示、进程重启和本地恢复；针对缺口补证据，不重复宣称全产品已验收|本侧负责；真实旧库迁移需脱敏样本，正式环境演练需服务器资料及明确授权|
|6．河南转北京的切换准备|已决定河南先测，北京条件齐备后切换|保留配置分组、历史订单主体与规则，检查更新配置后旧验证不会继续生效|本侧准备；真实切换要等北京主体、账号和资源齐备，不提前改写历史订单|

这是一份后续顺序建议，不表示上述所有任务已经开工或队友已经认领。建议下一阶段以“已有业务集中审阅＋完整测试流程验收”为主，数字人产品资料核对并行准备，避免同时打开多条尚缺产品条件的开发线。

## 哪些事确实要等OSS

真实用户私有材料上传、成品云端保存、受控下载与失效链接的真实验证，以及数字人成果正式归档。等待期间可用隔离测试验证逻辑，但不能展示假上传成功或改成公开链接。

短信、账号权限、订单状态、合同历史、佣金计算、通知评论、报表及MySQL恢复逻辑不以OSS开通为前提。这里的“可推进”指开发和隔离验收，正式支付、签署、数字人等仍有各自外部条件。
