# 数据迁移、备份恢复和故障处理

本说明供本侧后端维护者和队友共同审阅。当前交付的是可重复执行的隔离演练工具，不是正式上线许可。工具只接受本机测试数据库，不能直接拿它操作生产。页面调用格式不变。

## 先分清三个结果

|工作|本次能做到|正式验收还缺什么|
|---|---|---|
|旧库迁移|只读盘点SQLite，完整保存表结构、原值和来源，在MySQL逐条核对；同一材料重复导入不重复保存|实际脱敏旧库、账号归属与授权映射、每笔旧订单/余额的复核材料；本次没有把旧记录转成可执行业务|
|数据库恢复|加密备份，在空白隔离库重建同版结构、恢复所有记录、核对内容和已用编号，恢复库禁止启动业务|生产数据规模、备份频率、异地保管、真实恢复时限及值班人员的验收|
|私有文件恢复|明确数据库里只有文件位置与校验值，不包含文件本体|实际私有存储的对象、版本、权限、删除记录和恢复演练；不能用数据库恢复代替|
|上线条件|核对版本、配置、登记的供应商证据、积压任务和待补材料，输出缺项|真实供应商网络验证、合同/产品条件、页面联调、真机、独立安全复核、双方签字|

## 一次重做本阶段演练

在仓库根目录安装已有锁定依赖，使用原有本机MySQL测试环境，将 `JX_MYSQL_TEST_ENV_FILE` 指向专用测试配置文件，然后运行：

```text
node scripts/backend-check.cjs release
node scripts/backend-check.cjs all
```

测试配置必须是 NODE_ENV=test、DB_CLIENT=mysql、127.0.0.1:33316、jx_local、控制库jx_dev。测试自行建立随机jx_test库，结束后删除这些库；不用手工连接生产。专项结果是 `.local/ci-evidence/release-rehearsal.json`；完整结果是同目录summary.json。合成旧库、加密备份和测试密钥只留在被Git忽略的.local目录，不上传。测试数据不含真实个人材料。

专项覆盖旧材料保留、大整数/原始金额/二进制、重复与并发导入、被改写的材料、错误密钥、加密文件篡改与截断、覆盖保护、外键失败整体回滚、自动计算字段、微秒时间、已用编号、真实入口拒绝启动，以及有限并发HTTP权限检查。本机观测不是生产容量承诺；不以某次毫秒数承诺所有设备和服务器的性能。

## 收到脱敏旧库后怎样处理

1. 数据提供方先关闭写入，制作一致的脱敏副本，说明来源版本和脱敏方式。提供文件路径即可，不把数据库、密码、证件或订单正文提交到Git。
2. 本侧先只读检查。命令从 `晶晶日上工程交接包/01_源码/backend_server` 运行：

```text
node scripts/release-tools.cjs legacy-inspect --file <脱敏副本路径> --source-ref <本次材料编号> --source-kind SANITIZED_COPY
```

3. 文件正在使用、存在未合并WAL、完整性不通过或超过范围时停止，向提供方索要关闭后的合格副本。不得为了通过检查擅自删除WAL。
4. 再用 `legacy-retain` 将材料保存在已建好结构的随机隔离库。需要 `--env-file`、`--database`、`--file`、`--source-ref`、`--source-kind`。工具使用单一事务，保存来源摘要、原表结构、列说明、每条原始数据和校验值；不执行旧库自带SQL。
5. 对账表逐项记录账号、机构、作品、许可、订单、支付和历史承诺如何对应新系统。标记“已付”的旧字段只保留为历史申报；必须另有真实支付核验。没有确定的金额单位或合法身份归属时不得猜测转换。
6. 实际业务映射和切换脚本应在收到样本与映射规则后补齐、测试及审阅。本次归档工具不冒充这一步已完成。旧的db_import_mysql.js现已停用，不能回去执行会关闭外键检查的旧导入流程。

## 备份与恢复的操作边界

维护命令同样从backend_server运行。先用 `key-create --file <新密钥文件>` 创建32字节随机密钥，不打印内容。`backup` 需要 `--env-file`、`--database`、`--source-ref`、`--file`、`--key-file`；输出备份文件摘要和明文内容摘要，不输出业务记录。保留两种摘要和加密文件，密钥另地保管。文件已存在时拒绝覆盖。

`restore` 需要 `--env-file`、`--database`、`--file`、`--key-file`、`--sha256`；最后一项是备份输出的payload_sha256，不是文件摘要。目标必须是操作者事先创建的空白随机测试库，名字符合jx_test_数字_12位十六进制。程序不接受业务库名称、生产地址或任意SQL恢复命令。

恢复只能使用与备份完全一致的迁移文件。先由受信任的仓库迁移建表，再写恢复隔离标记，保留外键检查导入；逐表逐行比较内容，自动生成列由数据库重算，已用过的自增编号不退回。备份提供的SQL从不执行。迁移失败、外键不匹配或任何对账差异都不能报成功；保留失败库隔离状态，另建空库重试，不在半成品上重复灌入。

恢复成功仍会保留 `recovery_status=QUARANTINED`。正式API和后台程序启动都会拒绝使用它；没有“一键解锁”命令。不能为了启动而删除标记，也不能把返回的MATCHED理解为可以恢复收款。原后台任务、旧会话、外部交易编号仍在库中：先核对外部最终结果、重置必要凭据、处理会话和未完成任务，再经独立审阅决定如何放行。

当前是有明确大小上限的应用数据备份：总内容64MiB、单表10万行，只支持本项目同版MySQL/InnoDB结构；不覆盖大规模物理备份、binlog时间点恢复、数据库账号/授权、主机配置、触发器或外部私有文件。正式规模超出时须另做受控备份方案并验收，不能静默截断。文件mode=0600不代表Windows访问控制已经设置，实际保管人须限制Windows目录/文件权限。加密无法弥补同目录同时泄露备份与密钥。

备份使用只读一致性快照，并与仓库迁移共用锁；所有建表改表须走该迁移流程，维护期间禁止管理员绕过锁执行DDL。[MySQL一致性读取说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)说明了快照与DDL的限制。

## 出问题后按什么顺序处理

|情况|本侧先做什么|继续运行前必须确认|
|---|---|---|
|付款、退款或供应商请求超时|保留原请求编号，暂停重复发起，查询供应商实际结果，保留通知与查询证据|未知结果不写成失败后重新扣款；按既有幂等处理核对到账和账本|
|后台任务积压/失效|查任务状态、最近一次执行和占用期限，先排除供应商/权限/配置问题|旧执行者不能再写结果；不手工改成成功；重试仍使用同一业务依据|
|升级或迁移失败|停止新写入和后台处理，记录版本/迁移状态，保存现场|不要直接删新表或篡改已执行迁移；先在新的隔离库复现恢复与对账|
|需要恢复数据库|确认备份时间、版本、摘要及密钥，新库恢复，保持隔离|核对备份后的外部付款、退款、发行、制作结果和权限撤销，避免回退数据复活旧权限或重复动作|
|私有对象丢失|停止相关下载和交付，核对对象版本与校验值，联系实际存储负责人|私有权限和文件本体均恢复并检查；不能改成公开链接兜底|
|发现错误上线材料|撤销该版本的验收结论，记录修复及新证据|新提交需重新匹配证据；不能沿用其他版本或过期记录|

实际故障负责人、联系方式、可接受的数据损失和恢复时限尚未确定，由项目方确认后填写。本说明不擅自承诺时限或自动执行部署/回滚。

## 上线检查怎么填

示例是同目录 `release-review.example.json`，所有检查默认MISSING。复制到受控本地目录，填准确的40位Git提交、检查人、证据编号、检查时间、有效期和PRODUCTION_CANDIDATE环境；不要把路径指向含密钥的材料。供应商清单按实际选择填写，不将示例服务名称当已开通。

`release-check --env-file <测试配置> --database <隔离库> --manifest <材料清单>` 只读生成报告。配置检查只是声明检查，不验证证书文件或真实网络。已登记正式验证也只显示“需要再次核验”；供应商清单为空须补齐实际启用范围。结果永远不自动批准上线。正式供应商、页面、隐私/合同和上线决定需要实际负责人分别验收。
