# 上传代码后怎样查看自动检查

这套检查会自动验证数据库更新、耗时任务恢复和服务器已有功能，帮助双方发现改代码时带入的问题。已经在GitHub的干净Linux环境实际跑通，不只是写了一份配置。

## 现在能用到哪里

目前自动检查跟随本次开发分支，尚未加入双方共同开发版本。它需要前面已写好的数据库和后台任务代码；这两项还在等另一方检查。先让它们进入共同版本，再合入自动检查，不绕过原来的检查要求。

文件合入后，本侧和队友按约定使用的开发分支、共同版本和主版本，每次上传新代码都会触发；提出代码合并申请时也会检查。不需要每人手工搭同一套环境，不使用正式数据库或外部服务账号。

## 双方怎么用

1. 上传自己的代码后，在GitHub仓库点 **Actions**，找到“服务器自动检查”；代码合并申请页面也能看到检查状态。
2. 绿色通过表示本次所列测试通过。红色失败时，点开“数据库、后台任务和服务器功能”，查看失败的具体步骤和日志，再修复并重新上传。
3. 运行页面底部可下载测试记录，保存14天。失败时也尽量保存已产生的日志；配置或安装阶段就失败时，原因在步骤日志中，可能尚无测试文件。

当前共五组：数据库基础、后台任务、外部服务基础、旧付款/实名/权限问题专项、服务器已有测试。最后一组包含前几组的内容，不把数量相加成已完成业务数。

**唯一允许跳过的是缺少脱敏旧库的比较测试。** 数据库没连接、测试没运行、意外跳过、测试失败或执行超时，都不能当通过。正式付款、实名、影片制作、旧数据搬迁和手机页面是否能用，还需要各自的实际验收；这些不由本次绿色结果代替。

没有改GitHub的分支保护设置，因此当前是“自动报告检查结果”，不声称GitHub已经强制禁止合入失败代码。没有自动部署动作。

## 给负责复验的开发者

自动运行配置在 `.github/workflows/backend-checks.yml`。它使用Ubuntu24.04、Node22.19.0、MySQL8.4.11及锁定的npm依赖；只授予读取仓库的权限，最长运行15分钟，同一分支的新运行会取消过期运行。工作流只调用固定版本的官方GitHub操作。

一次性数据库由 `scripts/ci-mysql.cjs` 管理：只允许在GitHub Linux运行环境启动，随机生成仅供本次使用的口令，只开放本机33316端口。测试账号只有测试数据库权限；每个真实数据库测试创建自己的 `jx_test_*` 数据库。结束时核对容器归属后删除，测试账号配置不会放进下载记录。

已有本地MySQL环境可按 [数据库运行说明](../../晶晶日上工程交接包/01_源码/backend_server/docs/MYSQL_FOUNDATION.md) 启动，再在服务器代码目录执行：

```powershell
$env:JX_MYSQL_TEST_ENV_FILE=(Resolve-Path ../../../.local/mysql/runtime/test-env.json).Path
npm run test:ci
```

本地和GitHub用同一个检查入口，结果保存在仓库 `.local/ci-evidence`。测试进程沿用外部网络拦截，只允许本机连接，避免误调用收费服务。安装依赖和下载测试数据库发生在测试前，需要网络；不能把“测试禁止外部请求”理解为整个安装过程断网。

缺少配置时命令非零退出；结果判定也会拒绝空输出、失败、意外跳过和不完整的测试汇总。本次实际记录见 [自动检查任务记录](../tasks/records/CORE-S0-006.md)。

实现参考：[GitHub的Node测试说明](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)、[工作流配置说明](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)。这些说明只用于实现依据，验收以本仓库实际运行结果为准。

账号/机构专项已加入同一个自动检查入口，使用真实MySQL检验本人接受邀请、越权、重复请求、并发和事务回滚；内部流程通过不代表短信、公开HTTP或App联调已经完成。单独运行用npm run test:party，仍必须提供隔离配置。
