## 怎么协作，避免重复改两遍

1. 前端先确定页面结构和视觉，接口数据与业务操作尽量放在现有独立服务/状态层；后端不要求照某个临时布局制作。
2. 前批新增两个只读接口和实名副本；本批在原account-data增加八个分类，已有路径及旧分类兼容保留。页面以contracts/openapi.yaml和实际示例为准，不读取数据库或服务器内部函数。
3. 继续沿原三个功能包交付：本人资料、机构批量、推荐与榜单。可在同一轮UI工作里完成，但逐包标明接了哪些、验证到哪里；不要等全部UI改完才报告接口不合适。
4. 后端负责明确规则、接口、合成资料和组合验证；前端负责App、本人网页、运营网页与下面所列交互，允许修其负责路线的必要接口问题。共享规则变更先写清影响，避免两边同时改同一文件。
5. 独立分支开发，阶段集中交付到原PR39协作，不覆盖对方提交；交付要给提交号、接口版本、页面入口、同一组记录编号、正常/失败结果和未覆盖项。前后端不能各用不同版本测试后宣称整链通过。

本轮实名分类：`GET /api/v1/privacy/requests/{request_id}/account-data?section=IDENTITY_CHECKS`。每项有id/person_id/current_status/object_version/age_band/valid_until/result_recorded；末尾两项original_documents_included、provider_evidence_included固定false。不要把PENDING/UNKNOWN写成已通过；历史核验结果不是当前实时资格，实际办理仍核有效期。已有会话/换号接法见[前批交接](PRELAUNCH_SECURITY_RANKING_HANDOFF_20261106.md)。

完成标准：同一申请从提交到分类查看、分页、保存、返回重开；换账号/机构越权拒绝；历史记录和未知时间解释准确；文件内容与原件一致；范围不足继续办理，不自动结案。后端仍在[资料覆盖清单](PERSONAL_DATA_COVERAGE_20261109.md)补其余范围，页面如实显示未提供项。

### 本批八个分类：页面可直接接，不新增第四工作包

统一入口仍是account-data；无X-Acting-Party，沿原申请编号分页。范围不足409；不登录401；他人申请404；不合法或已清理的游标400；存储摘要异常503不能当空清单。全部request_completion=NOT_CONFIRMED，用户导出并不自动办结申请。

|section|所需申请范围|展示和恢复要求|
|---|---|---|
|SUPPORT_TICKETS|PROFILE或ALL|本人反馈/投诉摘要与状态；不包含机构经办记录，也不包含其他纠纷模块的全部材料|
|SUPPORT_MESSAGES|PROFILE或ALL|按ticket_id归并本人提交及面向本人的回复；id/游标为UUID.版本号，作为字符串原样传；asset_ids只是历史引用，下载可能已不可用|
|INVOICE_REQUESTS|TRANSACTIONS或ALL|本人个人订单开票请求、抬头、申请/占用金额与状态；不能把占用金额当新增扣款；机构发票仍从机构业务入口查看|
|INVOICE_HISTORY|TRANSACTIONS或ALL|按invoice_id归并处理历史与更正；游标UUID.版本号；内部待审文档编号不返回|
|INVOICE_DOCUMENTS|TRANSACTIONS或ALL|只含ISSUED/SUPERSEDED，展示历史替换关系、模拟标识；copy_sha256是脱敏内容摘要，attachment_recorded只说明曾登记附件，不承诺当前可下载|
|FAVORITES|PROFILE或ALL|本人收藏引用及当前公开标题；UNAVAILABLE显示内容已不可访问，不缓存旧标题照片|
|BROWSING_HISTORY|PROFILE或ALL|仅仍保留记录，空列表不能说明从未浏览；删除/关闭不恢复，history_complete=false|
|COLLECTION_SETTINGS|PROFILE或ALL|当前历史记录开关、保留天数与条数上限；由服务器配置返回，不硬编码|

收藏/浏览游标是十进制字符串，不转JavaScript数字；设置无分页。每页最多100项，400游标失效重新第一页。副本文件保存按现有客户端安全流程，不把完整资料放公共链接或错误日志。

原附件下载继续用 `/api/v1/support/tickets/{ticket_id}/assets/{asset_id}/content` 或 `/api/v1/invoices/requests/{invoice_id}/documents/{document_id}/content`，这些原业务接口需要原个人身份头，不能带机构身份冒领。先核对个人身份；401/403/404明确提示，不更换接口绕过。服务端会重新核权，original_documents_included=false不能显示“原件已导出”。

新增验收：同一反馈及票据在原业务页和副本页对应；个人/机构切换不串资料；已替换票据仍可查、待审不可查；浏览关闭/过期/删除后不复活；失权内容清空原缓存；导出/下载内容与同版记录一致。后端180项受影响回归已通过，前端这批页面认领和验收尚未确认。[证据](../../reviews/privacy-activity-copy-20261109/REPORT.md)

### 续批：本人处理、通知与活动记录（0.31.44）

仍属第一包，不要求另建页面框架。原account-data入口增加下表八分类，均需本人QUERY/COPY申请、PROFILE或ALL范围，不带机构身份头；游标为UUID字符串，每页最多100条。维持request_completion=NOT_CONFIRMED和original_documents_included=false。原路径、旧分类及数据库迁移0211不变。

|分类|页面展示与边界|
|---|---|
|PRIVACY_REQUESTS|本人申请文字、范围、时限、当前已审核答复；待审方案不显示；calendar_version为空时不能称已按正式工作日历计算|
|PRIVACY_RESPONSES|按request_id和object_version展示历次已审核答复、留存说明和剩余事项；不要将旧答复覆盖成最新约定|
|PRIVACY_EVENTS|本人可见的办理消息与版本，不含工作人员账号|
|PRIVACY_ACTIONS|撤回授权/模型删除操作及关联结果编号；不能仅凭有一条操作记录就说供应商已删除|
|PRIVACY_EXECUTIONS|执行状态、目标、规则编号及拟更正的姓名；QUEUED是排队，EXECUTED还需按原办理页核实际结果及剩余事项；内部任务和存储路径不提供|
|NOTIFICATION_DELIVERIES|个人通知发送状态和模拟标识；PENDING/UNKNOWN/SUPPRESSED不能展示为已收到；不代表站内阅读记录或真实设备推送已开通|
|GUARDIAN_LINKS|本人参与的监护关系摘要；own_role区分监护人/儿童。儿童侧relationship为null，双方都无对方账号/证明。撤销/过期按原状态显示，不能凭摘要进入儿童档案|
|ENGAGEMENT_RECORDS|按kind展示十类本人活动记录；数据白名单见接口。机构经办、全局评审、设备标识均排除，不把此列表说成所有活动记录|

已审核历史答复附件现在可沿原 `/api/v1/privacy/requests/{request_id}/evidence/{asset_id}/content` 下载。使用该历史答复所属申请编号，不换成当前导出申请编号；重新登录校验本人，无机构身份头。文件已删除、变更或无权限时明确提示，历史附件存在引用不保证仍可下载。下载字节与原件一致、no-store；不允许公开缓存。

新增验收：先拟答复但未复核时看不到草稿；两次审核答复均保留，两个版本的附件均按原申请下载；切账号/换申请拒绝，删除后拒绝；机构活动不进个人清单；撤销监护仍只能看关系摘要。193项后端回归通过，App/网页和完整监护/活动链尚未验收。[本批证据](../../reviews/privacy-participation-copy-20261109/REPORT.md)

## 两端统一的交互要求与完整测试

这些是原有功能的验收要求，不是要求全部从头开发：

- 登录后回原业务位置；身份清楚，机构操作要明确旗下真人/形象。切换后清旧权限缓存，慢请求不能回写旧身份页面。
