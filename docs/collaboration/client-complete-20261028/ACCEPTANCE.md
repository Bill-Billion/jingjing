# 如何记录测试并交付这一版

本规则补充18组施工任务，不表示这些功能已经完成。验收真相保留在 [验收登记](../../testing/FULL_BUSINESS_ACCEPTANCE_20261028.json)，负责人和开发状态仍在 [任务表](../../tasks/board.json)。133条是原始来源，另有18组任务专项；不得把两者相加当成新增需求数或已通过数量。

## 先把一条业务从头走通

每组交接同时给出：对应任务和验收编号、当前可调用接口/仅示例/未实现接口、正常及错误返回、前后端配套版本、运行命令和已知阻断。前端可先用明确标注的示例开发；正式联调必须用这一版的隔离后端。同事没有实际认领或审阅时保持原状态。

第17组可以提前写用例和逐链执行，最终完成须等前16组双端成果齐备。按首次供给、成交履约、经营体验逐批交付；不要等全部页面写完才第一次联调。一个小任务通过只更新它对应的证据，不自动完成整条业务。

账号、基础授权和已审核测试规则可预置，但正在验收的业务必须从用户能操作的起点开始：首次上架没有旧商品，首次试镜没有旧方案，共创从本人新建房间开始。共创先建房再形成本次正式报价，不能借用旧报价关联的房间。操作产生的同一业务记录跨App、机构网页和运营网页继续，不能拿不同预置订单的成功截图拼成一条链。

12条整链各验正常、关键逆向、越权、重复提交、状态已变化和失败恢复。相关等待/回执由隔离模拟器驱动，业务仍经真实接口、事务和后台任务；模拟不代替权限检查。接口测试不能代替端侧操作，浏览器页面打开也不能代替成交、交付或退款。

18组专项补足原始标准未写全的开票、换号、收藏足迹等细节。第17组还须验证登录深链回跳、未提交输入保护、字段错误定位、分页返回及待核对操作恢复。弱网、窄屏、系统大字和真实设备保留具体检查结果；没有跑过不能以桌面截图覆盖。

## 登记与证据格式

每项只有一个 `status`：`NOT_RUN`、`BLOCKED`、`PASS`、`NOT_APPLICABLE`。`source_expected` 保留原文；当前决定替代旧预期时写 `effective_expected` 和 `decision_refs`。例如20人权益按已确认的一份服务额度，定制按先确认预览再补60%；不因旧标准文字把实现改回去。

缺代码、缺前端、缺模拟能力、缺外部服务都不是“不适用”。仅已被当前范围决定替代的来源条目可登记 `NOT_APPLICABLE`，须附 `boundary`：`kind: SUPERSEDED`、原因、决定文件、作者和另一位实际审阅人。完整E2E链不能整条豁免。真实资金、实名、长期模型、法定依据等继续列正式启用边界；隔离行为能测的仍需测。

`PASS` 的 `evidence` 是报告引用数组，每项含仓库相对 `path` 和文件实际字节的 `sha256`。报告格式如下，示例中的占位值必须换成实际结果，不能提交为验收证据：

```json
{
  "result": "PASS",
  "code_sha": "受测源代码的完整40位提交号",
  "environment": "isolated",
  "dataset_id": "本次独立资料批次，不含账号凭据",
  "contract_version": "0.30.2-rc.1",
  "rules_version": "TEST-20261028-2",
  "build_hashes": {"app": "实际交付App包SHA256", "web": "实际交付网页包SHA256"},
  "summary": {"passed": 1, "failed": 0, "skipped": 0},
  "checks": [{
    "acceptance_id": "E2E-01",
    "case": "normal",
    "surface": "app",
    "result": "PASS",
    "record_id": "本次合成业务记录号",
    "actor": "buyer"
  }],
  "artifacts": [{"path": "脱敏原始操作记录或测试输出路径", "sha256": "原始文件SHA256"}]
}
```

报告可覆盖多条标准，但每个 `checks` 项须来自实际断言/操作，不能只复制需求编号。`summary` 必须含全部失败与跳过；`SKIP`、空检查或任一失败都不能写成PASS。混合结果先保留原始报告，再修复或拆出范围清楚的已执行检查；不得删除失败行凑通过。每条E2E的正常路径须有同一记录、至少两个岗位、三个端的证据，且代码与资料批次一致。截图、日志等原件和摘要一起交付，不只提供本机已不存在的截图路径。

旧5项修复的模块/页面片段证据保留在 [原证据说明](../../testing/evidence/full-business-20261028/README.md)。其中未知提交、旧截图、Windows换行产生的原摘要保持原样，不补造来源；重测后另存新报告。旧模块数量不能自动写进151项当前状态。检查器只核对声明、文件和对应关系，真实断言质量及另一方审阅仍由人负责。

## 日常检查和定版检查分开

每次提交运行：

```sh
python3 scripts/collaboration_check.py
python3 scripts/full_business_check.py
python3 scripts/full_business_check_test.py
node --test scripts/v5-r05-r12-app-actions-result.test.mjs
```

前两项检查任务/登记结构，允许真实的NOT_RUN；不声称完整业务通过。CI会运行登记检查和反例测试。App操作脚本同时以退出码表达失败，未知动作或零项执行直接拒绝，不能只看shell命令“运行结束”。测试站工具另运行 `.github/workflows/client-testing-checks.yml` 中的Node测试。

准备完整测试版时，先保存受测源代码提交、构建App和网页包，填写 `release` 的代码提交、接口/规则版本、资料批次、两端产物路径及SHA256、实际独立审阅记录；在此候选版本上执行：

```sh
python3 scripts/full_business_check.py --require-ready --candidate <受测源代码完整提交号>
```

此命令要求133条来源和18组专项逐项有结果、前后端36项已实现并测过、共享边界实际审阅、报告及两端产物对应同一候选。受测提交之后可追加证据/说明文档，可执行文件不能变化；有代码修复就换候选并重测受影响场景。变更影响复核须覆盖相关权限、钱账和跨端链，不用“只是小改”自动复用整链结果。命令失败就保持 `client_test_version_ready: false`，不能手改标志绕过。

第18组报告还必须分别覆盖候选CI、构建冻结、备份恢复、保留已有订单/反馈的回退、访问到期关闭，以及从真实交付产物完成的冒烟。数据库启动成功不算恢复演练；只有反馈JSON恢复也不算业务库恢复。旧库迁移样本缺失继续写未验，不能拿924通过掩盖那1项跳过。

测试站准备时固定两端文件清单，启动和响应时核验；同一会话不能重建目录后静默换版本。替换候选须重新准备会话，沿用反馈批次及原到期上限。旧配置缺少冻结清单时明确拒绝，不自动补造摘要或延长时间。普通产品构建、测试专用入口和注入脚本分别留证，测试入口不能进入正式环境。

通过定版检查只证明所列测试条件，仍不授予合并、部署、开放公网或真实服务的权限。当前PR39维持草稿，完整测试版尚未定版；用户后续授权实际交付时，再核对目标环境、实际运行版本、反馈保留和到期时间。
