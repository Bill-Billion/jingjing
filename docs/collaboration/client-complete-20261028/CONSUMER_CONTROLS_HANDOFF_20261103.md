# 用户自己限制充值和消费：前端接入说明

后端负责人 **chengcongcong222**；前端负责人 **Bill-Billion**。这是原18组中第11、14、16、17组的跨业务补全，对应余额/会员及付款路线，不另起产品阶段。接口 **0.31.24-rc.1**，数据库 **0206**，从原PR39取得同版代码。页面尚未认领；发布到仓库不等于对方已经看过。

## 用户最终能办什么

在“我的”中设置自己的月度充值上限和现金消费上限，两者分开。降低立即生效；提高或者取消上限，先等待冷静期，再由本人确认。可以取消尚未生效的提额申请，并查看变更记录。0表示停止新的相应付费，空值表示本人未设置额外上限，**不表示平台上限、实名或服务开通条件已被取消**。

新付款及向支付机构发送尚未发出的付款请求时，服务器都会检查，不依赖页面拦截。真实充值仍关闭；已有模拟支付继续隔离使用。设置额度不需要先开钱包，也不会创建余额或会员资格。

## 原文与本轮暂定口径

[37号文“自助限额”](../../sources/contracts-20261029/extracted/37.md)原文：“用户可自助设置月度充值/消费上限，调低即时生效、调高需冷静期”。同文“单笔/单日限额”原文：“对单笔、单日充值设上限（具体阈值上线前定，建议参照常见平台分级），超限需二次确认或次日再试”。平台原有单笔、日、月充值规则继续执行，用户额度只能加一道限制。

以下为落实流程的**暂定实施方案，不是甲方原文**：

- 冷静期暂按24小时；到期不自动提高，需要本人再次确认。政策版本和申请时间留在每次记录中。后续调整规则不能倒改已受理的等待时间。
- 以北京时间自然月计额度，单位为人民币分。计入本月发起或本月确认到账的付款/充值，以及仍未确认结果的跨月请求；同一请求在同月只算一次。跨月请求可能在两个自然月都占用额度，这是防止月底预留后绕过新月限制的保护口径，**不是重复扣钱**。
- “已占用额度”包含尚未确认的请求，不叫现金已消费。`pending_minor`单列其中待确认部分。退款照常退钱，但本月额度不因退款恢复，避免循环付款/退款绕过保护；未发送且取消、或供应商明确关闭的未付款请求释放额度。
- 降低到已占用额以下允许保存，剩余额度显示0；已经发给支付机构的请求不能承诺撤销。后续真实回执照常记账，不伪造失败或阻止退款。
- 仅控制本人现金充值/付款；机构经授权的采购、免费权益和晶钻消耗不是该现金额度。未成年收费仍按原规则禁止，不能用设置额度解除。
- 同月相关记录超过单类10000条时明确需要核对，不能截掉记录后显示错误额度。

## 页面怎么接

|用户操作|接口|前端处理|
|---|---|---|
|打开设置、刷新状态|GET `/api/v1/wallet/consumer-controls`|显示两种当前上限、本月占用/其中待确认/剩余、待生效申请和确认时间|
|修改一种上限|POST 同路径，`{kind: "PAYMENT" 或 "RECHARGE", monthly_limit_minor: 整数或null}`|显示本次是立即降低还是申请提高；携带当前`If-Match`和固定`Idempotency-Key`|
|冷静期后确认提高|POST `.../confirm`，`{kind}`|需用户主动点击；不能在页面加载、倒计时结束或重新登录后自动确认|
|取消待生效申请|POST `.../cancel`，`{kind}`|只取消提额申请，不清空现有额度|
|查看历史|GET `.../history?limit=20&cursor=...`|只显示本人每次操作、前后额度及时间，支持分页|

所有接口都需要登录及本人`X-Acting-Party`。三个POST需要`If-Match: "版本号"`，响应设置带`ETag`。网页与App复用同一接口，不读取数据库。

结果未知时保留原请求键、原请求体和原版本，沿原请求恢复，再GET最新状态；历史重放返回原操作结果，不能把其中旧版本误当最新。切身份、退出、权限失效时清理页面和待确认缓存，不跨账号恢复。

|错误|面向用户的处理|
|---|---|
|`CONSUMER_MONTHLY_LIMIT_EXCEEDED`|“本次操作超过你设置的月度额度”；显示当前额度、占用和待确认，提供返回设置，禁止自动换请求键重付|
|`CONSUMER_LIMIT_COOLING_PERIOD`|“提高额度还需要等待”，刷新并显示服务器返回的可确认时间|
|`CONSUMER_LIMIT_CHANGE_NOT_PENDING` / `CONSUMER_LIMIT_UNCHANGED`|刷新后说明申请已处理或当前额度相同|
|`VERSION_CONFLICT`|设置已在其他页面修改，重新读取后由用户确认，不自动覆盖|
|`CONSUMER_USAGE_REVIEW_REQUIRED`|记录需要核对，保留当前设置，不展示虚假可用额度|
|普通401/403|按现有登录返回和身份失效规则处理，不自动重放付款或提额|

**新增前端范围只有一组个人额度设置与付款提示**，建议6–12人时接入后再按实际跨端工作重估；不是六项合同页面或财务运营台的替代，也不把它当全部剩余前端工作。用户已要求后续信息直接入仓库，本批未宣称Bill-Billion已认领。

## 同版验收

先用合成订单和模拟支付：设置消费上限150分→同时发起两笔100分付款→只能一笔占用；降低至0→尚未发出的付款不能发送；申请提高→等待期内拒绝→到期后本人确认→付款继续。断网未知结果继续占用，同一请求重试不多算；取消未发出订单释放占用，余额支付同时释放预留余额；已成功付款退款后钱退回但额度不恢复。

分别检查：充值额度不影响消费额度、平台限制不能被提高个人额度绕过、跨月未知请求与迟到账、首次设置已有历史金额、切身份、身份停用、过期版本、历史分页。后端自动检查已覆盖所列数据库流程；**App/网页接入和人工体验仍待验**。不能把这些新标准偷偷记为原151条全部通过。

## 同批补齐：奖池公示7天后才可抽奖

[22号文第三章](../../sources/contracts-20261029/extracted/22.md)要求：“调整奖池或概率的，提前 7 日在站内显著位置公示。”。新完成双人审核的奖池返回`publication_notice`：`published_at`为真正完成审核并公开的时间，`opens_at`为七天后的时间，`days=7`。此期间用户可查看奖品、概率和约定，但不能发起扣晶钻抽奖；还须同时满足原`starts_at`、`ends_at`和资格/库存条件。

原文说调整时提前公示；为防止通过另建奖池规避，本批暂定**所有新发布奖池（含首发）都等7天**。历史已发布奖池没有此字段时按原快照继续；不倒改历史中奖、库存和扣分。窗口不足7天的新池拒绝完成发布，需重新安排时间，不能公示期未满就自动放行。
