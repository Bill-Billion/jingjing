## 先说明需求来源

不是额外引入的新法律要求，依据是甲方20261029合同包中的[37号《用户理性使用与防沉迷干预制度》](../../sources/contracts-20261029/extracted/37.md)：

> 连续充值或短时多笔消费时弹窗提示、强制阅读确认

> 夜间（如 22:00–次日 8:00）大额消费加强提示

> 提供使用时长统计、休息提醒、夜间提醒；用户可开启"定时休息""夜间免打扰"。

> 推送可自助关闭或设置免打扰时段；营销推送不得高频骚扰，提供一键退订。

> 抽奖前提示理性参与；对高频抽奖、累计消费较高的用户进行频次提醒与消费限制；未成年人不得参与付费抽奖。

**以下是流程补全，不能当成甲方原话**：本人开启后才统计；30秒前台报告、超过90秒空档不计入；提醒确认后重计间隔；跨午夜重置当日累计、多设备不重复；确认绑定具体消费请求；已排队通知发送前再读最新偏好。它们分别解决默认跟踪、重复计时、失效提示被复用和退订后仍发送的问题。使用时长是估计，短暂后台时间可能有误差；用户确认提醒不等于已实际休息。

## 消费提示：调用次序与恢复

路径前缀`/api/v1/wallet/consumer-risk`，全部登录后调用；本人操作带当前本人`X-Acting-Party`，机构不代本人确认。

|接口|用途|
|---|---|
|GET `/status`|查看是否已有审核生效的规则；不带身份头|
|GET `/rules`|有`WALLET_RULE_REVIEW`权限的运营查规则；不带身份头|
|POST `/rules`|运营提交`{rule}`，带请求键；不带身份头|
|POST `/rules/{record_id}/review`|另一人用当前版本审核`{decision:APPROVE或REJECT,reason}`；带请求键及`If-Match`，录入者不能自审|
|GET `/preview`|用下表查询参数，获得提示、当前规则和`preview_sha256`|
|POST `/confirm`|提交`{target,preview_sha256,read_confirmed:true}`及独立确认请求键；返回确认记录|

消费目标有四类，**传原始目标，不要把预览返回的计算字段重新拼进请求**：

|目标|参数|接下来调用|
|---|---|---|
|付款|`kind=PAYMENT,order_id,installment_key,request_key`|用同一个`request_key`调用原付款接口，金额由订单计算|
|恢复尚未发送的付款|`kind=PAYMENT_RECORD,payment_id`|确认后继续查/恢复原付款，不创建第二笔|
|充值|`kind=RECHARGE,amount_minor,request_key`|金额单位分，原充值请求键不变；真实托管仍未连接|
|抽奖|`kind=LOTTERY,pool_id,count=1或10,request_key`|确认后用原键调用抽奖；此时返回目标的`amount_minor`是300/2700**晶钻数**，不是现金，界面必须按kind显示单位|

预览`configured=false`表示没有审核规则；不能显示“已经通过正式消费风控”。`required=false`时无需确认；`required=true`时显示服务端message和reasons，由本人明确点击继续。确认返回成功后才继续原操作，不代表钱已付、抽奖已完成。操作最终结果仍读原业务接口。

新合同奖池（source_profile=CONTRACT_20261029）须先有独立审核生效的消费保护规则；缺少时抽奖返回CONSUMER_POLICY_NOT_CONFIGURED，不扣钻、不创建抽奖记录。页面提示“活动保护规则待审核，暂不可参与”，不能在configured=false时直接继续这类抽奖。历史奖池不套用新启用条件。

`CONSUMER_RISK_CONFIRMATION_REQUIRED / EXPIRED / PREVIEW_CHANGED`：重新查当前预览、显示提示，等本人确认。`LOTTERY_PARTICIPATION_LIMIT`：解释当前参与受限，不能循环换键重试。原确认请求断网先沿原确认键恢复；已过期需新的**确认键**，原付款/抽奖键不换。登录失效或切身份后不自动重放消费。

运营规则严格字段见OpenAPI `ConsumerRiskRule`。包含观察秒数、触发次数、大额充值分值、夜间区间及金额、确认有效秒数、抽奖窗口次数和当天晶钻上限。**均须真实运营审核，不内置正式金额/次数**；本机测试数值只为构造边界，不是甲方经营规则。新规则生效不改旧订单价款或退款约定，只约束尚未向供应商发出的新消费。已发出/结果未知的付款、回执和退款继续原核对流程。

## 夜间与推送：字段和边界

`GET/PATCH /api/v1/privacy/preferences`仍只操作登录本人，不使用身份头。原三个字段保留，新增可选字段：

```json
{
  "personalization": false,
  "marketing": false,
  "rest_reminder_minutes": 0,
  "push_enabled": false,
  "night_reminder_enabled": false,
  "quiet_hours": {"enabled": false, "start_minute": 1320, "end_minute": 480}
}
```

分钟为北京时间当天0—1439；起止不得相同。初始22:00—08:00只是关闭状态下的设置示例，用户可以修改，不是已强制生效的甲方时段。夜间提醒使用同一时段，但开关独立：开夜间提醒不等于关闭推送。旧客户端只保存原三项时，新项保持原值；仍需按当前版本和原请求键保存，防覆盖。

`GET /privacy/usage`和`POST /privacy/usage/pulse`增加`night_reminder`：`enabled,due,timezone,start_minute,end_minute`。即使没开定时休息，也能返回夜间提醒。不保存夜间精确浏览轨迹；前端按账号及本地日期只温和提示一次，是本批实施建议，避免每次轮询弹窗。

外部推送当前**未连接**，不能显示“已送达手机”。业务消息一直进入站内通知；新增内部队列只对已开启推送的用户建立业务推送记录。实际发送前重新查账号/身份及业务权限。关闭推送/营销会抑制尚未发出的记录，免打扰将其延后。已交给供应商的请求无法撤回，结果未知只查同一请求，不自动重发。

内部模拟发送器仅接受`test + SANDBOX`，无公开发送接口，不放真实密钥。营销暂按每账号每天最多一次发送尝试，这是保守实施方案，未冒称甲方指定；失败/未知也占次数。站内业务不受该营销次数限制。发送内容仅“你有一条新消息，请登录查看”，不带故事、合同、金额等私密内容。后续真实适配器接入必须复用队列检查，再独立验证送达和退订。

## 奖池核对结果

[22号抽奖规则](../../sources/contracts-20261029/extracted/22.md)给出300/2700消耗、十连保障、11项概率、制作金门槛和期限；代码已有兑换、本人绑定、核销、补救及已用券退款不返还，本轮补新材料候选配置校验。

运营提交奖池时`config.source_profile=CONTRACT_20261029`启用新材料校验，`cost_basis`填审核依据及单抽/十连对应消费基数（分）。候选生成函数`redemption/contract-pool.candidate`要求逐项提供成本，缺项拒绝，不凭“约1800元”补价格。所报期望成本必须不超过所报消费基数的1%；计算不能证明成本资料真实，仍由独立法务、财务审核凭据。旧无profile奖池作为历史/合成兼容，不得据其称已符合新合同；正式采用新材料必须选择该profile并完成审核。

仍需甲方签认两点：①新材料同时写“独立随机概率”和“十连必保底”。暂沿现有前九次独立、第十次在此前未中奖时按保障奖品权重抽取，页面公开单抽和十连条件概率；②“净回馈率”的成本和消费基数怎样算，必须有真实财务依据。缺这些不阻塞合成测试，但不声称正式奖池已批准。
