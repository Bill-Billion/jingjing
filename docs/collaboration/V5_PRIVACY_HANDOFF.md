# 个人信息申请：页面怎么接、用户会看到什么

本批在worktrees/privacy、core/v5-privacy-protection。起点65f8938，沿用0147—0150数据库迁移顺序；这属于未合入的必要依赖，完整分支包含它们。上一批样片与合同功能在PR25单独审阅，不需等待本批页面。

本侧负责请求、权限、处理记录和接口；队友负责App/网页入口和实际操作验收。队友尚未确认接手。当前上传、测试和剩余工作以CORE_CURRENT为准。

## 用户怎样操作

1. 在“我的—隐私与个人信息”选择查询、复制、更正、删除、注销或投诉，说明具体资料范围。此入口按登录账号访问，不随机构身份切换，不传X-Acting-Party。
2. 提交后显示“已收到，正在等待处理”，展示目标答复日期。未配置审核后的节假日日历时，明确标“按普通工作日估算，需人工核对”，不能显示成已承诺的法定截止日。
3. 工作人员处理并拟好答复，另一位有权限的人员检查材料、第三方信息是否已脱敏及剩余事项。未经复核的草稿不向申请人开放。
4. 用户查看审核后答复，下载属于这份申请的私有材料，查看暂时保留的具体资料、依据与复查日期。不能用“有订单”一概保留所有资料。
5. 用户可提出异议；旧答复与记录保留，不被新回复覆盖。

## 本批已经提供的接口

统一前缀 `/api/v1/privacy`，契约候选0.27.0-rc.1。以下是可调用的已实现请求流程，不代表实际删除、注销已完成。

|页面动作|接口|注意事项|
|---|---|---|
|查看/保存偏好|GET、PATCH /preferences|初始版本为0；保存带If-Match与Idempotency-Key；冲突重新读取，不覆盖另一页面的修改|
|提交申请|POST /requests|type、scopes、details；同一提交重试沿用同一请求键|
|查看我的列表与详情|GET /requests、/requests/{request_id}|仅本人可读；不把机构成员当成可代办个人隐私申请的人|
|查看旧答复/提出异议|GET /requests/{request_id}/history；POST .../reopen|异议须带当前版本和原因，旧答复保留|
|领取答复附件|GET /requests/{request_id}/evidence/{asset_id}/content|服务端校验归属和文件摘要，返回私有文件，不公开跳转|
|工作人员列表/详情|GET /operations/requests、/operations/requests/{request_id}|须PRIVACY_HANDLE明确授权；普通运营角色不自动获权|
|开始处理/拟答复|POST .../start、.../response|对应请求版本；拟答复材料须由处理人上传且为REVIEW_EVIDENCE|
|独立复核|POST .../review|须PRIVACY_REVIEW，不能审核自己的请求或自己拟的答复；检查同一答复摘要|

列表可分页；错误提示转换为具体中文，例如“申请不存在或你无权查看”“这份申请已有新进展，请刷新”“请由另一位工作人员复核”。原错误码保留在技术记录，不直接当页面说明。

## 偏好与处理结果的边界

个性化和营销默认关闭，休息提醒由页面按保存的分钟数执行（0表示关闭提醒）。当前榜单本身是不按个人画像排序；本批没有启用营销推送。保存设置不等于新建推荐引擎或已验证系统推送退订。

RESPONDED只表示已有人工核验的答复，不能显示“所有操作完成”。FOLLOW_UP表示仍有待处理事项或需复查的保留记录。DELETION_REQUESTED、ACCOUNT_CLOSURE_REQUESTED始终带EXECUTION_PENDING和待办，不会自动删文件、删账号或伪造供应商回执。实际执行、后续回执与撤回效果仍须按对应业务核验。

正式保留说明必须引用已生效的 `privacy.retention` 规则版本，内容包含 `terms.privacy_retention.categories`；每项声明scope、basis和max_review_days。它只是明确已审核依据和复查上限，不由程序自动认定法律允许。用户确认尚缺正式依据，登记EXT-PRIVACY-20261020，不能用合成测试配置上生产。

## 怎样验收

从仓库根目录运行 `node scripts/backend-check.cjs privacy`，使用指定的本机隔离MySQL。专项覆盖本人/他人、机构头拒绝、重复提交、独立复核、草稿不泄露、附件私有、旧答复保留、删除待处理、分类留存、并发设置及审计失败回滚。真实材料与实际删除、页面、真机和正式启用另外验收。

尚需本侧继续：实际删除/注销处理与下游结果衔接、投诉对具体业务限制及解除的核验、素材机审和真实文件标识。需队友：页面和提醒实际运行。需甲方：真实联系人、投诉渠道、分类保留/删除依据。不能把三类待办混成“全部等甲方”。

## 结果通知兼容补充

审核通过的答复在同一笔数据库事务内进入既有业务通知。通知domain新增PRIVACY，页面点击后打开对应个人申请详情；只发申请人的个人身份收件箱，不发机构或其他成员。即使关闭营销，也保留这种业务答复通知。请扩展消息类型处理，不能因遇到新增类型导致页面报错。通知正文不带申请详情或附件内容，仍需本人登录后查询。

如果通知保存失败，答复与正式历史一起回滚，不会在后台显示已答复、用户却没有通知。原有通知已读和权限机制继续使用。
