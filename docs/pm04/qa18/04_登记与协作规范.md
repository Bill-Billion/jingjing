## 2. 每一条事实（最小机器槽位）

槽位键为 `原标准ID|实际端|所需场景`，完全自动由原JSON生成。原`E2E`通常是`api/app/web × normal/reverse/unauthorized/duplicate/state_change/recovery`。

每条测试须有：`run_id, round, criterion, surface, case, outcome, owner, environment, backend_sha, app_sha, web_sha, assertion_id, test_command, exit_code, evidence_path, evidence_sha256, chain_id?, record_id?, roles?, defect_id?, resolution?`。

状态含义：

- `NOT_RUN`：本轮没有证据；默认状态，不能靠已有源码升格。
- `PASS`：当前冻结版本、当前环境的**确切测试断言**通过，有实际退出码0及内容摘要；E2E还须同链ID、主记录ID和角色。
- `FAIL`：断言与正式预期不符，有原失败日志，生成QA18缺陷单。
- `BLOCKED`：运行环境、合法测试资料、设备、已证实前置阻断造成未执行；有具体证据及责任人。
- `NOT_AUTOMATABLE`：必须是客观不能机器判断的人工质量、真实外部通道、实体机或合规签收，需书面原因、实际责任人，不折算机测PASS。

不使用“跳过即成功”。归档历史测试仅作线索；不同代码SHA的PASS只可用于复现比较，不自动搬到新一轮。

### CLI例子（G01测试事实，字段均需换为实际值）

```bash
python scripts/qa18_registry.py record \
  --run-id pm04-g1-discovery-20261125-01 \
  --criterion TASK-01 --surface api --case normal \
  --outcome PASS --owner chengcongcong222 \
  --environment <真实独立测试环境ID> \
  --evidence .local/qa18/proofs/g01-actual-pass.json \
  --assertion '<实际被执行的精确断言ID>' \
  --command 'node --test <实际测试文件>' --exit-code 0 \
  --note '同一已核合法供给方提交，业务进入待审；平台独审后公开，本次按现行合同核对'
```

示例 `TASK-01` 属于原G01；实际是否覆盖本次测试内容，仍必须按`matrix.csv`中该标准确切端×场景，以及真实执行断言核对，不能仅凭例子或文件名记PASS。日志文件必须真实存在、包含有效断言结果，不得先创建伪PASS文件。跨端E2E必须另加`--chain-id --record-id --roles`；后续从FAIL到PASS需要`--resolution`描述本次确证修复/夹具修正。

```bash
python scripts/qa18_registry.py check --run-id pm04-g1-discovery-20261125-01
python scripts/qa18_registry.py report --run-id pm04-g1-discovery-20261125-01
```

### 输出与备份

`.local`保存受控原始执行日志、业务记录和凭据，禁止推送。要存仓库的公开摘要只允许：源SHA/测试断言/去标识的业务ID和角色别名/路径/错误码/结果/摘要哈希；不保存Bearer、短信、身份证件、未脱敏文件和私有视频。若证据真实含隐私，生成**删敏**报告并附原始文件SHA，原文仅留本机。日报与组覆盖摘要可从`report.json/md`衍生并写`docs/reviews/pm04-qa18-20261125/`，但不得冒称已在远端写入。

## 3. 统一BUG条目（同一问题只设一个缺陷ID）

`bug_id, discovered_at, group_ids, acceptance_ids, e2e_ids, severity, kind, owner, status, version, environment, actual_record_id, role, original_key_sha256, expected, observed, request_endpoint, response_code, reproduction, before_proof_path, before_sha256, root_cause, fix_commit, target_retest_path, target_retest_result, regression_run_id, reviewer`。

- `OPEN` → `REPRODUCED` → `ASSIGNED` → `FIXED_WAITING_RETEST` → `RETARGET_PASS` → `FULL_REGRESSION_PASS` → `CLOSED_REVIEWED`。
- 反向可进入 `NEEDS_MORE_EVIDENCE`、`BLOCKED_EXTERNAL`、`NOT_A_BUG`（须阐明原标准及已有实际行为）；绝不以“无法复现”直接当PASS。
- 页面已出现后端 `200`但无法显示或保留原状态时，前端先复现；后端直接 `403/409/503`须对照当前权限、合同与具体前置，不能按状态码自动判后端错。
- 证据格式固定：失败前命令+日志、修复SHA、同原场景复测、影响域回归、审阅。缺任一环节不得关闭问题。

## 4. 机测组织模式

后端Codex担任测试主办/裁判（不是前端代码作者）：生成同批资料、分批执行后端/HTTP、收集两端正确日志、导出覆盖表及缺口、归因分派、总回归。前端Codex只管理自己的Flutter/Vue运行、测试和修复，交回准确SHA、构建/断言日志、页面动作/截图/文件状态；不代后端签成功。

按组交流极简：

- **开组**：组号、冻结SHA/环境、必测标准列表、已有可复用测试文件、预计用到角色/业务ID。
- **交结果**：PASS/FAIL/BLOCKED及与正式条款关联，原证明路径、最小复现、谁补。
- **交修复**：改动SHA、原失败→当前通过、影响模块、是否需新建测试数据。
- **交回归**：新一轮完整运行的统计及尚欠项，不用以前不同SHA的成功凑18/18。

“逐组机测”不等于每组一个PR；可以一个测试候选累积真实证据，每组一个稳定报告记录。P0/P1及时修，其余问题集中分域领取，不让前后端反复中断互相等候。每个新固定源码全量回归必须有全新的run_id。
