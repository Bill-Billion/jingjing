## 问题归属、修复与失败保留

**QA18-FE-024：App开票材料取到正确字节后无法保存。** 初始浏览器请求200且文件摘要正确，但 FilePicker Web 拒绝没有扩展名的文件名。修前新增回归实际1失败；`18a8d20faa52cb8b8cf7956926a32c820a49dd86` 将保存名补为中性`.bin`，不猜原文件类型，不改变字节或权限。27项关联测试通过；浏览器在原失败申请上成功保存两份材料，最终新环境也再次实际保存。测试同时覆盖后续读取被拒绝时不得保存旧字节。

**QA18-ENV-022：批量隔离环境未显式启用模拟开票。** `57b2b2df`仅在BATCH测试环境传入`NODE_ENV=test`及`INVOICE_SANDBOX_ENABLED=true`。3项配置对照确认缺配置拒绝、显式测试配置仅生成模拟票据、生产开具仍关闭；随后真实API和双端流程到达独审及更正。没有打开真实税务接口。

**QA18-TEST-023：准备和驱动假设。** 原订单读取路由、封存读者名单、恢复按钮滚动位置先后有误，修正为实际契约，保留非参与人拒绝及来源创建者必须在读者名单的规则。旧主申请回执丢失后，第一次驱动退出；随后仅凭API确认原结果，没有冒称该次App已恢复。最终新环境在主申请本身完整观察了App原键恢复。

**QA18-TEST-025：误把历史已付款样例用于当前模拟器退款。** 原环境`712c3a32`的付款绑定是`synthetic.app/synthetic.merchant`，当前模拟器为`SIMULATED_ONLY`，因此退款发送503，原退款仍APPROVED/版本2，未发送。这是已有样例限制，不是确证后端支付缺陷。原申请`0910e15d-26e3-4da5-876f-83ba67cd926b`及退款`92970b06-3e15-4584-ab00-05acae8173f7`原样保留；没有重写其绑定、到账状态或把新ID当作它的成功。

改用新环境后，测试准备尝试从已有已购商品下单，先遭错误报价摘要412、重复订单409；另一个待审商品虽正常双审上架，但仍用旧规则，被当前合同要求409拒绝。最终准备脚本`73693b6b`使用原未付款订单，通过当前付款服务办理，不再新增商品或放宽规则。中间正常审核造成的待审商品上架状态保留在新环境，不称环境仍是初始状态。首次UI宿主尚未就绪的ENOENT也保留。上述均为测试前置失败，未计为多个产品缺陷。
