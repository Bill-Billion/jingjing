# 给前端 Codex：G1 机测协作，不再泛化开发

本轮由后端Codex牵头统一机测。前端在原 `pm/pm04-acceptance-20261118` 已形成的源码基础上，仅开展原18组要求的 **App/FlutterWeb/Vue端侧自动测试与确证缺陷修复**。不创建MCN新冷启动需求，不提前做不必要的视觉重制，也不按后端失败直接更改前端测试预期。

## 执行接口

1. 接收后端的当前组号、正式标准ID、`required_surfaces`及`required_cases`、当前后端准确版本与新隔离环境ID。
2. 保留自己现有工作树和未提交增量；本端测试固定实际前端SHA及构建摘要。实际连接同一个127.0.0.1隔离后端和原业务记录；不可用独立单元测试创建的别的订单代替同记录。
3. 对每条 App/Web要求实际执行：正常、失败、越权、重放、状态变化和恢复（以正式151登记为准），并返回 `case_key / frontend_sha / backend_sha / environment_id / chain_id / record_id / role / assertion_id / command / exit_code / proof sha`。
4. 页面问题先检查真实控件与网络实际请求、已上传文件回执、权限与版本；只有有最小复现时才修源码或更新已经不适用的测试定位。真实需求未变，不能删弱断言、移除P0年龄/资金权限前置。
5. 机测可以先在Flutter Web和Vue完成；实体机的安装、视觉、播放与文件保存放在第二轮机器回归之后，不把debug包构建视为手机验收。
6. 仅修本端证据确定的缺陷。修完交SHA、改动文件、前后对照原日志、受影响测试通过结果及残余限制；后端将其纳入下一候选的完整回归。

## 优先接单顺序

按 `G01→G16→E2E-01…12→G18`；任何组无 App/Web要求的槽位不用额外开画面。多个组共享路由/组件的重复页面检查可以跑同一次测试，但必须逐条记录具体断言，不能用“Vue已构建成功”代表一个流程全绿。
