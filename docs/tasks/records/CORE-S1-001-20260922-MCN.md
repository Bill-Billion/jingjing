# 第三批修复：机构不能擅自绑定艺人或改掉他人身份

2026-09-22，本侧已完成这批旧入口修复，本机检查通过，待上传后的GitHub复验。它解决的是未经同意就获得权限的问题，完整的邀请确认流程尚未建成，旧问题整组仍在进行。

|原来会怎样|现在怎样|
|---|---|
|机构填入艺人编号就建立合作，还覆盖对方身份资料|旧添加入口明确未启用，不建立关系、不改身份；客户端声称“已同意”也不能绕过|
|移除不属于本机构的艺人，也可能改掉对方身份|旧移除入口暂不放行，不改任何人的身份或历史关系|
|提交机构申请会覆盖申请人的个人身份|只保存待审核机构材料；个人身份保持原样，不附带未经确认的免费期承诺|
|旧绑定被当成查看艺人及收入、导出资料的权限|名单、收入、排名和导出暂不放行；机构只看自己的申请概况，历史批准明确待核验|
|批量提现没有真正受理也返回编号和到账承诺|明确未启用、未受理；不返回假编号，不承诺到账|
|粉丝画像返回编造的年龄、性别和地区统计|明确尚未接入真实数据，不提供假统计|
|旧“已交付”订单可以继续验收结算，给未经确认的MCN分佣|祝福视频和代言视频的旧验收结算入口暂停，内部结算调用也拒绝；不改订单、不动钱包|

为什么连读取和结算一起处理：只关掉新绑定仍会让过去未经本人同意的关系继续读取资料或产生佣金。旧表没有保存本人确认、合作范围或期限，因此不能凭active或approved推断授权成立。历史资料没有删除或批量改写；不因此断言历史合作全是假的。

原MCN旧实现可从Git历史查看。本轮不新增SQLite业务表，不把新的邀请业务继续扩展在旧数据库上。正式数据库仍为MySQL8。

## 当前计划和下一步

下一步本侧进入个人/机构权限基础（CORE-S1-002）：

1. 在MySQL中分别保存个人账号、机构、机构成员及能力，避免一种身份覆盖另一种。
2. 明确谁能代表机构发出邀请；邀请只能由对应本人接受，保存确认记录，处理重复点击、失效及撤回。
3. 机构成员权限与艺人商业合作授权分别管理。入驻或入机构不自动等于允许使用作品、读取全部收入或代为收款。
4. 测试跨账号、跨机构操作被拒绝，再接双方页面。商业合作范围、期限、单笔佣金和历史合同约定按后续合作/合同任务落实，不能把邀请接受直接当成无限授权。

队友继续App和网页：机构申请展示“待审核”，旧批准展示待核验；合作、收入和提现未启用时显示原因，不把空列表解释成“没有历史艺人”，不把失败改成演示成功。当前机构信息的talents为空同时cooperationStatus=not_enabled，表示尚无可用的已核实关系，不是清空历史。本侧未修改前端，未替队友认领。
