晶晶日上 · 分账逻辑与清分结算规则

面向后端/结算系统：定义每一类业务的资金如何拆分给谁、何时清分、如何开票计税、如何退款，以及分账规则与分账明细的数据结构。规则引擎化、可配置，新业务只加规则、不改主流程。

1核心：两层分账模型

先抽平台佣金（第一层），再把"供给侧可分账金额"在 MCN 与艺人之间分（第二层）。返佣从平台侧列支，不碰供给方本金。

1.1 资金流（一笔订单的钱怎么走）

买家付款出品人/品牌/用户下单支付
→
持牌机构监管进入待清算/托管账户，平台不触碰、不沉淀
→
履约 + 确认交付/验收，买家确认或自动确认
→
清分引擎拆分按分账规则一次拆成多笔
→
T+1 到各方账户平台 / MCN / 艺人 / 返佣方 / 承制方

1.2 两层拆分（撮合类业务）

  • 第一层 · 平台佣金：成交后平台先抽——样片/数字商品 18%，商单/线下出场 22%。
  • 第二层 · 供给侧分成：扣除佣金后的 82% / 78% 为"可分账金额"，在艺人和其归属 MCN 之间分：默认 艺人 80%、MCN 20%（即可分账金额的 80/20）。
  • 独立艺人（无 MCN）：可分账金额全部归艺人（样片 82%、商单 78%）。
  • 返佣（推荐/KOC）：从平台佣金里列支、设上限，平台不倒贴；详见第 4 章。
设计原则：① 平台不设资金池、不垫资，全部走持牌清分；② 分账只动"真实成交、已确认"的订单；③ 数字人、样片所有权始终归艺人本人，分成关系不等于所有权转移；④ 所有比例可在后台按合同/MCN 等级配置，但需当事人在线签署确认。

3MCN 与艺人的分成规则（第二层）

分成只针对"供给侧可分账金额"（样片 82%、商单 78%），默认艺人 80%、MCN 20%。
归属状态样片（占成交额%）商单/线下（占成交额%）
独立艺人（无 MCN）艺人 82%、MCN 0艺人 78%、MCN 0
归属 MCN（默认 MCN 分 20%）MCN 16.4%、艺人 65.6%MCN 15.6%、艺人 62.4%

3.1 规则要点

  • MCN 分成率可配置：默认 20%，可按 MCN 合同/等级在 10%–30% 区间设定；调整须艺人在线电子签署确认后生效，存量订单按签约时比例执行。
  • 所有权不转移：数字人形象、声音、样片版权始终归艺人本人；MCN 仅按约获得分成，不取得资产所有权。
  • 签约关系决定分成：以有效《MCN-艺人签约/授权协议》为准；默认一人一"主 MCN"，订单发生时按当时归属关系自动路由分账。
  • 解约：分成关系终止即停止向 MCN 分账，资产不转移、不影响艺人后续交易；已成交未清分订单仍按原约执行。
  • MCN 侧义务：MCN 承担其承诺的管理/推广/垫付等义务，平台只负责按确认结果清分，不介入 MCN 与艺人的内部约定纠纷（但冻结争议金额）。
合规：MCN 与艺人的分成、授权须书面化、实名化；自然人艺人所得的个税处理见第 6 章。平台不得通过分成安排使任一方规避法定纳税义务。

4推荐返佣与共创裂变

返佣是平台的"获客成本"，一律从平台佣金/毛利里列支、设上限，绝不动 MCN/艺人本金；只设一级推荐关系。
业务返佣（占成交额）口径 / 上限平台净留
样片/数字商品7.2%平台佣金 18% 的 40%10.8%
商单 / 线下出场6.6%平台佣金 22% 的 30%15.4%
定制片 / 共创包场10%在平台毛利约 40% 内列支毛利约 30%

4.1 返佣规则

  • 只设一级：仅"直接带来该订单的推荐人"获得返佣，不设多级/团队层级、不以发展下线人数计酬（符合禁止传销规定）。
  • 结算时点：订单确认并度过退款/售后期后，与分账同批或售后期满 T+1 结算；退款、撤单、自购、虚假交易不计返佣。
  • 风控：返佣与实名、设备、支付、IP、收货真实性挂钩；异常订单冻结返佣，刷单追回。

4.2 共创片场裂变

  • 门槛：最低 10 人上传数字人开拍、满 20 人发起人免单（免单为服务权益、不产生现金分账）。
  • 返佣：邀请/发起方按定制片规则返佣约 10%；各参与者获得含本人数字人的专属片段用于再分享。
  • 一带 N：一个主订单带动多人创建数字人（创建费/托管），后续成交各自走第 2 章分账。

5资金清分与订单状态机

买家资金全程在持牌机构监管账户，平台不设资金池；清分由持牌机构按分账指令直接到各方账户。

5.1 订单状态机

待支付
→
已支付·托管资金进入监管账户
→
履约中里程碑/交付
→
待确认交付待验收
→
已确认或超时自动确认
→
已清分T+1 到账
退款中未清分：原路退、取消分账
→
已退款
纠纷·冻结冻结争议金额
→
裁定继续清分 / 部分或全额退

5.2 清分要点

  • 持牌清分：对接银行/持牌支付机构的"担保交易＋分账"能力；平台只下发分账指令，不代收代持。
  • T+1：确认后次工作日完成清分；自营里程碑按节点分次放款。
  • 多次清分：一笔订单可按里程碑/部分退款产生多个分账批次（batch_no），每批多条明细（seq），全程幂等、不可重复清分。
  • 自动确认与售后期：交付后约定时限（如 7 天）买家未操作自动确认；数字商品一经交付原则不支持无理由退款。
  • 结算账户：平台/MCN/艺人/承制方均须实名并绑定本人/本企业收款账户，通过资质与协议审核后方可收款。

6发票与税务处理

结算系统须为每笔分账记录"开票方、税率、个税处理方式"；增值税一般纳税人现代服务税率 6%，含税收入先做价税分离。

6.1 两种开票模型（按业务配置）

模型A · 撮合（平台仅就佣金）B · 自营（平台全额收）
适用样片、商单、线下出场等撮合交易定制片、代做样片、创建、托管
平台开票就平台佣金/经纪服务费开 6% 发票就订单全额向买家开 6% 发票
他方开票MCN/艺人就各自所得向付款方开票（自然人由委托代征主体/税务代开）外包承制/制作方向平台开进项发票，平台抵扣
C 端简化（可选）为买家体验，也可由平台全额向买家开票、各供给方再向平台开票（平台进项抵扣）——需系统支持"全额开票＋进项回收"链路

6.2 自然人个人所得税

  • 所得性质：自然人艺人/推荐人所得一般为劳务报酬（预扣率 20%–40%）或经营所得（按规定核定/查账）；企业 MCN 自行申报。
  • 代扣代缴 / 委托代征：支付方（平台或 MCN）依法代扣代缴；建议对接持牌灵活用工/委托代征平台对自然人批量结算、代征个税并代开发票，实现"到手即完税"。
  • 结算前置校验：自然人收款方须选择税务处理方式（自证企业身份 / 平台代征 / 自行申报），未确定不得清分；返佣所得同样完税。
红线：不得用"私户拆分、虚开、虚假灵活用工"等方式帮任何一方逃税；开票须与真实交易、资金流、合同流一致（三流一致）。

7退款、纠纷与尾差处理

7.1 退款规则

时点 / 情形处理对分账影响
清分前退款取消分账指令，原路全额退款无资金流出
部分履约/里程碑按已完成且确认部分结算，余额退回仅就已履约批次清分
清分后退款数字商品已交付原则不退；服务类按责任方承担按各方分账比例追回；不足部分从保证金/风险准备金垫付后追偿
返佣联动订单退款则对应返佣作废/追回未发不发、已发追回

7.2 纠纷与尾差

  • 纠纷冻结：未清分冻结争议订单全额；已清分冻结等额风险准备金；举证后平台调解或依仲裁/司法结果执行。
  • 尾差：分账按"分"四舍五入，须保证 Σ各方金额＝可分账金额；尾差（通常 ≤1 分）统一由平台承担或计入平台，并记录 rounding_diff 字段。
  • 保证金（可选）：MCN/承制方可缴纳保证金，用于担保退款、违约与交付，提升清分优先级。

8后端开发规格（数据结构与门禁）

建议"规则配置驱动、清分与业务解耦"：监听 order.confirmed / milestone.reached 事件 → 读取 settle_rule → 生成 settle_batch/settle_entry → 调用持牌机构分账接口。新业务只加规则。

8.4 校验门禁（落库/清分前）

  • 规则内 percent 之和＋remainder 逻辑＝100%；配置保存即校验。
  • Σ settle_entry.amount ＝ settle_batch.base_amount（含尾差），借贷平衡。
  • 幂等：同一 order＋milestone 的批次唯一，重复请求不重复清分。
  • 仅"已确认 / 里程碑达成且未退款、未冻结"订单可发起清分。
  • 收款方实名、协议、税务处理方式齐备，否则该笔挂起并告警。
  • 退款/纠纷自动联动冻结或追回返佣与各方分账。
落地建议：比例与角色全部配置化（不写死在代码）；清分服务独立、以事件驱动；对接持牌机构分账 API 并保留全量对账文件，每日与渠道对账、差异自动告警。
