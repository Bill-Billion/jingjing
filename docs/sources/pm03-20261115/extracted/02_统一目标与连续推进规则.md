# 统一目标与连续推进规则

## 一、当前判断与工作模式

主要后端功能已经具备交给前端集中接续的基础。下一阶段不再把“后端把全部潜在问题排查完”作为前端开工条件，而采用：前端按当前有效需求和现有页面持续接入，后端交付可操作环境并随联调修复，设计提前准备下一批。

当前候选c1d750b4，接口0.31.78-rc.11/0225。后端报告222文件、2334通过、0失败、1项真实旧库缺样本；128份同次HTTP、9624响应格式通过。PR与服务器远端检查已有成功回执；App检查与网页构建成功，网页交易准备仍失败。具体来源见驾驶舱“范围与依据”。这些是准备联调的依据，不是正式上线结论。

## 二、四份输入共同使用

1. **当前有效需求与已确认变更**：决定谁能做什么、哪些规则适用。V5不是孤立的最后依据，后续合同和通告发布变更必须一并核对。
2. **固定候选的接口与实现清单**：决定方法、字段、权限、状态、错误和真实限制。`contracts/openapi.yaml`与`contracts/implementation.json`同时读，不能仅看到接口名就认为实际供应商已经接通。
3. **前端现有页面及已确认UI规范**：复用近期重塑成果，不重新生成全站。一个页面可以组合多个接口，不要求一个接口对应一个新页面。
4. **可用的隔离环境、角色和业务资料**：可以实际办理并保留记录，区分脚本准备与真正页面操作。

需求、接口、设计不一致时，引用冲突点登记并交对应负责人解决。不得为迎合现有代码删需求，不得为了页面效果自行计算最终钱账和授权真值。

## 三、进入接入不等于通过合并或上线

### 可以立即并行的事

前端核自己的工作树、页面及接入差距，按固定接口准备；UI交共用组件和首批状态；后端准备隔离服务、角色、文件、规则和已知失败的合法测试前提。

### 一条业务开始实际联调的条件

本条需要的服务可访问；前后端版本明确；需要的角色、身份、授权、已审规则和资料有效；可以做一次最小动作并核到结果；没有阻断本条的资金、越权或隐私风险。

其他不相关业务的非阻断失败，不必使全体等待。当前网页PR15及PR17的受影响路径必须先排查，不能以跳过或假成功取得本条通过。

### 合入共同版本和正式启用的条件

按仓库要求完成准确候选的必要检查和实际审阅，不绕过失败强行合入。真实服务、签名包、设备、恢复、运营与财务签收保留原条件。开始联调不代表可以部署、收费或对公众开放。

## 四、连续执行循环

**选择原任务 → 核有效需求/接口/已有页面 → 核环境角色 → 接入一个操作 → 立即实际验证 → 记录并归类问题 → 修复/复验 → 完成本条跨端办理 → 对应验收复核 → 进入下一条。**

前端同时深入联调一条主业务，最多再准备一条不冲突的业务；UI可以提前一批。后端先处理当前已复现的高风险和主链阻断，再准备下一条环境资料，之后处理同批普通缺陷及有明确资料的外部服务接入。

任何一方等待时，不需要重复全文扫描或全量跑测来填时间。可切换到不受影响任务；真正无可执行项时写清最后缺项、负责方和继续条件。

## 五、如何处理接口问题

- **资金、权限、隐私、数据损坏**：立即停止受影响危险动作，查根因并修复；不能推迟到前端全部完成后。
- **正常业务无法继续**：本批优先处理。先核数据和配置，再区分页面调用或接口缺陷；后端修接口，前端修接法。
- **不阻断的一般问题**：归入原任务，同批集中修复；如果它属于原必测要求，未修前仍不能关闭该项。
- **视觉微调**：UI统一给定稿，前端集中应用；不阻塞安全可用的接口接入。
- **真实业务规则冲突**：只暂停受影响动作，提交引用和选择建议；不凭猜测增加收费、权益或合同范围。

“后台运行时修复”与“网页测试资料修复”不是一回事。当前实名失败应恢复正常角色前提，保留未实名、未成年、过期、无权和重放的拒绝检查，不能把所有测试账号默认改为合格。

## 六、版本与合并安排

1. 接手先fetch和查看工作树，不覆盖本地UI重塑、未提交或未上传内容。
2. 将c1d750b4作为本次交接参考；若远端更新，先核提交/接口/迁移差异和检查结果。前端可在保留自己成果的工作树/任务分支中整合该候选，不从旧main重新开发。
3. 固定本批版本，后端只发布必要补丁；每次说明影响操作、字段/状态/错误/权限、迁移或配置变化、前端动作和验证结果。
4. 补丁使用前后端明确的新版本组合，并重新验证受影响范围。不要反复用旧构建跑新接口然后汇总为“同版通过”。
5. PR39不强推、不由本包自动合并。必要检查及维护者审阅后形成共同版本；后续按可独立验证的较小业务批次提交，避免一个申请长期堆叠。

## 七、进度和原验收分别记录

新增的“后端有接入基础、环境与角色可用、页面已接通、完整办理已验证”是中间进度，不替代原151项标准。原要求包含真实服务、实体机或独立审阅的，必须继续保留。

原本仅要求后端且已满足的项，可以由另一责任人及时复核，不用无限等全站UI。原本要求跨端的项，不能用接口通过替代。通告发布投稿切片完成，不代表通告到商单履约整条路线完成。

看板不直接把工作便签写入原PASS。双方在仓库现有任务板、各自CURRENT和正式验收文件里记录事实，引用一份实际证据，不复制多套总账。

## 八、停止条件与范围保护

遇到真实资金/生产调用、公开服务、破坏性迁移/清库/重置、超出权限的合并、重大商业规则变更，先暂停对应动作并取得必要授权。日常已授权的页面开发、隔离测试及本侧缺陷修复可连续进行。

不动既有3490和离线APK，不把模拟角色或源文件放进正式环境，不在仓库、看板或便签里记录密码、Token、Key和真人敏感资料。限定测试服务的访问、有效期和停止办法；有效期不会自动因计划变化延长。

## 九、本轮完成目标

12条已有业务在所需App/网页/运营角色之间能完整办理，并有原标准要求的正常及关键逆向证据；必要接口问题关闭。真实外部条件和最终发布仍按原要求逐项取得结果，不删范围、不以停用功能冒充交付。

不设置未经测量的总完成率或新的固定上线天数。首批现货与通告实际完成后，按真实页面缺口、联调缺陷和外部待办重新评估剩余工作。
