# 交接记录与补丁规则

## 一、环境交接：没有填写就不能说已经可用

复用 `data/联调环境交接模板.json`，并把实值归入现有仓库交接记录。不要平行建立新环境管理系统。

|字段|应记录什么|
|---|---|
|版本|实际后端commit、接口/迁移版本；前端commit与构建分别记录|
|访问|实际受控访问方式；前端不能访问远端服务器的127.0.0.1时，用经授权的本地同环境或受控连接，不擅自开公网|
|期限|环境何时到期、由谁停止；续期需明确，不能因计划文档自动延长|
|角色|本条需要的买家、艺人、机构、制作、运营、独立审核；权限范围和合成身份前提|
|资料|已审规则、商品/规格、授权、文件、合同及样例版本；不得作为正式商业默认值|
|模拟|哪些外部环节是模拟，如何触发失败、等待和重复回执|
|操作|实际启动、停止、备份、重置方法及影响；重置前协调，不删对方尚待复验的记录|
|回执|前端实际连接/最小操作结果、日期、测试业务编号、未解决问题|

只记录受控凭据交接位置，不填写密码、短信验证码、API Key、访问Token和真人信息。

## 二、问题记录：先定位，不直接把所有失败归为接口缺陷

沿原W/ACC登记：问题编号、业务链、候选/前端构建、角色、业务编号、预期与实际、复现步骤、必要脱敏响应、证据路径、严重程度、唯一主办、下一动作、修复版本、复验人/结果。

优先判断：测试前提或环境 → 页面调用/参数 → 后端行为 → 需求冲突。归因未确认就写待定位，不为制造进度把静态猜测写成漏洞。

高风险和主链阻断优先；其余同批处理。接口缺字段但前端确无该业务依据时，不自动增加字段。两次重复失败而缺新信息时，停止盲目重试，记录原因并切换下一安全任务。

## 三、补丁交接：每次后端更新前端都能知道影响

至少写清：准确commit、契约/迁移版本、受影响的业务动作、字段/状态/错误/权限变化、是否需要更新配置或数据、前端修改点、回滚影响、测试结果、仍未验证部分。

本批接口原则上稳定，无关功能不混入；必要缺陷仍修。能保持兼容就不破坏旧接法；必须改变时双方先约定再发布。旧订单/合同不追改，新规则按适用版本执行。

前端升级后复验受影响范围，并在同一记录补上结果。后端修复完成不是自动验收通过。大范围共享权限、资金、迁移变化要按仓库要求补充分回归。

## 四、每条业务交付最小证据

- 有效需求和原W/ACC/E2E；引用完整预期，不改分母。
- 后端候选、前端源码与构建、接口/规则/数据版本。
- 参与角色、实际业务编号、准备脚本做了什么、页面做了什么。
- 正常办理、原要求逆向/拒绝/重复/恢复结果。
- 文件实际下载/字节、金额和权利结果等本条需要的核对。
- 已知缺陷、真实服务/设备/独立审阅等尚缺条件。
- 实际复核人、结论及证据路径。

不要把不同记录或不同版本的局部成功随意拼成整链；版本差异若确无影响须说明可复用依据。

## 五、状态分别记录

“后端有接入基础”“环境与角色可用”“页面已接通”“完整办理已验证”是工作状态。只有原正式登记按完整条件更新后，才能称“原标准正式通过”。端侧、供应商或独立审阅未完成，不能因为工作状态向前就把PARTIAL改PASS。

看板允许写入本地工作便签及导入导出；便签不触发仓库更新，也不改变上方正式统计。标记为验证完成时必须附证据和复核人；其他候选的记录只作为历史查看，不能移用到当前版本。

## 六、如何同步而不增加文档负担

各自更新自己的CURRENT：正在做哪条、已交什么、最后阻断、下一动作。任务板与正式验收只引用一份证据。每完成一条业务或一批必要补丁集中交接；无需每轮生成一套新的报告和副本。

阶段末由用户发起远端复核和驾驶舱更新。项目总览不在本轮维护；没有自动后台监测。
