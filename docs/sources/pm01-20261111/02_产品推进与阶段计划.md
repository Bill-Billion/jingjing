# 晶晶日上｜产品推进与阶段计划

## 1. 本轮产品管理结论

项目已经拥有较多实现和局部验证。下一步不宜继续平均扩大功能或只补更多字段，而应优先完成：有效需求一致、关键操作入口可用、同一笔业务完整办理、必要外部服务真实接通。

采用六阶段推进，不代表删去本轮范围或重新定义产品一期、二期。阶段用于组织依赖和检查成果。除受到真实服务或明确决定阻断的部分外，工作持续前进。

## 3. 学习成熟团队的方法，但不照搬组织规模

本计划参考Microsoft的需求分层、DORA的小批次与同时在做数量控制、GitHub的任务证据关联、Google的可重复发布。采用这些方法是为了缩短从实现到验证的距离，不增加大型会议、审批部门或另一套工具。

- [Microsoft：需求分层与验收条件](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/define-features-epics)：产品目标、功能、工作项分层；不是本项目业务来源。
- [DORA：小批次交付](https://dora.dev/capabilities/working-in-small-batches/)：每批可独立检查，及时反馈；不以代码量衡量价值。
- [DORA：限制同时在做的工作](https://dora.dev/capabilities/wip-limits/)：先完成少量高优先事项，不持续扩大进行中队列。
- [GitHub：关联任务、变更与看板](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/best-practices-for-projects)：同一数据的多个视图；本轮未新建线上Project。
- [Google：可重复发布与发布准备](https://sre.google/sre-book/release-engineering/)：构建、版本、回退和上线检查独立管理。

在本项目的具体应用：

|管理对象|沿用内容|用途|
|---|---|---|
|产品范围|V5及后续已明确变更、现有有效预期|确定必须做什么与适用版本|
|功能定位|原30个交付包、121个检查点索引|防遗漏，追踪到原REQ与现有代码|
|业务检查|12条办理路线|检查跨端、同记录的实际结果|
|交付签收|18组检查、151条验收标准|逐条积累证据，分层关闭|
|具体执行|本轮30个工作项，映射现有任务|规定下一动作、负责人、依赖和过关条件|
|发布条件|真实服务、构建、迁移恢复、运营交接|决定哪些功能可以实际开放|

这些分母互相交叉，不能相加，也不能用代码行数、截图数、接口数、数据库列数或单元测试数量换算产品完成率。

## 4. 产品经理与开发负责人的边界

产品经理负责：需求解释与来源标记、阶段目标、优先级、任务边界、变更影响、验收口径、阻断升级和阶段复盘。未得到依据的收费、权属、收益、资质与真实资金安排，不代业务方决定。

后端负责人chengcongcong222负责：业务处理、数据、主接口、后台任务、服务接入、资金与权利一致性，以及相应测试。前端负责人Bill-Billion负责：App、机构和运营网页、交互、客户端接入、原生构建及设备操作。跨端路线主办人负责组织同记录证据，并不意味着接管另一方的全部代码。

本轮任务是已制定的计划，但实际认领、提交和审阅必须由当事人记录；不得替队友宣布已接手。遇到明确本职实现问题可继续处理，不需要每个小任务都重新请示。商业规则变更、生产部署、真实收费和真实敏感材料操作保持独立授权。

## 5. 时间安排：短工作批次，按成果进入下一步

计划起点：11月11日这轮接手核对。首个复盘点建议为11月12日，核版本、规则及计数；第二个复盘点为11月13日，查看普通发布与资料办理成果。检查点不是完成承诺，不用于限制工具吞吐。

每个开发工作日结束只更新四项：本次实际交付、证据、阻断、下一动作。每个可独立复验的小批次形成一次集中交付。执行较快时可提前进入下一步；发生失败时登记具体原因和修复计划，不自动滑过验收。

后续阶段在前阶段退出时确定下一检查点，避免没有实际吞吐和外部服务信息却编出整个产品的上线日期。阶段条件满足后双方可自行继续施工；产品经理在用户发起阶段核对、提供新反馈或交付材料时做复盘，不持续后台运行。

## 6. 并行安排

每位开发者同时主办一个交付事项，另保留一项复核/支援位置。这是减少积压的工作组织，不限制工具在该事项内并行分析或运行独立测试。供应商待资料项进入独立等待清单，不占满两条开发线。

第一轮：后端W01/W02核起点及规则，随后W03处理通告；前端在候选固定后做W05资料办理，并接W03的普通发布界面。后端以W04限定本次副本范围并给样例；W09外部服务能力核对并行。

第二轮：前端W06机构批量、W07匹配说明；后端修复联调发现及旧记录兼容，准备现货/定制的同记录复验。三项后端已具备能力不重建。

## 7. 需求覆盖、问题修复与安全的顺序

“先覆盖需求”指先保证所有已确认业务都有明确去向及可办理主线，不是先实现一个已知错误的资金/授权规则再返工。已经确定会造成越权、错付、重复付款、敏感材料泄露或旧合同被改写的问题，必须和功能一起修。

一般排序：明确的业务规则差距 > 影响正常办理的缺口 > 关键异常和历史兼容 > 不影响办理的视觉微调。已授权视觉方向不重新推翻，不引入无来源的新会员权益、通用聊天或复杂制片平台。

个人信息工作按适用类别、持有目的、本人权限、原件和保留依据收敛验收。不把1207个数据库列都当作对外字段，也不能因赶进度省略需要提供或删除的本人资料。每类必须有依据和剩余说明。

若有阻断，写清哪个文件、哪个业务结果、怎样解除。不强制推送、不重写历史、不重复挑拣已包含提交，不直接合main。后续每批围绕一个可验收成果提交，避免继续把所有工作堆进无止境的大申请。
