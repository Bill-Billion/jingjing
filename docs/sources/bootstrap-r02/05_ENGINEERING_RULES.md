# 工程规范与后续施工护栏

**这是交接方提出的工程规范，不是来源文档已经实现的能力。首轮做设计和审计，确认后才按此施工。**

## 1. 先保留可用资产

根据仓库快照说明，主客户端为Flutter，主服务为Node.js/Express/CommonJS，运行数据库为SQLite。先核查当前仓库，不推倒重写、不因“正规化”立即微服务、不同时增加多个Web框架。

Web工作台若已有实现优先复用；若没有，提出一种成熟框架和一个共享认证/权限方案，说明成本后再定。A/B是使用界面与权限，不是必然拆成两套后端或两份数据。

MySQL迁移应有现有SQL兼容、数据转换、事务与并发、部署、备份恢复测试；DDL存在不等于可以改一个变量切换。是否本轮迁移根据实际独家锁定/交易并发及运行要求论证，不直接重复早期“1–2天可切换”的估计。

## 2. 数据与状态

- 登录账号、自然人/机构签约主体、成员、管理关系、收款主体分别设计；同一机构多种服务能力。
- 订单、支付、退款、授权、内容版本、供给方结算各有事实和状态，不混成单一可随便编辑的枚举。
- 授权有效性不仅取决于“SIGNED/EVIDENCED”标签，还看身份、权利、用途、期间、范围、撤回与提供方资产状态。
- 合同、报价、已购许可、样片确认和结算版本不可静默覆盖；改稿和补充条款以新版本/追加记录实现。
- 不能只按脚本ID锁独家：应检查许可范围、版本、用途、地域、语言、期间和既有许可；用事务/约束防止冲突成交。
- 修改现有数据结构采用迁移与兼容方案；旧数据丢失或不能恢复的变更先批准。恢复可以是备份恢复或向前修复，不硬要求所有破坏性迁移“无损down”。

## 3. 资金与金额

- 整数最小货币单位保存运算，明确currency及接口单位；旧接口可能已转换成元，逐字段查，不统一再除100。
- 金额、佣金、折扣承担、税和费用分别记录，定义舍入及总额守恒；不得用浮点和前端回传价格作为最终记账依据。
- 真实付款由验证通过的回调或可信查单推进；校验签名、商户/应用、订单、金额、币种、交易状态，处理重复/乱序/迟到回调。
- 退款申请、通道受理、实际退款成功、账务调整分开；重试不能双退。
- 私人/机构提供方的结算账户、应付、冻结、实际出款凭证分开；不把“管理员点已结算”描述成持牌机构已打款。
- 已付款的独家预留过期、规则升级、权利撤回等异常要进入补救/退款或人工处理，不吞单。

## 4. 素材、版权和隐私

- 私有文件按所有人/主体/项目/许可核验访问，不只在菜单上隐藏。
- 完整剧本的阅读、必要导出、指定AI服务交接必须有范围与日志；不宣传绝对防截图。
- 原图、声纹/声音、身份证、合同和结算凭证不得进入公开静态目录或日志。供应商缺配置不能降级为公开文件。
- 采集同意、项目使用同意、代理授权、公开用途升级分别留证；运营可代录不能代表示真实意思。
- 撤回后暂停新增受限处理；在制、已交付和已发行按实际权利及适用规则处置并保留证据，不用“旧合同快照”自动允许继续。
- 测试采用合成/明确获准材料，不拿真实客户照片或未授权作品调用AI。
- 标识应覆盖实际可控的展示、导出和交接；具体规则上线前根据官方要求复核。

## 5. 外部服务

分别记录：实现、配置、测试环境验证、真实环境验证、商业启用条件。火山、阿里和支付宝厂商偏好不是已经拥有产品权限的证据。

运行接口超时、失败、限流、任务恢复、文件失效、额度不足都必须有用户可理解的状态。统一适配层可以方便替换，但不承诺换厂商零成本；授权范围、数据地域和生命周期可能跟着变化。

真实网络失败明确失败。Mock可用于隔离测试、演示和开发，不得在生产交易失败后回退出虚假成功；演示数据不能混进正式报表。

## 6. 安全运行与仓库操作

- 先读README和脚本再执行；`npm install/ci`的生命周期脚本、应用导入、test、migration status也可能有副作用。
- 初次运行前确认SQLite路径是可丢弃目录，上传目录也是测试目录，第三方调用关闭；不要自动调用默认公网地址。
- `seed.js`可能清表；不在带真实数据的路径运行。`FIELD_ENC_KEY`不能为既有数据每次随机重置。
- 只查看.env.example；真实配置仅检查必要键是否存在，不把值读进报告。不得执行显示GitHub token的命令。
- 不自动修改远端、工作树、未提交文件、证书和云配置；不reset/clean、强推、部署、切换生产数据库。
- 工具、SDK或网络缺失写“未执行/阻塞”，不修改锁文件去凑一个绿色结果。
- 长中文Windows路径、POSIX npm脚本、Android签名和Flutter SDK锁定要求均先核实。不要全局改变执行策略解决局部命令问题。

## 7. 最小验收集合

除正常路径外，至少包含：

1. 个人作者与多业务机构共存；跨机构不能读写对方资源。
2. 主体授权、数字人授权和剧本许可检查失败时不能开始受限制作。
3. 首款、样片确认、尾款、成片各节点有真实依据，越级操作被拒绝。
4. 两位买家同时抢同一独家范围、预留过期后付款、重复回调均不会重复许可/扣款。
5. 商品改价、佣金调整、修改轮次改变不影响旧订单承诺。
6. 许可交付成功但制作取消、许可权利瑕疵、成片质量不符分别进入正确补救路径。
7. 下载链接过期、跨用户复制、后台越权、已撤回授权、私有文件回退等被正确阻断。
8. 测试替身与真实环境结果分开；无供应商凭证时不能生成“已生产验证”的证据。
9. 迁移从空库和代表性旧库都验证；旧数据不完整显示迁移/复核要求，不能默认通过。
10. Web工作台有真实操作闭环；Flutter真机性能与Android/iOS包分别验证，不能用截图替代。

已有`data/acceptance_seed.json`用例均未执行；首轮需按REQ生成完整映射，不把它们当完成结果。

## 8. 两人+Codex协作建议

一人牵头身份/权限/接口/数据库/支付，一人牵头App/工作台/交付体验；彼此交叉复核。公共接口、迁移顺序、许可和资金状态先定契约再并行。Codex承担局部实现与测试，不承担自动批准商业规则。

每个工作任务需有：REQ来源、目标、明确不做项、文件范围、依赖、兼容策略、风险、验收、外部启用条件。一次改动不要混品牌重命名、数据库迁移和新交易流程三个大变化。
