# 统一需求、参数与变更治理

## 1. 交接输入，不覆盖来源

`data/requirements_intake.json`保存REQ-001—REQ-060，逐项保留R0.2原记录。原44项带R0.1快照，新16项带版权增量来源。它是交接索引，不是本轮已批准的产品配置。

首轮在`intake_reports`中生成拟纳入仓库的合并版。原件和本包不回填，不把“暂无异议”变成批准，不用图片验收代替业务表决。

## 2. 编号规则

- REQ-001—REQ-060永久不改号，不编码期数。新增缺口先记`GAP-001`等，审查后再分配REQ-061起的新号。
- 旧决策明确写`V2-D01`，会后项明确写`V3-A1 / V3-D1`；不写歧义的D1。
- A01/B01/C01/M01/X01/Q01/F01为V2图示模块编号，不等于V3的A/B/C/D决策组。
- R0.2中拟新增的V3-C8仍是拟新增来源，不说原32项工作簿已包含它。
- PAR、WORK、AT-R02、AC等已存在的编号保持原义；新增测试采用独立`ACC-xxx`且保留关联。

## 3. 每条需求的最小记录

```text
id / 标题
原始来源、版本、章节/行号、原话摘要
原建议 / 研究修正 / 本轮拟采用
归并动作：保留、细化、调整、取代、待材料、待外部、待范围
本轮范围和历史分期（两列）
决策状态、实现状态、商业启用状态（三列）
批准人/日期/生效版本（未批准留空）
参数与合同版本、是否影响旧订单
模块、代码证据、测试证据、依赖、风险
复核条件、变更记录
```

来源中的“已确定”和工作簿空白冲突时，写清“方向来源声明已定；参数未见批准”，不要二选一抹掉另一边。

## 4. 三条状态轴

|状态轴|可用值示例|绝不等同|
|---|---|---|
|决策|待资料／研究暂定／方向明确／正式确认／已取代|正式确认≠已实现|
|实现|未审计／未开始／部分实现／模拟／待验收／已验收|测试替身通过≠真实上游可用|
|启用|未核验／待外部条件／可内测／可正式启用／暂停|已编码≠可公开收费|

每一次状态变化要有证据。测试记录包含环境、commit、命令、时间和范围，失败不删，未跑写未跑。

## 5. 参数不可静默覆盖

`data/parameter_history.json`保留R0.1的21条与R0.2的9条增量记录；某些编号重复是同一参数的版本变化，不是错误。现有唯一参数编号共28个。PAR-004保留90秒与2分钟旗舰冲突，PAR-019普通商单佣金不能与PAR-022剧本15%佣金混用。

暂定15%、50%、2轮、5日等只能用于方案/测试候选，不在正式种子数据或客户端硬编码。参数应有单位、适用商品/地区/渠道、允许范围、批准人、生效时间和版本。

每笔已确认订单保存交易时的规格、价格、付款计划、修改、交付、退款、许可及合同快照。改新默认不能重算旧单尾款或减掉旧客户修改次数。

## 6. 完整范围下怎么安排任务

旧P0/P1/P2只是`historical_phase`。另记`current_scope`，并用WORK-01—14组织依赖和验收；优先级用“阻断/高/中/低”，避免再用P0同时表示产品分期与缺陷严重度。

凡已纳入本轮的门户/商品/许可/独家/结算能力，必须有实际操作面和异常处理；不能“结构预留”即完成。外部暂未开通则分别记“内部实现完备”和“商业启用阻塞”，不伪造全部完成，也不擅自从任务清单删除。

## 7. 后续仓库内的建议位置

经首次报告确认后，建议在已有文档目录下合并（不要强迫改已有良好结构）：

```text
docs/requirements/
  source-register.json
  baseline.json                 # 结构化唯一维护入口
  baseline.md                   # 从同版记录生成的易读说明
  parameters.json
  decisions/                    # 正式确认的决定
  changes/CR-YYYYMMDD-NNN.md
  acceptance/                   # 用例与运行证据索引
  CURRENT.md                    # 当期范围、状态、下一步
```

Excel用于人类评审，评审结果经责任人确认后回写同一结构化基线，再导出新版，不能Excel/JSON/PPT各自独立改。包内原始Excel没有被本轮修改。

## 8. 变更流程

新意见 → 定位REQ → 比较原/新规则 → 判断对新单/旧单/授权/资金/接口/上架/工期的影响 → 对应负责人确认 → 更新规则版本和用例 → 在指定版本启用 → 记录结果。

普通页面与代码组织细节可由开发者决定并留设计说明；交易主体、真实权利、费率最终发布、正式付款、上线资质和已签合同改变，不用AI推荐代替责任方批准。

## 9. 需求与代码都要留连续记忆

每次开发会话结束更新`CURRENT.md`：基线版本、分支/commit、已完成、未完成、测试、风险、外部阻塞、下一步。两名开发者各用独立分支/工作树；涉及迁移、公共类型、付款和权限的修改先协调责任人。

不要把聊天长文当唯一记忆，也不要把旧文件名里的FINAL/ACTIVE/SSOT当永远不会过期的优先级。
