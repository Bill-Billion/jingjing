## 0. 本轮结论

先采用一套保守、可执行、能验证成本的P0方案，不再要求影视团队从零设计每一条软件规则。建议以“本人数字人参与的私人剧情短片定制”为第一款服务，由平台作为真实履约方组织有限的签约制作班底；商业经营、MCN市场和正式发行分期开展。

这不是把版本3直接改成“最终定稿”。本轮把文件中已有方向、未确认的原推荐、研究后暂定的规则、外部现实条件分别登记。可以暂定产品方案，但不能通过文件把未取得的授权、未开通的接口、未批准的资质写成已经具备。

本包已逐项处置版本3的32项决策，并补充12项遗漏或跨模块规则。来源、理由、相对原文变化、原会议结论、实施和上线状态分别保留。

## 3. P0暂定产品方案

### 3.1 先卖什么，暂时不卖什么

P0暂定售卖一项明确的私人定制服务：用户建立本人数字人，选择有许可的故事方向，确认角色与制作要求，经报价、首款、样片确认、尾款、成片验收后获得私人作品。

P0不开放：用户自由接商单、第三方真人陪演市场、MCN分销提现、角色竞拍、公开发行申请及发行收益分配。平台虚拟配角可以作为自己的合法库存服务资源使用，但不能混同为开放陪演市场。

P1保留数字人经营、商单、机构协作和匹配的交易结算；P2保留出品、公开发行及发行收入管理。后续不是重做P0，而是增加有独立规则的新业务类别。

### 3.2 谁向客户承担责任

暂按**真实自营定制**设计：平台是客户合同相对方，负责报价、交付、质量、退款和售后；编剧、制作团队、素材权利人依独立采购或授权合同提供服务。后台需要记录销售收入与采购支出，但P0不因此给客户或合作人开设平台可提现余额。

这是一项**附条件设计前提**。如果公司实际只撮合客户与独立制作商，不承担卖方责任，就不能只把文案改成自营；必须重做卖方、收款、开票、售后和持牌平台支付方案。由公司、财务/法务、支付机构核对一张真实合同与资金关系表后，才可启用正式收款。

原V3-A4/A5建议的多方分账并未删除，而是移到开放第三方交易时实施。普通商户销售款、采购付款、代收清分和用户资金余额不得混称为“分账”。

### 3.3 产品入口

长期业务心智保留“建立数字人—入戏—培育—成角”。P0公开App建议只显示“首页 / 入戏 / 我的”；数字人从首页及“我的”进入。“培育”“成角”在实际开放前不做可点击空入口，不宣传当前尚不存在的交易能力。

这明确调整了V3-A9的五个Tab推荐，理由是先服务实际可交付业务。未来新增能力要同步评审、功能说明与商店审核，不采用审核后暗中开放的方式。

### 3.4 数字人与素材范围

第一批只接受本人数字人与有充分使用许可的平台虚拟角色。陌生人、明星或网上图片不作为“自娱”例外放行。暂不向未成年人开放真人建模或付费定制；18岁是本轮产品范围选择，不称其为所有场景的法定统一年龄。

“长期数字人”的采购验收应看事实：完成一次有效授权后，可以反复选择同一数字人生成多部作品；脸声表现达到约定水平；可以暂停、撤回并处置服务商端资产。一个长期ID不必然证明专属模型训练、专有版权或稳定质量；反过来，用户无需再次上传素材也不必然说明使用了专属训练模型。应核验最终体验和权利控制，而不是只看接口命名。

### 3.5 剧本与制作方式

P0先准备3个具有明确许可的故事框架，按需填入用户角色、台词和场景。框架的许可须覆盖修改、AI处理及向个人客户交付；不以“已存证”代替创作/使用授权。AI辅助润色，人工负责质量控制。

运营或制作负责人维护框架。制作人员仅查看分配给自己的订单，提交样片、修改版及成片；不能代客户同意授权、代客户验收、修改支付结果。A端可代上传生产文件，但要区分“代录文件”与“代签意思表示”。

### 3.6 首个试制规格

| 项目 | 暂定内容 | 生效限制 |
|---|---|---|
| 标准成片 | 90秒，1080p，9:16 | 内部试制验证后，按订单确定的准确规格售卖 |
| 样片 | 30秒，展示人物、声音、关键画面与叙事风格 | 样片不是最终成片，需明确验证目标 |
| 角色数量 | 1位本人主角，最多1位合法库存虚拟配角 | 不接复杂多人真人剧情融合 |
| 付款 | 首款50%、样片确认后尾款50% | 称首款/阶段预付款，不称定金或资金托管；iOS商品适配另核验 |
| 修改 | 样片阶段2轮集中创意修改 | 平台错误、错脸、错误台词、文件损坏等纠错不占轮次 |
| 反馈 | 48小时未回复提醒 | 不自动验收、不自动扣款 |
| 工期目标 | 条件齐备后样片5个工作日；样片确认并尾款到账后成片5个工作日 | 只是试制目标，未验证前不可对外承诺 |
| 产能 | 首轮同时最多5单在制 | 满额须停止接单或明确排队，不无提示继续收费 |
| 成片在线访问 | 试定180天，提前30天提醒下载 | 经成本/条款审查，旧单不得被新默认值缩短 |
| 正式价格 | 本轮不发布统一零售价 | 原5000元为示例；按真实成本、渠道和利润要求逐单审价 |

P0仍然需要最后一次成片验收。样片确认只代表进入下一制作阶段，不代表用户放弃最终交付质量或法定救济权利。

### 3.7 退款与需求变更

| 场景 | 暂定处理 |
|---|---|
| 已付首款但未开工 | 全额退款，平台不另扣通道费 |
| 已开始制作，用户改变主意 | 按事先披露、实际完成且有凭证的合理工作结算；没有依据不自动扣费 |
| 样片在原范围内需调整 | 先完成约定的创意修改；平台错误另行免费纠正 |
| 已付尾款后用户换题材/换人物/增加时长 | 另行报价与确认，不偷偷改原订单 |
| 交付不符合约定、无法修复或平台未履约 | 依法处理退款、补救及责任，不使用“定制商品一概不退” |
| 付款或退款结果不确定 | 显示处理中，查渠道结果，不用本地记录冒充真实到账 |

以上是拟采用的客户政策，不是直接可签的法律条款。未经审查，不沿用原稿“未开工扣通道费”“最多扣30%”等任意扣减。

### 3.8 自娱、下载、公开分享与发行

P0交付私人查看和下载留存，不提供公开作品链接、站内广场发布或一键向公开平台发布。用户被明确告知：私人服务不附带公开商用、冒充真人、广告代言或影视发行权。

公开发朋友圈/社交平台与正式影视发行也不是同一件事。后续可以单独增加“允许公开非商业分享”的商品许可，但须先核清脸声、模板、音乐、配角、上游服务和标识范围。

平台不能技术上保证阻止已下载文件被转载，也不能承诺从他人设备追回删除。应通过授权、提示、报告投诉、平台可控链接和必要处置来管理风险。自娱转公开用途需要新的用途确认，不能直接后台改一个类别。

## 5. 需求如何统一记录

### 5.1 一个入口，不再四份材料各自修改

建议维护一份《统一需求台账》作为当前要求的索引。主文档、图、PPT、会议纪要是不同用途的展示，不各自新增与原要求冲突的规则。

本包以JSON保存同一版结构化记录，Excel用于评审与补充意见，Markdown说明当前整体方案。评审表有调整后，指定一名维护人登记到同版源记录再重新导出，不能让JSON和Excel长期各自编辑。正式工程阶段可把源记录和说明文件一起纳入版本管理；不必自建需求管理软件。

### 5.2 每条需求保存哪些信息

每条记录至少包括：永久编号、来源版本/原编号/位置、原推荐、本轮暂定方案、采用理由、与原文差异、P0/P1/P2归属、影响模块、所需外部证据、确认状态、实际实现状态、正式启用状态、验收方法与复核触发条件。

这三类状态必须分开：

- **决策状态**：待研究、暂定采用、正式确认、后置、已取代。
- **实现状态**：未审计、未开始、开发中、待验收、已验收。
- **生产状态**：未核验、待外部条件、允许内测、允许正式启用、已停用。

“暂定采用”不等于功能写完；“功能写完”不等于允许公开收费。

### 5.3 永久编号与历史编号

新需求统一使用REQ-001等永久编号，不编码所属期数，避免P1前移P0后要换号。原编号作为别名保留：例如REQ-001对应V3-A1，并关联V2-D17。

一定写**V2-D01**与**V3-D1**，不能都简称D1。原图中的A01/B01/C01/M01/X01/Q01等模块编号继续保留，但需注明来源体系。旧会议决策D01—D23不删除、不悄悄改义。

P0/P1/P2是上线分期；缺陷严重程度另用“阻断/高/中/低”，不要又混成一个P0标签。

### 5.4 合并后的优先级

1. 现行适用法律、已签合同与真实有效授权限制；
2. 有批准人、范围、生效时间的正式变更；
3. 指定版本的统一需求基线中已确认事项；
4. 当前允许用于设计/试制的暂定方案；
5. 原始纪要、会后评审建议、历史演示和代码注释。

最新原始反馈可能是重要新要求，但仍须登记影响并升级基线，而不是直接覆盖所有旧订单。现有代码则回答“已实现什么”，不能反向决定“业务必须如此”。

## 6. 数字可调整，但旧约定不能被随意重写

### 6.1 参数登记不是无限制后台配置

参数应写清默认值、单位、适用商品/渠道/地区、允许范围、调整权限、生效时间、版本、影响哪些订单及复核条件。暂定值不直接成为生产系统配置。

例如首款50%、免费2轮、工期目标5日，是试制假设；产品价格、上游额度、服务开通状态不能被一个“启用”开关当作既有事实。

不可设计为普通运营随意关闭的事项包括：未经授权不得处理/使用素材、支付验证、必要审核、标识、用户资料权限、历史合同不可静默改写。

### 6.2 每单保留“当时承诺”

客户下单时保存：准确价格、首尾款、角色/模板/用途、样片与成片规格、修改次数、退款规则、交付时间、许可范围、合同版本、交易渠道及当时适用规则版本。

之后默认规则从2轮变为1轮，新订单用1轮，旧订单仍按2轮执行。已付首款的旧订单，尾款不能用新首款比例重新计算。若用户在制作中要求新增角色/换题材，要新增一份变更报价并确认，而非直接改旧记录。

历史冻结不意味着发现违法内容、撤回或安全风险时必须继续履约。此类变化要另有暂停与处置记录，不能以旧合同快照压过适用法律或当事人权利。

### 6.3 变更分级

| 变更类型 | 例子 | 处理方法 |
|---|---|---|
| 参数变化 | 新单价格、产能上限、提醒时间 | 允许范围内由授权业务负责人审批；新版本、生效时间、新订单适用 |
| 流程变化 | 样片改为分镜确认、增加一次验收 | 业务与研发一起评估页面、通知、测试、在制单处置与排期 |
| 权利/资金变化 | 由自营改撮合；私人作品可公开发行；新增真人商用 | 重新检查合同、支付、许可、数据与商店条件，不能只后台开关 |
| 监管/安全事件 | 撤回授权、素材侵权、支付异常 | 可立即阻断风险；形成处置记录，再评估恢复与旧订单补救 |

### 6.4 变更记录的最小流程

新意见进入台账 → 找到受影响REQ编号 → 写明来源、理由、新旧差异 → 判断对新单/旧单/合同/费用/外部依赖的影响 → 相关负责人批准 → 更新基线及测试 → 在指定版本启用 → 验证后记录结果。

两名开发者阶段不需要复杂委员会：指定一人维护需求与基线，另一人复核影响；经营责任、合同、支付、权利事项仍由承担责任的人批准。不能让AI输出本身充当公司批准证据。

## 7. 保持系统可变，而不是把系统做得过重

P0只要求几个稳定边界：数字人及授权、商品和规则、定制订单、制作任务、作品版本、支付记录、后台权限与操作记录。P1商单、P2发行项目以后引用这些对象，但不把所有业务塞到同一个巨大“订单状态”里。

付款、制作、授权、退款各有事实记录。例如“已付首款”是付款事实，不是制作完成；“授权撤回”可以暂停制作，但不能把已经到账的款项抹掉。未来增加新付款节点时，不能直接把旧状态名重新解释。

当前不建议为32项待决策开发通用工作流搭建器或无限制规则编辑器。先做有限的价格/规格/提醒/产能配置，稳定的流程和必要的版本记录；确实出现第二种业务后再扩展。

来源中旧工程存在一些完成声明与主工程不同的情况，因此本包所有“实现状态”均为“未审计”。本轮只评审需求，不运行、不修改、不重新认证任何代码或生产服务。

## 8. 实验与正式发布条件

先完成5条内部样片/成片，记录AI成功与失败重试、人工工时、模板/角色许可、内容审核、存储及售后预估。正式售价必须由这些成本和真实采购、通道条件推导，而不是由“5000元”或“20%抽佣”倒推出盈利。

条件满足后最多5单同时在制；首20个完成订单或30天先到时复盘。样本小，只用于修正规格和流程，不用于宣称市场成功。严重投诉、授权、支付或质量问题即时复盘，不等样本满额。

建议跟踪：报价到首款、首款到样片确认、样片确认到尾款、各阶段主动退款、实际返工、每分钟生成成本、人工小时、按期交付、客服工时与单笔贡献。交易额、销售收入、渠道净到账、采购成本和利润各自显示，避免重复加总。

在取得以下事实前不能把对应能力正式开放：真实主体与商品身份、合法角色/模板素材、长期数字人服务能力、必要身份/同意与私有存储、支付/退款/iOS商品核验、适用备案与商店审查、真实制作能力和售后承担安排。

这不是把所有细节重新交回讨论，而是把大部分产品选择由暂定方案解决，把必须来自现实世界的少量证据留给实际责任人。
