# 完整流程由谁测、用什么资料测

本侧负责主要测试、准备模拟资料、记录问题和修复，并保存复测证据。队友检查涉及其页面的改动和双方共用规则；还未替队友认领或批准。用户只需确认业务是否符合预期，以及后续手机上的实际体验，不需要靠空账号逐页试错。

本批先处理身份反复跳动，再把“选本→许可→报价订单→项目改稿→制作→验收→尾款→结算”串起来。每次发现问题，先留下可重现步骤，再修复、复测、更新[问题记录](BUGS_20261005.md)。后续依次补充付款异常、退款、撤回授权、人员退出、商单与发行等操作。这里的测试范围不等于全部产品已验收。

## 已准备的业务资料

每次启动都新建独立测试库。以下六组订单相互独立，不必先做完上一组才能测试下一组。它们通过原业务接口和权限检查创建，不是在页面硬塞“成功”。

|打开哪组资料|已经走到哪里|接着可以检查什么|
|---|---|---|
|待确认报价|选本、预留许可、供应方报价、独立审核已完成|客户阅读并确认报价；核对生成的订单和当时承诺|
|待付首款|客户已确认，首款尚未记为到账|读取分期和付款状态；检查未付款时不能提前交付|
|待客户审样片|模拟首款、许可激活、项目改稿、剧本确认和样片审核已完成|客户读私有样片，接受或提出修改|
|客户要求修改|客户已对当前样片提出修改意见|制作方查看意见并提交下一版本；历史意见保留|
|待付尾款|当前成片已验收，尾款尚未记为到账|检查尾款信息，以及私有最终文件的付款限制|
|已交付并确认结算|模拟尾款已核对，正确最终文件可读；结算已独立审核且双方确认|核对订单、付款、合同和分成来源；没有真实转账|

测试规格、时长、金额、分成均明确属于虚构资料，不能复制成正式商品规则。本例许可只含私人改编和制作，不含发行。模拟权利、实名和签署材料不构成真实审核依据。

## 七种测试身份

手机号均为程序专用的虚构号码；只在本机短信替身中产生验证码，不向这些号码发送真实短信。验证码不是固定万能码，仍通过原登录接口验证。

|角色|用途|工具中的名称|
|---|---|---|
|客户／机构负责人|选本、下单、反馈样片、验收、确认结算|`payer`|
|作者／制作方|许可商品、报价、制作版本、结算资料|`recipient`|
|独立审核员|按照现有分离职责检查作品、许可、制作与结算|`independentReviewer`|
|无关用户|检查别人的订单、项目和文件不能被读取|`outsider`|
|机构普通成员|检查加入、成员权限与负责人权限的区别|`member`|
|渠道资料登记人|已有渠道资料和发行相关检查的辅助身份|`channelRegistrar`|
|另一客户|已有项目反馈和身份隔离检查的辅助身份|`customer`|

实际号码、机构编号和六组业务编号在本次启动后由 `node scripts/full-flow.cjs status` 显示。重启会改变编号；不要把本次截图中的编号硬编码在页面或测试中。后三种身份保留既有资料，本轮六组主流程主要使用前四种。

## 本侧与队友复跑方法

以下是给开发者的补充，用户不需要亲自执行。工作目录为仓库根目录。依赖沿用后端和工作台的锁文件；Flutter、浏览器、MySQL 8 和 FFmpeg 须已经安装。不得使用生产数据库配置，也不要把私有运行文件上传 Git。

1. 启动本机隔离 MySQL。设置 `JX_MYSQL_TEST_ENV_FILE` 指向专用测试配置；Windows 额外设置 `JX_TEST_FFMPEG` 为已有 ffmpeg.exe 的绝对路径。代码会拒绝不符合隔离要求的数据库配置。
2. 在单独终端运行 `node scripts/full-flow.cjs start --test-only`，看到 ready 后再打开页面。业务服务只监听 `127.0.0.1:3362`；受保护的测试控制服务为 `127.0.0.1:3363`。
3. 在网页工程用 `VITE_BACKEND_ORIGIN=http://127.0.0.1:3362` 启动 Vite：`node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5211 --strictPort`。
4. 在 App 工程运行 `flutter build web --no-pub --no-web-resources-cdn --dart-define=JX_ACCOUNT_API_URL=http://127.0.0.1:3362`，然后 `python -m http.server 8780 --bind 127.0.0.1 --directory build/web`。Windows 中文路径下若工具失败，可把工具和 App 目录临时映射到空闲盘符；不要覆盖已有映射。
5. 手动测试：先运行 `node scripts/full-flow.cjs status` 找到角色；页面点击“获取验证码”后，再运行 `node scripts/full-flow.cjs code payer` 读取该虚构角色的本地验证码。其他角色替换名称。客户选择机构身份，才会看到该机构的业务。
6. 自动页面测试：设置 `CHROME_PATH` 为已有 Chromium/Edge 的绝对路径，然后运行 `node scripts/full-flow-browser-check.mjs`。证据保存到 `docs/testing/evidence/20261005/`。脚本会确认报价并提出样片修改，因此再次完整运行前须停掉旧实例并新建资料。
7. 结束时运行 `node scripts/full-flow.cjs stop`。它只关闭经运行编号核对的当前测试实例，清理其自己创建的随机数据库、媒体文件和私有运行文件。确认文件 `.local/pr20-ui-runtime.json` 消失后，再关闭自己的页面预览和隔离数据库。不要用强杀代替正常清理。

测试控制服务不接受浏览器 Origin，要求随机凭证；它不会向页面暴露验证码读取权限。运行文件包含控制凭证，禁止复制到报告、Git 或安装包。公开证据只保存经过选择的账号、业务状态、请求路径和检查结果，不保存登录令牌。

## 怎样看待本轮结果

- 后端流程使用真实隔离 MySQL 和现有接口；短信、存储、支付传输使用替身。因此不等 OSS，也不能证明 OSS、真实支付、实名或电子签已经接通。
- 网页操作包括六组资料显示、确认报价、阅读样片和提交修改；App 的浏览器版本检查登录、身份详情受限、停止重试、恢复和退出。完整链条主要由接口连续执行，尚不是每一个业务步骤都已从手机页面点击完成。
- 本轮不重新开放公网、不发真实短信、不部署；昨天的短信登录包没有自动获得此次修复。新版安卓包和手机上的复测仍须单独完成。
- 从共同版本 `28662ab` 开始，本地整合仍待审的第21份 `419fa39`、第22份 `6536457`。当前完整入口为 `core/full-flow-acceptance-20261005`，仍在本地。原申请没有被代替、批准或合并。

实际数量、检查限制和后续顺序见[本轮任务记录](../tasks/records/CORE-full-flow-20261005.md)。

## 第二批：检查出错、重试和权限变化

主流程资料准备好后，可以单独运行 `node scripts/full-flow-risks-browser-check.mjs`。仍设置已有浏览器的 `CHROME_PATH`，只需启动上述3362/3363业务服务与5211网页预览，不依赖App网页构建。这一批会修改订单、退款和许可，必须使用新启动的资料，不能在前一轮已经操作过的资料上直接重复。

|怎样制造情况|应当看到什么|
|---|---|
|付款已创建，但丢弃本次回复|页面保留原操作，核对后用同一编号重试；只留一笔付款|
|付款查询超时|不误报到账、不允许取消有待核实付款的订单；恢复后只记一次收款|
|退款申请或执行已处理，但丢弃回复|恢复原请求；未批准不调用渠道；已批准重试只调用一次退款渠道|
|超额退款、反复核对退款|拒绝超额；多次核对仍只有实际金额，不重复累加|
|撤销审核员或机构成员的权限|旧登录令牌被拒绝，页面清空旧业务资料；恢复授权后可重新读取|
|成片已验收，尾款没付|私有最终文件仍不能取得；无关用户不能读取他人的样片|
|已看过样片，再暂停剧本许可|再读时被拒绝，页面移除旧播放器和“已读取”提示，旧验收状态不可沿用；历史订单和许可记录保留|

本批最后一项已发现并修复网页和App的旧内容残留。9组实际流程通过；App制作/付款/账号相关72项通过，包含新增409/503拒绝后的两项回归；网页9个模块174项通过，类型检查通过。最终异步保护调整后另复测制作17项和全部9组浏览器流程，不能重复相加。

证据在 `docs/testing/evidence/20261005/risks/`：`before-fix`为修复前失败，`results.json`与其余场景图为最终结果。App这里仍是自动控件测试，不是手机实测。本轮没有真实付款、退款、发短信或接通OSS。
