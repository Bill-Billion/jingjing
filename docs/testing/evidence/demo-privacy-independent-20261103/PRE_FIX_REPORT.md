## 原因与最小接法建议

前端 `src/business/references.ts:33–34` 只为 `FILE_ERASURE` 配了 `policy_rule_id` 来源。本人账号选项已在页面处理，**不需要重做本人账号选择**。

后端 `src/http/privacy-routes.js:10` 只有：

```text
GET /api/v1/privacy/requests/:request_id/file-options?kind=POLICY
```

`src/modules/privacy/execution.js:71–87` 仅允许删除/注销且涉及全部类别或原始素材，政策一律按 `FILE_ERASURE` 核验。它不能正确承担资料更正/账号关闭规则目录：只允许关闭账号的规则会被过滤，允许清素材却不允许关账号的规则反而可能被列入。因此这不仅是前端漏接已有正确接口。

建议后端按当前本人请求和明确动作返回受控执行规则摘要；校验本人归属、申请类型/范围、实际动作以及生效状态，复用现有对应动作的 `policy()` 核验，不公开全库规则。更正、关闭账号和素材清理分别查询。运营分类留存规则另按 `PRIVACY_HANDLE` 权限和具体请求/类别返回，提交时仍重查规则，不能把查询结果当批准。

前端补相应来源，显示规则依据和适用范围；不能以允许手填任意 UUID 来替代本人可理解的办理。双方接好后从新申请重跑，补原请求失败恢复、撤权、账号最终关闭、保留理由和独立结案。

既有 `scripts/pr39-six-finish-browser-check.mjs` 用网页办理核验时钟，但关闭账号的提出、审核、执行通过直接 `api()` 完成，所以不能引用其成功结果证明上述页面已可用。
