# 曝光权益逐单依据和兑现：隔离复测

关联 E2E-09 局部。共同基线 `b0ed887871ea07f8dcaf2c5e4258042a99d7b82c`、原接口 `0.31.33-rc.1`；本地候选接口 `0.31.34-rc.1`，数据库迁移仍为 `0209`。Android 模拟器、Chrome 和本机服务使用随机临时 MySQL、合成人物、文件和规则，不使用真实权益、收费或外部服务。`after-result.json` 记录受测代码和网页构建摘要；完成后测试库、服务和 Android 转发均清理。

修复前，Android 本人对权益 `d7f15a6e-0da0-4e44-af42-7f3f41cdbbf6` 的绑定可按原键恢复，网页独立运营岗位能读取该项，但排期表单“实际排期依据”没有选择项（`before-operator.png`）。后端要求材料属于履约主体且独立审核不能由权益持有人代办，原接口没有将履约方具体提交的材料提供给本单运营。`before-result.json` 的 `passed: true` 仅表示复现脚本按预期识别了这个阻断；随后的排期和完成由测试直接调用接口，不是页面成功。

候选增加履约主体查看承接摘要及逐单提交材料的入口；独立运营员按本权益和用途读取选项与核对材料。后端重新验证履约主体、操作岗位、材料归属和当前限制，读取文件的存储传输前后再次核权；材料受限时不列入选项，重复同键和重复提交同一材料不生成多份。旧排期／兑现接口及历史权益约定保留，不将提交依据写成已审核、已兑现。详细接口和权限需后端负责人实审。

修复后，同一合成权益 `fbc1f908-5f4a-4fdb-84df-4eee0cd9159c`：Android 绑定响应丢失后按原键恢复；网页履约方上传并提交排期依据，独立运营员读取该文件并提出排期 `f1b08e80-f1f9-44d9-99e2-7ff9e42b072c`，另一岗位独立审核，持有人在网页明确接受。仅在隔离数据库连接将时间推进 2 天再推进 9 天，分别核对生效及到期；履约方再提交完成依据，运营员读取后在网页记录实际兑现。此轮的履约方与持有人为同一合成账户，运营和独立审核为其他账户；时间推进、文件和兑现均为模拟，不代表实际七天曝光或正式奖励已发生。

隔离 API 专项另检查不同履约方／持有人身份、其他主体不可提交、非独立岗位不可读取、不同权益不自动共享材料、重复请求、旧版本、错误材料归属、限制与传输中新增限制；源码、日志和实际 HTTP 响应供复核。该项不是 151 条整体通过，实际甲方候选、全部失败分支和另一方审阅仍待完成。

`redemption-suite.log` 为权益模块 40 项通过；`contract-validation.log` 校验了 25 份实际隔离 HTTP 响应及协议样例，不代替权限实审。网页受影响业务检查 99 项、类型检查与构建通过。完整网页测试退出成功，但当前沙箱拒绝若干测试进程绑定无须使用的 Vite 热更新端口并输出 `EPERM`；这些日志不能当作远端 CI 已通过。最终服务器自动检查还会核对全局登记的接口版本，当前旧登记导致该检查失败，需由后端负责人组合时同步。
