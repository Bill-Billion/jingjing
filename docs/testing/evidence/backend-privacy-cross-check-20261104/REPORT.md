## 需求依据与实施补全

[28号材料《账号注销、数据删除与AI内容退出规则》](../../../sources/contracts-20261029/extracted/28.md)第1节原文：“清楚知道收集什么、为何收集、共享给谁；可限制处理范围、拒绝非必要授权。”

第2节原文：“存在未完成交易的，先完成结算或退款；属于交易依法须留存的记录，不因注销而立即删除。”

第4节原文：“多方关系：数字人涉及 MCN、共创多人或已参演剧目的，撤回须结合已签合同、第三方权益与已发行作品处理；平台协助出具下架与停用清单。”

**流程补全/修复**：已批准的内容限制应在所有返回同一私有文件的入口执行，不能只在通用文件下载入口生效；读存储期间可能有新的限制或撤权，因此返回前再核对。此为落实现有处理决定的实现补全，不新增自动删除条件、不新增业务禁令或保留期限。用于测试的保留规则是合成前提，不能作为甲方正式法律依据。

## 复现方法与同记录证据

所有新业务记录均通过本地真实HTTP办理；各轮使用新建随机MySQL库。合成账号、岗位、已审隐私政策和存储由夹具准备，没有把已限制状态直接写入数据库。

顺序为：本人创建商单或发行渠道并引用本人依据 → 本人提出隐私投诉 → 运营受理 → 运营提出具体限制方案 → 另一账号独立审查范围和保留事项 → 原运营人员执行 → 原业务下载入口读取同一文件。逆向分支沿同一文件解除限制、再次读取及验证文件内容一致。

## 修复与验证范围

仅修改两个业务文件，各补一处已有公共检查：

- `src/modules/gigs/settlement.js`：在原记录可读、文件确被引用且状态可用后检查资产内容限制。
- `src/modules/projects/checks.js`：在原归属、证据用途及状态校验后检查资产内容限制。该检查也用于参演/发行处理中的证据有效性核对。

原路由已有“读存储前、读完后再次核验”的结构，故无需修改路由或接口格式。权限检查仍在前，无关账号不会因查询受限文件而获得“是否存在内容限制”的额外信息。未增加数据库迁移，前端不需要变更请求参数。

新增可重复测试：`test/privacy-cross-module.integration.test.cjs`。真实隔离MySQL专项10组子检查通过；既有 `gigs.integration`、`projects.integration`、`participation.integration`、`privacy-execution.integration` 四文件回归共104项通过，见 [回归日志](regression.log)。局部差异检查通过。

本轮没有发现“商单或发行的证据文件可以从原始材料删除入口直接误删”：这些业务依据只允许证据用途，而个人原始文件删除只接受 `AVATAR_MATERIAL`。因此不能仅凭 `file-targets.js` 未列商单/发行表就声称已证明误删，也没有为了表面补齐扫描而扩大删除范围。真实新增形象引用会使已批删除方案在执行前返回 `PRIVACY_FILE_RETENTION_REVIEW_REQUIRED`，并保留可读原件及引用说明。
