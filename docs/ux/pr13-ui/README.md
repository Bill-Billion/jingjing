# 作者与作品资料：本批页面交付

本批让作者提交供给资料、保存每一版作品和权利证明，再由获准人员分别审核资格、权属与内容。App 和网页都接入第13份的真实接口，继续使用已选暖白 App、浅色深绿工作台风格。

本批从已合入第12份的`integration/e58c7fc`建立`ux/pr13-pages`，通过`1f6edd3`原样合并第13份后端`318f263`；前端功能提交`81a9727`按用户授权统一通过原[第13份申请](https://github.com/Bill-Billion/jingjing/pull/13)交付，目标分支`core/stage-4-works-evidence`。未修改后端源码、数据库迁移或接口文件。最新上传版本和自动检查结果以申请页为准；尚未合入共同版本或部署。

## 页面与使用顺序

|谁来办事|App|网页|
|---|---|---|
|当前个人或机构负责人|我的账号 → 作者与作品|供给申请、我的作品|
|作者资料|首次申请、补正、当前结果与历史申请|申请填写、详情、补正与历史修订|
|作品资料|原作草稿、上传正文与证明、权利关系、新修订与版本详情|作品列表、投稿表单、详情与新修订|
|作者操作|先保存草稿，再单独提交；撤回需填写理由|同上|
|获准审核人员|本批由网页办理审核|供给申请审核、权属审核、内容审核各有队列与详情|

审核入口不代表账号已获审核权；服务器核对真实授权和是否自审。机构普通成员不能管理供给申请或读取该机构私有作品。供给资料通过后才能创建、提交作品；新申请进入待审后，旧批准不能继续当作当前资格。

正文、整份作品权利证明、各作者／权利人／代理的证明分别保存。主体编号须来自真实身份，表单只在主动选择“使用当前身份”时填入；不会自动把作者或投稿人当作权利人。作品编号和上一版本从已读记录获得，不能任意改写。当前只开放原作，项目改稿等待真实项目许可接入。

每个新修订保存自己的材料和审核结果，不继承上一版批准；旧稿、旧意见和撤回说明保留。双审完成只表示两项审核完成，不表示已上架、售出、获得项目许可或发行权。

## 文件、错误和重试

选择真实文件，单份不超过8 MiB。只引用服务器确认可用的私有文件；下载重新核对权限，使用获准字节，不生成公开材料地址。App 增加现有平台所需的文件选择插件与 macOS 文件访问声明。

切换身份、退出登录或发现失权时清空私有资料，并丢弃迟到响应。写请求结果不明时保留原内容、原操作编号与版本；不盲目换编号重写。版本过期需重新读取和确认。操作成功后再次读取当前记录，同时更新详情、列表与历史中的同一记录。

### 现场导航问题与修复（2026-09-30，本地待交付）

用户现场点击“合同与规则”时发现“供给申请”和“我的作品”消失。原因是工作台、合同页和供给页各自维护菜单，合同页把供给两项合并成单一入口；App 也仍有旧版五入口、旧作品页和旧展示入口。这是当前 PR13 的导航问题，不应等 PR14–17 才修。

本地修复后，网页账号、合同、供给申请、我的作品、供给审核、作品审核共用六入口菜单，当前项保持高亮；App 根启动与登录后进入暖白五入口：首页、入戏、培育、成角、我的。账号、合同和作者作品使用返回式子页；旧地址映射到正确新版目的地或明确“暂未开放”，未知地址可返回新版首页。后续 PR14–17 的许可、订单、制作、商单等业务页面仍须逐批接入真实接口，不能把当前未开放页算作已完成。

网页六入口已在真实浏览器逐项点击，桌面与390px手机宽度均保留菜单和正确高亮；App 五入口、账号／合同／作者作品子页返回、登录回跳、旧`/my-works`及错误地址已在重建的 Flutter Web 预览中实点。证据：[网页结果](evidence/navigation-web.json) · [APP结果](evidence/navigation-app.json) · [网页合同页](evidence/web-contract-navigation.png) · [手机宽度网页](evidence/web-contract-navigation-mobile.png) · [APP新版“我的”](evidence/app-new-navigation.png)。新增 Vue 供给测试共19项、已有合同17项、Flutter相关74项及Dart静态分析通过；两端构建通过。此段修复只在本地分支和本机预览，PR13远端此前的检查不覆盖它；未修改PR14–17的提交。
