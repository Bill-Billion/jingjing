## 最终候选提交怎样回归

以下是可执行的收尾安排，未在本文件中标成已通过。各阶段独立测试记录可用于确定重点，最终共同候选提交仍需保留自己的操作证据。

1. Root 固定最终共同候选提交，核对实际 lock、运行时和前端产物；记录 App/Web 服务地址及后端环境。采用已有正常短信登录和隔离合成账号，明确个人、机构 OWNER、普通 MEMBER、独立运营和外部账号。已有同一提交且同一场景的有效结果可引用，新增合入或修复影响的场景补跑。
2. Experience 先查身份切换、会话失效、目录与详情失权。一个页面失去来源权限时，列表、详情、操作按钮和下载均停止；退出或切换账号/party 后，清空先前的私有正文、报告、音视频和 Blob/object URL，重新读取原 API。
3. 走一次订单到制作的完整流程：报价准确版本确认、付款未知结果保留原 key、脚本/样片反馈、旧版本失效、成片验收与尾款条件、私有预览和最终下载。保留未启用服务拒绝和普通 MEMBER/外部账号拒绝的实际结果。用合成沙箱事实，不写成真实支付或供应商已启用。
4. 走项目报名或邀请、SELECTED 后本人确认、PLAN/EDITION 准确 hash 与顺序会签、送审补件重提及历史。内部审核通过、外部待审和核实结果分别展示；参与方不能自行审核，原制作费与独立角色费分开核对。
5. 走财务约定和结算本人确认、本人份额投影、付款申请、独立凭据审核、已付/失败/退回。发行应收与银行实收分别展示；批准申请不能显示已付。付款或确认回复未知时核对原 key/body/version，不另发新款；合作方各入口只读自己的 SETTLEMENT 余额。
6. 走业务通知、四种留言目标、撤回/隐藏和运营审计。已读按 account+party，隐藏/撤回 body 为 null，独立运营不能隐藏本人留言。在 Web32 申请 CASH/SETTLEMENT/WORKLOAD 报告时保留真实队列等待、阻止、重试和成功状态；source 失权拒整份下载。核对 CSV 的 BOM、CRLF、期间/环境/口径、金额与公式安全，不把 JSON 快照 hash 当 CSV 字节 hash。
7. Root 汇总未测、失败、已修复和通过的场景，记录截图/实际网络结果/日志路径及材料 hash。只有对应负责人真正核验后，才整理 `frontend_journeys` 或 `peer_review` 的正式候选材料；此次文档整理不把示例清单改成 `VERIFIED`。

独立 App/Web 数据可避免双方消费同一版本。权限撤销、全局存储故障和 worker 开关由 Root 排定顺序，避免并发验证相互改变控制状态；每个受控场景结束后恢复，再核对原记录。安装包、设备和商店材料另由实际负责人补齐。

## 当前授权和未完成条件

当前授权限于本机隔离检查、现有前端联调和交接材料整理。未授权访问生产、部署、真实收费服务、安装新依赖或原生工具、原生 App 打包签名、提交商店或真机验收；也没有自动发布或恢复库解锁授权。复用已有 SQLite 原生模块进行后端测试，不构成 App 原生设备验收。

正式候选仍需准确版本的双方审阅、前端完整流程、真实设备、脱敏旧库映射、数据库与私有对象恢复、独立安全审阅、目标规模负载、值班联系方式、产品合同和供应商实际验证。已有隔离演练允许继续联调；是否正式发布由实际负责人根据齐备材料决定。
