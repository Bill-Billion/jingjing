## 三、首次部署（从零到可访问，供换机/灾备重建）

> 前提：Ubuntu 22/24、root、安全组与 ufw 放行 22/80/443（3000 不必对公网开放，见第九节）。

```bash
# 1) 运行时
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt-get install -y nodejs nginx
npm i -g pm2

# 2) 目录与代码（发布物由本地打包：排除 node_modules 的源码包 + uploads + .env）
mkdir -p /opt/jjsr && cd /opt/jjsr
# 用 SFTP 上传 jjsr_release.tar.gz 到 /root/deploy 后：
tar -xzf /root/deploy/jjsr_release.tar.gz -C /opt/jjsr
cd /opt/jjsr && npm i --omit=dev --no-audit --no-fund   # better-sqlite3 会在本机编译

# 3) 环境变量：上传 .env（含全部密钥，绝不入库）；首次启动自动建表/补列（db.js 幂等）
node --check app.js && node db.js            # 语法检查 + 预建表

# 4) PM2 拉起 + 开机自启
pm2 start app.js --name jjsr
pm2 save
pm2 startup systemd -u root --hp /root       # 按提示执行其输出的 systemctl enable 命令

# 5) Nginx 反代
# 写入 /etc/nginx/sites-available/jjsr（见第十节附录），软链到 sites-enabled，删 default
nginx -t && systemctl enable --now nginx && systemctl reload nginx

# 6) 防火墙（双层都要做）
ufw allow 22/tcp; ufw allow 80/tcp; ufw allow 443/tcp; ufw --force enable
# 阿里云轻量控制台防火墙同步放行 22/80/443

# 7) 日志轮转 + 定时备份/巡检（本轮已固化）
pm2 install pm2-logrotate
pm2 set pm2-logrotate:max_size 10M; pm2 set pm2-logrotate:retain 7; pm2 set pm2-logrotate:compress true
mkdir -p /opt/jjsr/ops /opt/jjsr/backups/db
# 上传 ops/ 三个脚本与 /etc/cron.d/jjsr-ops（见第二节），chmod +x ops/*.sh
pm2 save

# 8) 验收
curl http://127.0.0.1:3000/api/health            # 200 + version
curl http://127.0.0.1/api/health                 # 经 Nginx 200
bash /opt/jjsr/ops/healthcheck.sh                # RESULT: HEALTHY
node /opt/jjsr/ops/smoke_api.js                 # 全 PASS
```

## 四、日常更新发布流程（**强制：先备份、可回滚**）

> 本地工具：`work/deploy/ops/` 下 `r.js`（远程执行）、`up.js`（上传）、`get.js`（下载），连接信息在本机 `conn.json`（勿提交）。PowerShell 5.1 一律用 `;` 不用 `&&`；复杂远程操作写成 `.sh/.js` 用 `node r.js --file` 或上传后执行，避免多层引号；中文只用 Node/Edit/Write 处理。

1. **本地先绿**：改完 `node --check 改动文件`；涉及写库必跑 schema 审计；本地用临时 SQLite + 独立端口 + seed + 自签 JWT 走真实 HTTP 冒烟。
2. **远程备份（必做，带时间戳）**
   ```bash
   TS=$(date +%Y%m%d_%H%M%S); BD=/opt/jjsr/backup_v123_$TS
   mkdir -p $BD; cp -a /opt/jjsr/routes /opt/jjsr/services /opt/jjsr/app.js /opt/jjsr/config.js /opt/jjsr/db.js /opt/jjsr/.env $BD/ 2>/dev/null
   node /opt/jjsr/ops/backup_sqlite.js 7      # 同时再备一份数据库
   ```
3. **上传并字节比对**：SFTP 上传改动文件 → 远端 `md5sum` 与本地 `Get-FileHash -Algorithm MD5` 必须一致。
4. **语法检查 → 重启 → 验证**
   ```bash
   cd /opt/jjsr && node --check routes/xxx.js
   pm2 restart jjsr --update-env && pm2 save
   sleep 2; curl -s http://127.0.0.1:3000/api/health
   node ops/smoke_api.js                     # 回归全绿
   pm2 logs jjsr --lines 50 --nostream --err # 确认无新增错误
   ```
5. **公网复验**：本机 `node work/deploy/ops/pub_smoke.js`（走 Nginx 80）。
6. **清理**：删除远端/本地临时 `_` 前缀探测脚本；保留备份目录与 ops 永久脚本。

### 回滚（任意版本可退）
```bash
# 代码回滚（把备份目录覆盖回去）
cp -a /opt/jjsr/backup_v123_YYYYMMDD_HHMMSS/routes/ai.js /opt/jjsr/routes/ai.js   # 单文件示例
# 或整目录：cp -a /opt/jjsr/backup_v123_xxx/* /opt/jjsr/（注意不要覆盖 .env/库，除非有意）
cd /opt/jjsr && node --check app.js && pm2 restart jjsr --update-env && pm2 save
# 数据库回滚（谨慎，会丢失备份点之后的数据；业务低峰执行）
pm2 stop jjsr
cp /opt/jjsr/jingjingshangri.db /opt/jjsr/jingjingshangri.db.before_restore   # 先反向保护现场
cp /opt/jjsr/backups/db/jjsr-YYYYMMDD_HHMMSS.db /opt/jjsr/jingjingshangri.db
rm -f /opt/jjsr/jingjingshangri.db-wal /opt/jjsr/jingjingshangri.db-shm
pm2 start jjsr && curl -s http://127.0.0.1:3000/api/health
```

## 八、短信签名/模板过审后的精确回填步骤（定时任务之外的人工 SOP）

const set=(k,v)=>{const re=new RegExp("^"+k+"=.*$","m");
 t=re.test(t)?t.replace(re,k+"="+v):(t.endsWith("\n")?t:t+"\n")+k+"="+v+"\n";};

## 九、防火墙/安全组只读核查结论与建议（**未擅自改动，避免断连**）

现状（主机侧实测）：ufw active、默认 deny 入站，放行 22/80/443/3000（v4+v6）；云端轻量控制台防火墙按 09 记录同样放行 22/80/443/3000。
建议（按优先级，变更需选可连通时段并保留当前 SSH 会话）：
1. **关闭 3000 对公网暴露**：业务只经 Nginx 80，3000 仅本机需要。先在阿里云轻量控制台删除 3000 放行，再 `ufw delete allow 3000/tcp`；删完立刻用**新 SSH 会话**验证 22 仍可连、公网 80 仍 200。

3. 443 现在保留为空跑（无证书），等域名+HTTPS 时启用。
4. Nginx 建议加 `server_tokens off;` 与 gzip_types（含 application/json），属优化非必须。
5. 保持 ufw 默认 deny 入站；任何新增端口遵循"控制台 + ufw 双层都要配"的踩坑结论。

## 十一、容量与并发扩容建议（按"图片小、视频大"区分）

### 11.1 容量画像与测算
- 图片类（头像/海报/样片封面/文生图）：单张 0.1–1 MB；1 万张 ≈ 1–10 GB。
- 音频（TTS）：单条 50 字 ≈ 80–120 KB，极小。
- 视频类（Seedance 720p、15s 成片）：单条约 3–10 MB；**1 千条 ≈ 3–10 GB，1 万条 ≈ 30–100 GB**，是磁盘与带宽主头。
- 现状：系统盘 30G 用 5.2G(19%)，库 0.6 MB，uploads 7.2 MB → 图片/演示期单机盘足够；**一旦日产出视频上百条，单机盘将在 1–2 月内告急，必须先上 OSS**。
- 内存 1 GiB：Node 常驻约 60–90 MB，方舟/视频为**异步外部任务**（本地不渲染），内存压力主要来自 better-sqlite3 缓存与 PM2；当前可用约 420 MB、swap 未用，健康。

### 11.2 分阶段扩容路线
| 阶段 | 业务量画像 | 建议架构 |
|---|---|---|
| 现在（演示/MVO） | 日活几十、视频日产出 <20 条 | 维持单机：30G 盘 + SQLite + 本地 uploads；每日备份；pm2-logrotate 限日志 |
| 起步（日活数百、视频日产 20–200） | 单机盘/带宽吃紧 | ①素材先迁 OSS+CDN（最优先，解磁盘与下载带宽）②系统盘快照+库异地备份 ③升配到 2C2G |
| 增长（日活上千、并发下单/轮询明显） | SQLite 写锁、单 Node 瓶颈 | ①SQLite→云 MySQL（RDS，代码已预留 DB_CLIENT）②接 Redis（限流/会话/任务队列）③PM2 cluster 或多实例 + Nginx 负载 ④视频任务表+独立 worker 轮询，API 与 worker 分离 |
| 规模（多供给/高并发视频） | 上游配额/成本、可用性 | ①方舟提升 QPS/并发配额，多模型/多供应商兜底 ②视频成片全走 OSS，CDN 分发 ③至少 2 台应用 + 托管数据库 + 定时快照 ④接入成本告警 webhook（AI_DAILY_COST_CAP_FEN 已有熔断） |

### 11.3 运维参数建议
- SQLite 阶段：每日备份保留 7 天（已配），**每周下载一份到本机/异地**；WAL 若持续偏大，备份脚本已自动 checkpoint。
- 视频大文件：Nginx `client_max_body_size 50m` 仅覆盖图片/音频上传；视频素材走火山生成后回传 OSS，不建议让 APP 直传大视频到单机。
- 日志：pm2-logrotate 10M×7 + gzip；Nginx access log 量大时用 logrotate 同样按日压缩保留 14 天。
- 内存红线：healthcheck 已设 available<80MB 告警；触发后先看 PM2 内存与 swap，必要时 `pm2 restart jjsr`（无状态、秒级恢复）。
