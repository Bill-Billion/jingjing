### 2.2 联调链路与关键证据（J 系列断言）

1. **密钥对（J01）**：以子进程真实执行 `gen_alipay_rsa_keypair.js` 产出 PEM，再从 PEM 文件读回装配（等价真实「.env 回填」流程），验证 PKCS8/SPKI 头与单行公钥打印。
2. **配置装配（J02/J02b）**：`ALIPAY_ENABLED=true` + 测试 APPID/PID + 自生成密钥 → `status()` = enabled/configured/mode=public/sandbox=true；且 status 输出**不含任何 PEM/base64 密钥材料**。
3. **离线订单串（J03/J03b/J03c）**：`sdkExecute('alipay.trade.app.pay')` **不发起网络请求**生成订单串；用公钥按支付宝规则（剔除 sign、key 字典序、k=v& 拼接、RSA-SHA256）**独立复算验签通过**；`biz_content` 中 `total_amount=99.00` 来自服务端、`out_trade_no=pay_no`、`product_code=QUICK_MSECURITY_PAY`、`seller_id=PID`；`notify_url` 已签入（F1 修复后）。
4. **金额守卫（J04/J18a/J18b）**：0/负/小数分直接抛错；`99` 与 `99.00` 数值等价可入账，空值/乱值/0.01 一律拒绝（fail-closed）。
5. **鉴权与降级（J05/J06）**：未登录 401；未配置时 create 返回 `{configured:false,demo:true}` 且**不写 payments**。
6. **真实 SDK 验签（J09 系列）**：正确签名 `checkNotifySign(body,true)=true`；改内容沿用旧签名/坏签名 = false；「签名有效但内容被改」由后续金额对账兜底拒绝。
7. **HTTP 回调（J10~J13）**：坏签名/错 app_id/金额不符 → `fail` 且业务单保持 pending；合法回调 → `success`、业务单 paid、payments 回填 trade_no/notify_hash；**重放 2 次始终 success 且 paid 仅 1 条**。
8. **主动查单 trade.query（J14/J14b/J14c/J15）**：以受控桩模拟沙箱网关——`WAIT_BUYER_PAY` 不入账；`TRADE_SUCCESS` 且金额一致→补入账；再次查单幂等；网关抛错时接口仍 HTTP 200 返回本地 pending（异常被兜住）。
9. **分期与多业务（J16/J17/J17b）**：dream 席位 paid 并只累加一次项目进度（50000 分/人数 1）；样片意向金 9900（99.00）、制作款 490100（4901.00）**只认 config.sample**，回调后状态机 `draft→intent_escrow(step1)`、`script_finalized→producing(step5)`，与 `routes/samples.js` 状态机命名逐字一致。
10. **并发双击（J19a）**：两个 create 并发到达，均 200、payNo 一致、**仅 1 条 pending**（部分唯一索引 + 捕获约束复用兜底）。
11. **dream 防双加（J19b）**：席位已 paid 后再次 `markBusinessPaid`，项目 raised/client_count 不再变化。

## 三、三轮自审发现与修复（F1~F6，全部有测试覆盖）

走读范围：`services/alipay.js`、`routes/pay.js`、`app.js`、`db.js`、`middleware/auth.js`、`middleware/rateLimit.js`、`utils/settlement.js`、`routes/samples.js`、`services/paymentService.js`、官方 `alipay-sdk@4.14.0` 源码（sdkExecute/checkNotifySign/checkResponseSign 行为）。

| 编号 | 级别 | 问题 | 修复 |
|---|---|---|---|
| F1 | 功能健壮性 | `buildAppOrderString` 未把 `ALIPAY_NOTIFY_URL` 签入订单串，异步回调只能依赖开放平台后台默认 notify 配置，漏配则收不到回调 | sdkExecute 第二参带 `notifyUrl`（存在时），回调地址随订单签名下发，不再依赖后台默认值（J03c 覆盖） |
| F2 | 幂等/数据正确 | dream 分支 `projects.raised_amount/client_count` 累加不看 claims 是否真翻转；极端情况（旧单 closed 后重新支付成功）会双加 | 仅当 claims `pending→paid` 的 UPDATE `changes===1` 才累加项目（J19b 覆盖） |
| F3 | 健壮性 | 并发双击命中部分唯一索引 `idx_payments_one_pending` 时 INSERT 抛约束错→用户收到 500 | 捕获 UNIQUE/constraint 后回查 pending 单、以其 pay_no 重新离线签名并复用返回（J19a 覆盖） |
| F4 | 可观测/健壮 | 网关返回**无顶层 sign 的错误响应**时，SDK `validateSign:true` 会抛 Node 原生 TypeError（签名参数 undefined），错误形态不可识别 | `queryTrade/refund` 统一包装为 `code=ALIPAY_GATEWAY_ERROR`；路由维持 fail-closed（异常绝不入账，J15/J18 覆盖） |
| F5 | 严谨性 | SDK 客户端缓存签名用「密钥长度」，同长度换密钥会复用旧 client | 改用密钥内容 SHA256 指纹（只留内存哈希，不落日志） |
| F6 | 兼容/fail-closed | notify/查单金额用字符串严格相等，`99` 与 `99.00` 会被误判不等 | 新增 `yuanEqual` 数值比较，NaN/缺失一律不等（J11 仍拒 0.01；J18a/J18b 覆盖） |

同时复核**未发现问题**的安全面：SQL 表名来自固定 BIZ 映射、值全部参数化（无注入）；create/status 强制登录且服务端二次校验订单归属；金额只来自服务端订单行/config，前端金额字段只用于「比对并拒绝」；notify 无登录但有 RSA2 验签 + app_id + 金额三重闸；无 git 仓库、无 certs 落盘，密钥无入库路径；全局限流 120/分/IP，支付宝重试节奏远低于此。
