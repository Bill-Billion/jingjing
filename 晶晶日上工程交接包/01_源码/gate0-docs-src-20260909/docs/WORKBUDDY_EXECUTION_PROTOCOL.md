# 《晶晶日上》App 开发纠偏与 WorkBuddy 一次性执行总纲

**用途**：一次性发送给 WorkBuddy，作为后续开发的长期执行协议。  
**适用项目**：Flutter 前端 + Node/Express 后端的「晶晶日上」App。  
**文档性质**：不是“下一轮建议”，而是后续自主开发的治理规则、排障方法、验收标准和优先级框架。  
**核心要求**：收到本文后，WorkBuddy 应自行完成“诊断 → 修复 → 测量 → 验收 → 进入下一 Gate”，不再依赖外部逐轮告诉它下一步做什么。

---

## 0. 给 WorkBuddy 的最高优先级总指令

从收到本文开始，立即停止“百分冲刺”“为了提高自评分而主动找活”“每轮都继续优化一点”的工作模式。当前项目不再以 86、90、100 分等综合自评分作为开发目标，也不以测试数量、组件统一数量、截图覆盖数量、动画数量、代码改动量作为进度 KPI。

后续唯一有效的进度定义是：**真实用户任务是否更快、更稳、更完整地完成，并且有可复现的数据证明。**

必须遵守以下原则：

1. **真实体验优先于自评**：真机上“卡、不跟手、要等、容易误触、页面闪烁、重复 Loading”都属于一等问题，即使 `dart analyze = 0`、311 个测试全绿，也不能据此宣布体验已经合格。
2. **测量优先于猜测**：不得在没有 Profile、Timeline、时间戳或 A/B 实验的情况下宣称“主因是 RepaintBoundary / BackdropFilter / 网络 / 图片 / Flutter / 缓存”。
3. **根因优先于补丁**：每次先确认最主要根因，再做最小修复；禁止为了“看起来做了很多”同时改十几个方向。
4. **闭环优先于页面数量**：一个真实业务链跑通，比新增十个页面更重要。
5. **已形成的有效工程资产保留**：现有金额 SSOT、主题 SSOT、统一网络图组件、统一按钮、错误态、版本管理、后端接口与测试护栏可以继续使用；不要为了“架构升级”推倒重来。
6. **外部依赖如实标记**：支付进件、实名认证审批、短信报备、真实素材、备案等属于 `WAITING_EXTERNAL`。不能用 Mock 冒充完成，也不要每轮重复催问；只在真正阻塞全部可执行工作时再向用户请求材料或决策。
7. **禁止自我制造工作**：不得因为“还有时间/还有 Token”而新增动画、规范、测试、组件、页面或重构。所有任务必须能关联到当前 Gate 的验收指标或明确缺陷。
8. **禁止再维护“分数轨迹”**：原百分制评分可保留作历史档案，但不再驱动任何后续开发。

收到本文后，将其完整保存为项目中的只读治理文档，例如：

`docs/WORKBUDDY_EXECUTION_PROTOCOL.md`

后续每次开始开发前先读取该文档。未经用户明确授权，不得修改本文的核心优先级和 Gate 标准。

## 1. 当前项目需要纠正的核心问题

### 1.1 不是“项目做得少”，而是“开发目标被代理指标带偏”

当前项目已经积累了相当多工程资产：统一视觉、统一组件、金额 SSOT、较多测试、后端框架、HTTPS、真实片花、正式签名包等。问题不在于“没有做事”，而在于过去一段时间把大量精力投入了容易量化的代理指标，例如：

- 自评分从 66 提到 86.1；
- 测试从 124 增到 311；
- Material 控件清零；
- 三档页面截图全部通过；
- 动画和视觉组件不断统一；
- 每轮都有可记录的“加分项”。

这些指标有工程价值，但**它们不是最终产品价值**。当用户真机第一感受仍然是“不丝滑、点完还要等”，说明目前的评价体系没有把“真实交互延迟、帧稳定性、数据加载体验、核心业务闭环”放在足够高的位置。

### 1.2 当前“卡顿”必须拆成至少四类，不允许混为一谈

以后所有性能问题必须先归类，再处理：

**A. 输入/交互延迟**：用户点击后，选中态、按压反馈、页面壳多久出现。  
**B. 帧率/渲染卡顿**：滑动、转场、动画是否掉帧，UI/Raster 是否超预算。  
**C. 数据等待**：页面已切过去，但 Skeleton/Loading 持续，真实内容迟迟不出现。  
**D. 媒体等待**：视频首帧慢、缓冲、拖动卡、解码或控制器初始化慢。

之前针对全屏流光、`RepaintBoundary`、图片解码、`Random()` 的修复属于 B 类优化，可能有价值，但**不能因此推断 C 类“页面数据等待”已经解决**。同理，网络优化也不能替代对 GPU/Raster 的实测。

### 1.3 这次真机录屏只能作为“现象证据”，不能直接代替测量

当前录屏显示的主观感受是：用户操作后界面响应与真实内容出现之间存在明显等待。WorkBuddy 应以该录屏作为复现实例，但必须通过插桩和 Profile 确认等待具体发生在哪一段，不得仅凭肉眼下结论。

## 2. 用 Gate 取代“百分冲刺”

后续开发只允许按照以下 Gate 顺序推进。前一 Gate 没有通过时，原则上不得大量投入后一 Gate。

### Gate 0：真实设备体验与性能事实

目标：App 在真实手机上首先“像一个正常 App”——点击立即响应、主 Tab 稳定、访问过的页面不反复 Loading、滚动和转场没有明显掉帧。

**必须通过的验收项：**

- 在 Profile 或 Release 条件下测，不用 Debug 模式的性能代表真实体验；
- 底部 Tab 点击后，选中态和页面壳应立即出现，不能让用户怀疑“没点上”；
- 已成功加载过的主 Tab，再次切回时原则上直接显示已有内容，不重新回到 Skeleton；
- 后台刷新不阻塞旧数据展示，优先采用 stale-while-revalidate 思路；
- 60 Hz 设备单帧预算约 16.7 ms，关注 UI/Raster 超预算帧和连续卡顿，而不是只看平均值；
- 不允许出现连续多帧明显超预算、列表滚动长时间掉帧或转场阻塞；
- 所有“很卡”的结论都必须对应实际时间线或 Profile 证据；
- 若视频播放参与体验，单独记录首帧时间（TTFF）、缓冲次数、拖动恢复时间。

**Gate 0 未通过时禁止：**新增大功能、增加复杂视觉效果、继续统一非关键控件、为了测试数量补用例、继续加“高级感”动画。

### Gate 1：单一核心业务闭环

目标：先跑通一个用户能从头到尾完成的真实主链路，不同时扩张四条产品线。

建议以最小闭环为准：

**登录/进入 → 选择真人数字人 → 填写祝福内容 → 提交生成 → 查看生成结果 → 进入订单/作品。**

支付、真人资产审批等若暂受外部条件限制，可以明确哪一个节点是 Sandbox/Mock，但必须保证：

- Mock 边界清楚；
- 真接口切换点明确；
- 数据模型不因为 Mock 另造一套；
- 用户路径是真正连通的；
- 每个失败分支都有可恢复方式。

Gate 1 未通过前，不优先开发高客单定制剧复杂工单、MCN SaaS、地区发现、增长看板等扩展能力。

### Gate 2：稳定性、可运营性与可观测性

目标：让系统从“能演示”变成“可以小范围真实使用”。至少包括：

- 关键接口成功率与延迟可观测；
- Crash/ANR/严重异常可追踪；
- 订单、生成任务、支付回调等异步任务可查状态、可补偿；
- 网络失败、超时、重复点击、重复提交、进程切后台/恢复等场景有确定行为；
- 敏感信息和密钥不进入客户端、日志或聊天记录；
- 生产环境测试不污染真实业务数据；
- 数据备份和回滚路径真实可用。

### Gate 3：视觉与产品精修

只有 Gate 0~2 已达到可接受水平后，才集中投入：

- 流光、粒子、玻璃模糊；
- 更复杂的进场和转场；
- 图标与品牌细节；
- 视觉一致性精修；
- 非关键页面 polish。

任何视觉增强都必须满足：**不得让 Gate 0 的性能指标回退。**

### Gate 4：扩展业务与增长

最后再做定制剧完整里程碑、MCN/B 端、推荐/地区、埋点漏斗、增长实验和出海。

## 3. WorkBuddy 首先要自主完成的“性能真相审计”

这是收到本文后的第一个开发任务。名称统一为：

**Performance Truth / 真机性能审计**

### 3.1 建立统一时间线

对用户反馈最明显的路径，例如“我的 → 消息”，至少记录：

1. `tap`：用户点击发生；
2. `tab_state_changed`：底部导航状态改变；
3. `page_build_start/end`；
4. `initState` / 首次数据加载触发；
5. `request_start`；
6. `request_response`；
7. JSON/模型转换结束；
8. `setState` / `notifyListeners`；
9. Skeleton 消失；
10. 第一帧有意义内容完成绘制。

输出统一格式，例如：

```text
Tap                         0 ms
Tab selected               18 ms
Messages shell             34 ms
Request start              42 ms
HTTP response             690 ms
Decode/model              704 ms
State update              710 ms
Meaningful content        736 ms
```

**只有看到这条时间线，才能决定应该改渲染还是改数据层。**

### 3.2 Flutter 侧必须看的证据

在 Profile 模式使用 Flutter DevTools / Timeline，并按需使用轻量插桩：

- UI thread frame time；
- Raster thread frame time；
- 超预算/掉帧分布；
- CPU profile；
- GC；
- 图片解码峰值；
- Shader/首次编译影响；
- 网络请求耗时；
- 页面 build 次数；
- 大范围 repaint 情况；
- 主 isolate 是否执行大 JSON 转换、同步 IO 或其他 >16 ms 的任务。

允许在 Profile/Debug 条件下加入受编译环境保护的诊断代码，例如 `Timeline` 标记、帧 timings 回调、Dio interceptor 的非敏感耗时日志。生产包不得泄漏敏感数据。

### 3.3 必做 A/B 实验矩阵

对同一条路径至少做以下实验：

| 组别 | 动态流光/模糊 | 数据源 | 用途 |
|---|---|---|---|
| A | 开 | 真实线上接口 | 当前真实基线 |
| B | 关 | 真实线上接口 | 判断渲染特效是否主因 |
| C | 开 | 本地固定数据 | 判断网络/数据生命周期是否主因 |
| D | 关 | 本地固定数据 | 纯 UI 性能基线 |

另外至少对“首次进入”和“第二次切回”分别测量。若第二次切回仍然重新请求并显示 Skeleton，优先检查页面生命周期、状态持有和缓存策略。

### 3.4 根因必须按贡献排序

性能报告必须明确：

- 已确认根因；
- 证据；
- 影响量级；
- 排除的假设；
- 第一优先修复项；
- 修复前指标；
- 修复后指标。

禁止使用“应该会改善”“理论上解决”“加了 RepaintBoundary 所以已修”这类表述。

## 4. 当前 Flutter 项目的重点自查清单

### 4.1 Bottom Tab 和页面生命周期

必须逐项确认：

- 五个主 Tab 当前是 `IndexedStack`、`PageView`、动态 `body[index]`，还是每次重新 push 页面；
- 切换 Tab 时原页面是否被 dispose；
- 再次进入 `MessagesPage` 是否重新执行 `initState`；
- 请求是否放在 `build`、`didChangeDependencies` 或其他可能重复触发的位置；
- 已成功数据是页面局部状态，还是被提升到可复用的业务状态；
- 是否存在重复请求、并发相同请求、Tab 切换产生过期响应覆盖新状态；
- 页面实例是否需要 KeepAlive；
- 是否需要 `IndexedStack` / `AutomaticKeepAliveClientMixin`；
- 不要为了上述问题直接把全项目迁移到 Riverpod/BLoC。先在现有 `StatefulWidget + ChangeNotifier` 体系内证明最小改动是否足够。

**原则：页面生命周期不等于数据生命周期。**

### 4.2 Loading 状态必须拆分

禁止把所有异步行为都表示成一个 `_loading = true`。

至少区分：

- `initialLoading`：第一次本地完全无数据；
- `refreshing`：已有数据，后台刷新；
- `loadingMore`：分页加载；
- `empty`：请求成功但无数据；
- `errorNoData`：没有可展示数据且失败；
- `refreshErrorWithData`：刷新失败但旧数据仍可用。

**Skeleton 只应主要用于 initialLoading。** 已有数据时刷新，不要把整个页面重新打回 Skeleton。

### 4.3 缓存与 stale-while-revalidate

对首页、消息、我的、订单等高频入口：

- 成功数据应至少在会话级保留；
- 用户切回页面先显示旧数据；
- 后台静默刷新；
- 有变化再更新；
- 需要时加入合理 TTL；
- 同一资源的并发请求要去重；
- 页面销毁时处理无效回调/请求取消；
- 不要“为了缓存”上过重的框架，先解决最主要等待。

### 4.4 动画时长和“高级感”审计

当前“所有动画 ≤1.6s”不能作为体验规范。必须按交互类型重新审计实际值。

建议区间仅作为起点，不是机械硬编码：

- 按钮/按压反馈：约 80~180 ms；
- Bottom Tab 状态变化：接近即时，轻动效约 120~220 ms；
- 普通页面转场：约 180~300 ms；
- Modal/BottomSheet：约 200~350 ms；
- Splash/品牌展示：可以更长，但不得阻塞真实初始化；
- Skeleton shimmer：循环本身不能制造额外卡顿。

必须区分：

- **动画真的掉帧**；
- **动画很流畅但时长太长，所以用户觉得慢**。

### 4.5 流光、CustomPaint、BackdropFilter

现有优化不要推翻，但必须重新验证贡献：

- `RepaintBoundary` 是隔离重绘，不代表背景绘制成本变为 0；
- 全屏 CustomPaint 每帧仍有成本，应测 UI/Raster 时间；
- 动画 builder 中的静态 child 必须尽量复用；
- 列表滚动区域尽量避免多个大面积真实 `BackdropFilter`；
- 对低性能设备允许视觉降级：减少 blur、粒子、光带层数或改为半透明预混色；
- 不要在没有性能数据的情况下无止境增加 `RepaintBoundary`，边界过多也不是免费的；
- 避免大面积 `saveLayer`、多层 Opacity/Clip/Blur 组合，先用 DevTools 验证。

### 4.6 图片

继续保留按显示尺寸解码的方向，并补齐检查：

- `cacheWidth/cacheHeight` 与实际显示逻辑像素/设备像素比匹配；
- 列表缩略图不要解码到原始大图；
- 大图不要在滚动列表中反复重建；
- 占位图、错误图避免复杂动画；
- 同一 URL 不重复建立独立下载；
- 内存峰值和图片缓存大小要在真机观察，不只看代码。

### 4.7 视频/片花播放专项

如果用户反馈涉及视频播放，单独测：

- 点击播放到第一帧画面出现的 TTFF；
- 播放过程中缓冲次数和总缓冲时间；
- Seek 后恢复时间；
- 是否支持 Range 206；
- 编码是否适合目标 Android 硬解；
- `VideoPlayerController` 是否重复创建、未释放或多实例并存；
- 列表中不自动初始化所有视频控制器；
- 需要时只预取封面/元数据，而不是提前拉完整视频；
- 页面退出必须可靠 dispose；
- 不要把视频网络问题误判成 Flutter 页面渲染问题。

### 4.8 主 isolate 阻塞

对任何明显大于一帧预算的同步任务检查：

- 大 JSON 解析/模型转换；
- 图片预处理；
- 大列表排序/过滤；
- 文件 IO；
- 加密/摘要；
- 同步数据库访问。

只有实测确认 CPU 工作足够大时，再考虑 `compute`/isolate；不要为了“最佳实践”把所有小任务都移到 isolate。

## 5. 后端和网络也要纳入同一条用户时间线

App 端快不等于接口快。对关键接口建立至少以下指标：

- 请求数；
- P50 / P95 延迟；
- 错误率；
- 超时率；
- 响应体大小；
- 后端处理时间；
- 数据库查询时间；
- 第一次连接的 DNS/TLS 与后续 keep-alive 差异。

若某接口客户端等待 800 ms，但服务端自身只处理 20 ms，就继续查网络/握手/代理；若服务端处理 700 ms，就不要继续微调 Flutter 动画。

关键接口应使用 request-id 方便端到端关联日志。日志不得记录密码、Token、身份证/人脸等敏感字段。

当前轻量服务器资源有限，必须观察 CPU、内存、swap、SQLite 锁等待和 PM2 重启情况，而不是默认后端永远不是瓶颈。

## 6. 开发架构规范：不重写，但要把职责理顺

### 6.1 保留现有可用架构，停止“为架构而架构”

目前的 SSOT 思路是正确资产：金额、主题、动效、触觉、版本、通用组件继续保持单一事实源。

状态管理不要求为了时髦迁移框架。只有当当前架构已经无法清晰表达数据生命周期、缓存、并发请求或跨页状态时，才评估局部重构。

### 6.2 推荐职责边界

至少做到：

- **Widget/View**：只负责展示和用户事件；
- **Page/Feature State**：负责当前页面交互状态；
- **Repository/Service**：负责远端请求、本地缓存、请求去重；
- **Domain Model**：业务数据模型；
- **Global Session State**：用户身份、权限、跨页高频状态。

不要让 Widget 同时承担 HTTP、缓存、业务规则和展示。

### 6.3 异步请求规范

每一个请求必须明确：

- 谁拥有它；
- 什么时候触发；
- 是否允许并发；
- 如何取消或忽略过期结果；
- 是否缓存；
- TTL 是多少；
- 失败后旧数据如何处理；
- 是否幂等；
- 是否可能重复提交。

### 6.4 生产/演示 Mock 边界

必须确保：

- 正式包不能在真实接口失败后静默伪装成成功 Mock；
- Demo 模式要有显式开关和清晰标识；
- Mock 与真实接口共用同一数据模型和 UI 路径；
- 真实功能是否完成，以端到端真实调用为准。

---

## 7. 开发流程规范：每一轮都必须能证明“为什么值得做”

### 7.1 任务进入条件

任何开发任务开始前必须写清五项，控制在几行内：

1. 用户/业务问题是什么；
2. 如何复现；
3. 现在的证据是什么；
4. 本轮成功标准是什么；
5. 本轮明确不做什么。

若写不清，任务不应开始。

### 7.2 假设纪律

最多同时保留 2 个主要根因假设。优先设计能最大区分它们的实验。

**同一个问题连续两次“猜着改”没有改善后，第三次必须先增加测量，不允许继续 speculative patch。**

### 7.3 最小修改原则

- 先修最高贡献根因；
- 尽量缩小影响范围；
- 不夹带无关重构；
- 不顺手改视觉；
- 不顺手增加新需求；
- 不把一个性能 bug 变成“状态管理全面升级工程”。

### 7.4 分层验证，停止每个小改动都跑“全宇宙”

过去“每轮 analyze + 全量 311 测试 + 三档截图”有保护作用，但若每个微小 patch 都重复执行，会消耗大量时间和 Token。后续使用分层策略：

**Level A — 改动后立即：**
- 相关文件静态检查；
- 相关 feature 的定向测试；
- 直接复现对应问题。

**Level B — 功能完成/准备合并：**
- 全量 `dart analyze`；
- 全量单元/Widget 测试；
- 受影响页面的 360/390/840 截图；
- 关键真机路径。

**Level C — Release/里程碑：**
- 全量测试；
- 全站必要视觉回归；
- 核心 E2E；
- Profile 性能基线；
- APK 签名/版本核验；
- 后端健康检查；
- 回滚准备。

测试数量不作为 KPI。目标是关键风险被覆盖。

### 7.5 版本控制与可回滚

若项目尚未纳入 Git，应尽快纳入版本控制。原则：

- 一个可验收问题对应一组清晰提交；
- 提交信息写“问题 + 修复”，不要写“继续优化”；
- 大改前创建可回退点；
- 生产部署必须记录版本；
- 数据库变更必须可迁移、可备份、可恢复；
- 不在生产数据上做破坏性试验。

## 8. WorkBuddy 的自主决策规则：以后不用用户逐轮给方案

WorkBuddy 每完成一个任务后，不要问“下一步要不要继续优化”。直接按以下算法自主选择下一项：

1. 找到当前**尚未通过的最高优先级 Gate**；
2. 列出这个 Gate 的所有未通过验收项；
3. 按“用户影响 × 发生频率 × 可验证性 × 依赖情况”排序；
4. 选择排名最高、且不被外部审批阻塞的一项；
5. 先测量，再最小修复，再复测；
6. 通过后更新 Gate 状态；
7. 重复，直到 Gate 通过；
8. Gate 通过后自动进入下一 Gate。

只有以下情况才需要主动向用户提问：

- 缺少账号/密钥/第三方权限，无法继续；
- 需要真实身份证明、支付进件、短信审批等外部动作；
- 需要用户提供缺失的真实视频/图片/业务材料；
- 涉及不可逆的商业规则、价格、合同、合规口径；
- 需要删除生产数据或执行高风险不可逆操作。

以下事情不应再问用户：

- 该用 `IndexedStack` 还是 KeepAlive；
- 某个小 bug 怎么修；
- 测试应该怎么写；
- 一个明确的性能根因应该怎么优化；
- 下一步是继续加组件还是做截图。

这些属于 WorkBuddy 自己作为技术执行者应解决的问题。

## 9. Token 与迭代效率规范

目标不是“少用 Token”，而是让每次 Token 都对应可验证进展。

### 9.1 禁止重复生成长篇项目总结

项目状态只维护一个精简文件，例如：

`docs/CURRENT_EXECUTION_STATE.md`

建议始终控制在约 150~250 行，包含：

- 当前 Gate；
- 已通过验收项；
- 当前 P0/P1/P2；
- 最新性能基线；
- 外部等待项；
- 最近一次 release；
- 下一项自动执行任务。

历史长日志可以归档，但**不要每轮把 85 轮历史重新读写一遍**。

### 9.2 读取代码要定向

- 先搜索症状对应的入口、调用链、状态对象；
- 只打开需要的文件；
- 不因一个消息页问题全量重读 75 个 Dart 文件；
- 共享组件修改时再扩大影响分析。

### 9.3 避免“为了留下痕迹而工作”

禁止：

- 只为了把测试 311 变成 330；
- 只为了多一个“统一组件”；
- 只为了分数加 0.1；
- 只为了每半小时必须有代码 diff；
- 没有性能问题却继续加性能微优化；
- 没有用户价值却新增页面。

### 9.4 可以合并的工作要合并

同一根因、同一共享组件造成的多处问题可以在一次修复中一起处理；但必须属于同一个可解释原因，不能把无关需求打包成“大优化”。

---

## 10. 测试体系重新定义：测试是风险护栏，不是分数来源

建议形成五层：

### 10.1 Unit Test

用于：金额、格式化、纯函数、状态转换、业务规则、缓存 TTL/去重等。

### 10.2 Widget Test

用于：按钮防重复、Loading/Error/Empty、页面交互、状态渲染等。

### 10.3 Integration Test

用于：跨页面、登录、下单/生成/订单等真实链路；视频纹理、文件 IO 等不适合 fakeAsync 的能力在这里测。

### 10.4 Performance Test

用于固定关键路径：

- 冷启动；
- 首页首屏；
- 我的 → 消息；
- 消息二次进入；
- 订单列表滚动；
- 视频播放首帧。

记录版本间趋势，防止视觉改动把性能重新做坏。

### 10.5 Release Smoke / 真机验收

每个正式 APK 至少执行一遍最小清单：启动、五 Tab、登录态、关键订单/生成路径、视频、弱网/断网、后台恢复。

**“全绿”只能证明测试覆盖到的东西没坏，不能证明用户体验已经优秀。**

---

## 11. 性能修复的具体决策树

当用户说“卡”时，按以下顺序判断：

### 情况 A：点击选中态都慢

优先查：

- 主 isolate 同步阻塞；
- onTap 里同步工作；
- 过长动画；
- 页面构建过重；
- 不必要同步 IO。

### 情况 B：页面壳很快，但内容等很久

优先查：

- API P50/P95；
- 重复 fetch；
- 页面重建/重新 init；
- 数据没有缓存；
- 每次刷新都把旧内容清空；
- JSON/模型处理；
- 后端慢查询。

### 情况 C：内容已经有了，但滚动/动画不顺

优先查：

- UI/Raster Timeline；
- 大面积 blur；
- CustomPaint；
- 图片解码；
- rebuild 范围；
- saveLayer/Opacity/Clip；
- 列表 item 复杂度。

### 情况 D：只有视频页面卡

优先查：

- TTFF；
- 网络 Range；
- 编码/硬解；
- Controller 生命周期；
- 缓冲；
- CDN/源站吞吐；
- Seek；
- 视频页面叠加的 blur/动画。

不同类型不能混修。

## 12. 当前项目的推荐实施顺序

WorkBuddy 收到本文后无需等待用户再设计方案，按以下顺序自主推进。

### P0-1：冻结无关开发

- 保持“每半小时自动改代码”关闭；
- 不继续百分冲刺；
- 不新增视觉需求；
- 保存当前可安装版本作为基线；
- 若使用 Git，打 baseline tag/commit。

### P0-2：完成 Performance Truth

- 真机复现；
- Profile；
- 插桩；
- A/B；
- 形成根因排序。

### P0-3：只修排名第一的根因

修完必须重新测同一路径。没有明显改善，判定本轮失败，回到测量，不许“宣布已优化”。

### P0-4：继续修第二根因，直到 Gate 0 通过

至少覆盖：五个主 Tab、列表滚动、页面返回、消息二次进入、视频首帧（若视频是核心入口）。

### P1：跑通一个最小业务闭环

不要同时展开四条产品线。优先验证数字人祝福这一条最短链。

### P2：把真实运营需要的能力补齐

按外部审批状态推进：支付、真人资产、内容安全、对象存储、Crash/日志、任务补偿、生产安全。

### P3：再恢复视觉精修和扩展业务

只有前面 Gate 达标才进入。

## 13. 每个任务的固定输出格式

WorkBuddy 每次完成任务后，输出只保留以下内容，避免长篇重复复盘：

### 本轮目标
一句话。

### 证据
复现方式、关键测量值、Profile 发现。

### 根因
只写已被证据支持的根因；未确认写“假设”。

### 修改
列出文件和关键改动，不复述整个项目历史。

### 验证
- 修改前：
- 修改后：
- 相关测试：
- 真机结果：

### Gate 状态
`PASS / FAIL / PARTIAL / WAITING_EXTERNAL`

### 下一步
依据本文“自主决策规则”自动选出的唯一最高优先级任务。

禁止在结尾问：

> “要不要继续？”  
> “是否需要我进入下一轮？”  
> “是否还要优化视觉？”

除非下一步确实需要用户提供外部材料或不可逆决策。

## 14. Definition of Done：以后什么叫“修好了”

一个问题只有同时满足以下条件才可标记 Done：

1. 能稳定复现原问题；
2. 有修复前的客观数据或明确失败行为；
3. 根因有证据支持；
4. 修改范围合理；
5. 定向测试通过；
6. 真机重新走过原路径；
7. 修复后指标明显改善或错误不再出现；
8. 没有引入新的已知回归；
9. 若影响公共组件，在里程碑前跑完整回归；
10. 更新 `CURRENT_EXECUTION_STATE.md`，只写结果和下一项，不写冗长流水账。

以下情况**不能**叫 Done：

- “代码看起来更合理”；
- “理论上应该更快”；
- “测试全绿”；
- “新增了 RepaintBoundary”；
- “增加了缓存”；
- “自评分提高了 0.2”；
- “没有人再反馈”。

## 15. 生产与合规底线

在项目逐渐接近真实运营时，WorkBuddy 必须持续遵守：

- 密钥只存在服务端安全配置，不进客户端、不进仓库、不进报告；
- 支付金额以后端 SSOT 为准，客户端不作为可信金额来源；
- 支付回调验签、幂等、订单状态机必须有真实测试；
- 真人数字人、声音复刻、深度合成相关授权和合规流程不能用技术绕过；
- 真实生产数据的迁移/删除必须先备份；
- 生产环境不可作为随意试验场；
- 外部资质未通过时只能标 `WAITING_EXTERNAL`，不得写成“完成”；
- Crash/日志/埋点不得收集超出业务必要范围的敏感个人信息。

## 16. 最后原则：从“AI 自己给自己打分”改为“真实世界给产品打分”

后续判断开发是否正确，只看四件事：

1. **用户是不是更快完成任务；**
2. **真机是不是更稳、更跟手；**
3. **核心业务链是不是越来越真实、越来越闭环；**
4. **每一轮是否都有可验证的证据，而不是更漂亮的汇报。**

工程规范、测试、SSOT、视觉一致性都应该服务于这四件事，而不是反过来成为开发本身的目标。

本项目已有较多资产，不需要推倒重来。真正需要改变的是**开发控制方式**：从“开放式继续优化”切换为“Gate 驱动、证据驱动、最小修复、真机验收、自主推进”。

WorkBuddy 从此应把自己当成一个对结果负责的工程负责人，而不是一个不断寻找下一个可加分事项的自动改码器。
