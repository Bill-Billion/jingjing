# Gate 0 真机性能采集指引（给用户 / 执行 AI 共用）

> 目的：拿到"点击 → 页面响应 → 网络 → 首帧"的真实时间线，定位 APP"卡"到底卡在哪一段。
> 原则：只用 Profile/Release 包在真机测，不用 Debug、不用模拟器代表体验；先测量、再按贡献只修第一根因。
> 工程里的埋点 `[PERF ...]` 在正式 release 包中完全不运行（零开销），只在 profile/debug 采集包输出。

## 一、最简单：USB 连机，我来自动抓（推荐）

你只需要做 3 步：

1. 手机【设置 → 关于手机 → 连续点 7 次"版本号"】打开开发者选项；进【开发者选项】打开 **USB 调试**。
2. 用数据线连电脑，手机弹窗点 **允许/一律允许本机调试**。
3. 跟我说一声"连好了"。

剩下我来做（你不用操作）：
- 编译一个 profile 采集包并装到你手机（`flutter run --profile` 或 `flutter build apk --profile`）；
- 用 adb 抓取全程 `[PERF]` 时间线和 Flutter DevTools 的 UI/Raster 帧数据；
- 引导你按下面"标准操作路径"点 1 分钟；
- 出"每段耗时 + 超预算帧 + 根因排序 + 修前/修后对比"。

## 二、不方便连机：录屏也行

用另一台手机或系统录屏，录一段（约 30–60 秒），按这个**标准操作路径**：

1. 彻底关掉 App 再冷启动（看开屏到首页可点的时间）；
2. 底部五个 Tab：首页 → 圆梦 → 消息 → 我的，**来回切 2–3 轮**（重点看"第二次切回"是不是又闪骨架屏、要转圈）；
3. 在首页/艺人列表上下快速滑 5 秒（看掉帧/不跟手）；
4. 进一个艺人详情再返回（看转场和返回是否卡）。

把录屏发我，我结合埋点逻辑先做定性判断；精确毫秒数仍以方式一为准。

## 三、采集时会记录的时间点（`[PERF]`）

- `tab tap i= from=`：你点下底部 Tab 的瞬间；
- 各页 `initState / postFrame / load start`：页面被重建、开始加载；
- `request_start / request_end(xx ms,status)`：每个后端请求的起止与耗时（Dio 拦截器统一记录）；
- `meaningful frame n=`：真正有内容的第一帧绘制完成。

把这些点相减，就能区分：
- **点了没反应/转场慢** → A 输入/交互；
- **帧超 16.7ms、滑动掉帧** → B 渲染（全屏流光/模糊成本）；
- **白屏/骨架/转圈等待** → C 数据等待（已静态确认的 Tab 不保活、无会话缓存问题）；
- **视频转圈/黑屏** → D 媒体。

## 四、判定口径（达标线，来自执行协议 Gate0）

- 点 Tab：选中态/页面壳应"立即"有反馈（<1 帧，约 16.7ms 内）；
- 已访问过的主 Tab 切回：直接显示旧内容，**不再闪骨架屏**（当前实现做不到，是确定要修的 R1–R3）；
- 滑动：单帧 ≤16.7ms，无连续超预算帧；
- 网络：看 P50/P95，区分是服务器慢、网络慢还是前端等错地方；
- 任何"应该会变快"都不算数，必须有修前/修后同路径数据对比。

## 五、附：手动 adb 抓取命令（执行 AI 用）

```bat
:: 确认设备
C:\Android\platform-tools\adb.exe devices
:: 清理旧日志后只看 Flutter PERF 时间线
C:\Android\platform-tools\adb.exe logcat -c
C:\Android\platform-tools\adb.exe logcat -s flutter | findstr /C:"[PERF"
```

> 采集完成后把结果回填到 `docs/CURRENT_EXECUTION_STATE.md` 第 6 节性能基线表，再做 A/B 矩阵（流光开/关 × 真接口/本地固定数据，首进/二次各测一次）。
